7.3 Evaluation as a deliverable

"It seems to work well" is not something a bank's compliance team, or a hospital's clinical review board, can approve.

TL;DR
The AI Engineering track covers evaluation methodology in depth — this topic is about a different question: how evaluation results become a genuine deliverable a skeptical, often non-technical stakeholder can actually trust and approve. The evaluation dataset, methodology, and results need to be presented as evidence for a specific decision ("should we approve this for production use with real customer data"), not just as an internal engineering artifact.

Why the evaluation dataset itself needs to be defensible

A skeptical reviewer's first real question is often "how do I know these test cases represent what will actually happen in production, not just easy examples you picked." The defensible answer: build the evaluation set from real, representative production-like data (with appropriate anonymization), include known edge cases and adversarial examples deliberately, and be transparent about what the evaluation set does and doesn't cover — rather than presenting a curated, flattering sample as if it were comprehensive.

Showing failure cases, not just success rates

A specifically credibility-building move: proactively show a handful of cases where the system got something wrong, alongside your analysis of why and what mitigates it. A 100%-success presentation reads as either an easy test set or an incomplete one to anyone experienced enough to ask hard questions — showing genuine failure modes, honestly characterized, demonstrates a level of rigor that a clean success-only report can't.

Connecting evaluation to the specific risks from 7.2

A genuinely strong evaluation deliverable doesn't just report task accuracy — it specifically tests against the risk categories a security reviewer will ask about: does the evaluation set include adversarial prompt injection attempts? Does it test tenant isolation with deliberately crafted cross-tenant queries? Does it verify the system correctly refuses out-of-scope requests rather than attempting them with excessive agency? Answering these proactively, before being asked, is what separates a genuinely deployment-ready evaluation from a purely functional one.

Continuous evaluation after deployment, not just before

A one-time pre-launch evaluation answers "did this work at the time we tested it." A genuinely mature deployment includes ongoing evaluation sampling of real production traffic — connecting directly to 5.3's SLI/SLO material, treating evaluation metrics as a form of service-level indicator worth monitoring continuously, not just proving once at launch and then forgetting.

Check your understanding

1. Why should an evaluation dataset be built from representative, production-like data rather than a curated, easy sample?
The defensibility of the dataset itself is often scrutinized as closely as the results — an unrepresentative dataset undermines even genuinely good performance numbers.
2. Why does proactively showing failure cases build more credibility than presenting only success rates?
This is a specific credibility-building technique — demonstrating awareness of where a system falls short (and why it's mitigated) is more persuasive than an implausibly clean record.
3. Why should an evaluation deliverable specifically test against the security risk categories from 7.2, not just task accuracy?
This connects the two topics directly — a functionally accurate system that hasn't been evaluated against the specific risks a reviewer cares about hasn't actually answered the question that matters most for approval.
