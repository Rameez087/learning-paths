7.2 AI security for customer deployments

"In 2026, the attack doesn't happen at the model. It happens at the tool call." Most security teams are still only inspecting the wrong layer.

TL;DR
Only 14.4% of organizations send AI agents to production with full security or IT approval, while 82% of executives believe their existing policies already protect against unauthorized agent actions — a real, documented confidence gap. Prompt injection remains the #1 OWASP LLM risk, affecting roughly 34% of deployed agents; excessive agency jumped from 6th to 3rd place in the 2026 rankings specifically as agentic systems gained real tool access. For an FDE, this isn't abstract security theory — it's the specific set of risks that determine whether a customer's security team approves your deployment at all.

Why prompt injection resists a clean technical fix

The architectural reason prompt injection remains #1: instructions and data share one channel — the context window — and no equivalent of a parameterized query exists to separate them, so every mitigation lowers probability without ever reaching zero. This is a genuinely honest, important thing to tell a customer directly: defense-in-depth reduces risk meaningfully, but no vendor can credibly promise the risk is eliminated. Overpromising here is exactly the kind of claim that damages trust once it's inevitably tested.

Six control layers, the practical checklist

Complete AI agent security requires six layers working together: identity (who is this agent acting as), least-privilege access (can it only do what it genuinely needs to), runtime enforcement (checks applied while it's actually running, not just at design time), behavioral monitoring (does its current behavior look normal), audit logging (a durable record of every action, connecting directly to 7.1's audit requirement), and supply chain security (are the tools and packages it depends on genuinely trustworthy).

Tenant isolation: the specific failure mode multi-customer deployments must prevent

A specifically risky, documented pattern: a shared vector database where tenant data is only filtered at the application layer after retrieval — an attacker can craft a targeted embedding query that pulls another tenant's data into the context window before the filter ever applies. The safer pattern filters at the retrieval layer itself, or uses genuinely separate indexes per tenant, so cross-tenant data is never even fetched in the first place, not just hidden after the fact.

Check your understanding

1. Why can't prompt injection be fully "solved" the way a SQL injection vulnerability can be with parameterized queries?
This is a genuinely architectural limitation, not a solvable engineering bug — being honest about this with customers is more credible than overpromising a complete fix.
2. Why is a shared vector database with tenant filtering applied only at the application layer, after retrieval, considered a risky implementation?
The timing of the filter matters enormously — filtering after data has already been fetched into context is a fundamentally weaker guarantee than preventing the cross-tenant fetch from happening at all.
3. Why did "excessive agency" specifically jump from 6th to 3rd place in the OWASP 2026 rankings?
This ranking shift directly tracks the real-world shift toward agentic systems with genuine tool-calling capability — the risk became more pressing as the underlying technology's capabilities grew.
