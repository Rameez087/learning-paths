11.1 OWASP LLM risks in deployment

7.2 covered prompt injection, excessive agency, and tenant isolation. These are the other risks a customer's security review will ask about.

TL;DR
Beyond the agentic-specific risks in 7.2, four more OWASP LLM risk categories come up constantly in deployment reviews: insecure output handling (treating a model's output as trusted, executable content), sensitive information disclosure (a model leaking training data or context it shouldn't reveal), supply chain vulnerabilities (compromised models, packages, or datasets in the pipeline), and overreliance (humans trusting AI output without adequate verification). Each maps to a concrete, addressable deployment decision.

Insecure output handling: the trap of treating LLM output as safe

If an application takes a model's output and executes it — runs generated SQL directly, renders generated HTML without sanitization, executes generated shell commands — it's trusting content that could contain injected instructions (7.2) or simply model error, as if it came from a trusted source. The fix mirrors standard secure-coding practice: treat model output exactly like untrusted user input, validating and sanitizing it the same way you would anything else the model's context could have been influenced by.

Sensitive information disclosure: a real risk even without a training-data leak

Beyond the (rarer) risk of a model reproducing memorized training data, a more common and practical risk in enterprise deployments: a model's context window accumulates information across a conversation, and a poorly designed system can leak information from one part of a session into a response where it shouldn't appear — an internal system prompt detail, a piece of another user's data mistakenly included in context. The mitigation is architectural: minimize what actually goes into context, and treat the system prompt itself as something that could eventually be exposed, never as a place to put genuine secrets.

Supply chain: the model and package layer

A specific, real 2026 concern connects directly to 7.4's MCP security material: a compromised open-source model, a poisoned training dataset, or a malicious package in the AI toolchain can introduce vulnerabilities before any application code is even written. The practical FDE discipline: verify model provenance for any non-major-vendor model, and apply the same package supply-chain scrutiny (checking for known vulnerabilities, verified publishers) to AI-specific dependencies as to any other production dependency.

Overreliance: the human factor that no technical control fixes alone

A model can be technically well-evaluated (7.3) and still cause real harm if the humans using its output stop applying independent judgment — trusting a generated summary of a legal document without reading the source, or accepting an AI-suggested diagnosis without verification. This is why calibrated confidence signals and clear UI cues about AI-generated content (recall Phase 7.3's calibration discussion) matter as much as the model's raw accuracy — a highly accurate but overtrusted system can still produce a bad outcome the rare time it's wrong.

Check your understanding

1. Why should an application's use of LLM-generated content (SQL, HTML, shell commands) be treated the same way as untrusted user input?
This directly extends standard secure-coding discipline (never trust unvalidated input) to a new source of potentially untrustworthy content — the model's own output.
2. Why should a system prompt never be treated as a safe place to store genuine secrets?
This is a specific architectural discipline — genuine secrets belong in proper secrets management, not in a prompt whose contents could theoretically surface in an unexpected response.
3. Why can a technically well-evaluated, highly accurate model still contribute to a bad outcome due to overreliance?
This is why overreliance is listed as a distinct risk category from accuracy itself — a technically excellent model doesn't eliminate the risk of humans over-trusting its output on the occasions it's wrong.
