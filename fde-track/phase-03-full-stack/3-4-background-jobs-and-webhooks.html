3.4 Background jobs & webhooks

If a request takes longer than a user is willing to stare at a spinner, it doesn't belong in the request-response cycle anymore.

TL;DR
Anything slow, unreliable, or dependent on an external system — sending an email, processing an uploaded document, calling a rate-limited third-party API — belongs in a background job queue, not the synchronous request path. This keeps the user-facing response fast and lets a failed job retry independently without the user ever seeing an error for something that will resolve itself on retry. Webhooks are the receiving side of this same pattern: reacting to events pushed from an external system rather than blocking on a synchronous call to check for them.

What actually belongs in a queue

  • Anything calling a third-party API — that API's latency and reliability become your user's problem if it's in the synchronous path.
  • Anything processing a large file — document parsing, image processing, large data imports.
  • Anything that needs to retry on failure — a queue with retry logic handles this naturally; a synchronous request either succeeds immediately or the user sees a failure with no automatic second attempt.
  • Anything that can tolerate a delay of seconds to minutes — if the user genuinely needs the result in the same page load, it can't go in a queue; if they can wait for a notification, it usually should.

Webhook receivers need to be idempotent, always

Directly connecting back to 2.2's API integration material: a webhook sender (Stripe, GitHub, a customer's internal event bus) will retry delivery if it doesn't get a fast, successful response — meaning your receiver must handle getting the same event twice without creating a duplicate side effect. The practical pattern: check whether you've already processed an event with this specific ID before acting on it again, and always respond quickly (acknowledge receipt, then process asynchronously) rather than doing slow work inside the webhook handler itself, which risks the sender timing out and retrying unnecessarily.

Dead letter queues, one more time — now for webhooks and jobs

Recall the dead letter queue pattern from data pipeline reliability: a job or webhook that fails repeatedly (a malformed payload, a permanently unreachable dependency) shouldn't retry forever or silently vanish. Routing it to a dedicated failure queue after a bounded number of attempts means a human can inspect and resolve it — the same pattern, the same reasoning, applied at the application-integration layer instead of the data-pipeline layer.

Check your understanding

1. What's the practical test for whether a task belongs in a background job queue rather than the synchronous request path?
This is the core decision criterion — immediacy requirement, not task complexity alone, is what should drive the synchronous-vs-queued choice.
2. Why should a webhook handler acknowledge receipt quickly and process the actual work asynchronously, rather than doing slow work inside the handler itself?
This connects directly to the idempotency requirement — a slow handler risking a timeout-triggered retry is exactly the scenario that makes duplicate-safe processing necessary in the first place.
3. Why shouldn't a failing background job or webhook retry indefinitely?
This is the same dead letter queue reasoning from data pipeline design — a bounded retry count followed by routing to a failure queue is what prevents an unresolvable failure from consuming resources forever or silently disappearing.
