Phase 3 · Full-stack for FDEs

3.1 Frontend essentials

You don't need to be the best React developer in the building. You need to never be the reason a deployment stalls because "the frontend person isn't here today."

TL;DR
Current OpenAI FDE role descriptions explicitly include full-stack building as core work, not an occasional extra. The calibration that matters: enough React and TypeScript fluency to build a working internal tool or customer-facing interface without help, comfort with modern state management and API integration — but not the deep specialization a dedicated senior frontend engineer would have in animation, accessibility auditing, or design systems. The test is "can you unblock a deployment," not "could you pass a frontend-specialist interview."

Try it: what depth actually matters, by area

React component architecture
Must-have. You need to build functional components, manage props/state cleanly, and structure a page into sensible pieces — enough to build a working internal dashboard or customer-facing form without architectural help.
State management (useState/useEffect, or a library)
Must-have for anything beyond a static page. You don't need to have opinions on every state library's tradeoffs — you need to competently use whichever one the customer's existing codebase already uses.
API integration (fetch/axios, error handling, loading states)
Must-have — this is where frontend meets everything else you're building. Handling a slow or failed API call gracefully in the UI is a real, common failure point in customer demos.
CSS/design systems mastery
Basic awareness only. You need a page to look acceptable and functional — you don't need deep CSS specialist skills. Use an existing component library (the customer's, or a well-known one) rather than building visual polish from scratch.
Accessibility auditing, animation, performance profiling
Optional/skip for now, unless the specific engagement demands it. This is genuine specialist depth a dedicated frontend engineer would own — not the FDE's job to master unless nobody else on the team can.

Why "breadth over narrow depth" is the actual hiring signal

A senior backend engineer with eight years of distributed systems experience is not interchangeable with a full-stack generalist who knows a bit of everything — depth genuinely pays at senior, specialized roles. But FDE work specifically rewards the opposite trade: being unintimidated moving between a database schema one day and a frontend component the next, because a deployment blocker in a real customer engagement could be anywhere in the stack, and there often isn't a specialist on-site to hand it to.

What full-stack development alone doesn't teach

Full-stack technical range is necessary but not sufficient. What it doesn't cover on its own: customer discovery (Phase 9), production ownership inside an external organization's constraints rather than your own company's (Phase 6), and the AI-specific evaluation skills most 2026-era FDE roles now require (Phase 7). The technical overlap with a strong full-stack background is real and substantial — but it's not the whole job.

Check your understanding

1. What's the practical calibration test for how much frontend depth an FDE needs?
This is a deliberately practical bar — real fluency for the common blocking cases, not comprehensive specialist mastery of every frontend subdiscipline.
2. Why does FDE work specifically reward breadth across the stack rather than deep specialization in one layer?
This is specific to the embedded, often-solo nature of field engagements — the practical need to move across boundaries without a specialist backup is what makes breadth the higher-leverage trait here.
3. What does full-stack technical range NOT teach on its own, according to this material?
This is the honest gap-naming point — strong technical range is a real head start, but the customer-facing and external-ownership dimensions of the role are genuinely different skills layered on top.
