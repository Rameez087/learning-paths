3.3 Databases in integration contexts

You will almost never design a database from scratch as an FDE. You will constantly have to understand one someone else designed, years ago, with no documentation.

TL;DR
The database skill that actually matters most in FDE work isn't schema design from a blank slate — it's schema archaeology: walking into an unfamiliar customer database with no documentation and figuring out what it actually represents, where the real business logic is hiding (often in constraints, triggers, or stored procedures nobody remembers writing), and where it's safe to add something new without breaking what's already there.

Try it: walk through investigating an unfamiliar schema

Read-only first, always

Before writing a single integration query against a customer's production database, connect with read-only credentials and explore. Query the information schema (information_schema.columns, information_schema.table_constraints in Postgres/MySQL-family databases) to see actual column types, nullability, and foreign key relationships — this is more reliable than any stale documentation, since the schema itself can't lie about what it currently contains.

Signs a table is more load-bearing than it looks

  • Foreign keys pointing into it from many other tables — a heavily-referenced table is one where a change ripples widely; check this before touching its structure.
  • Triggers or stored procedures attached to it — business logic embedded in the database itself, invisible if you only read application code.
  • A column that's clearly overloaded — a generic "status" or "type" column with values that don't match any obvious enum, often a sign of years of ad-hoc extensions nobody refactored.
  • No foreign key constraints at all, despite an obvious relationship — sometimes deliberate (performance), sometimes a sign referential integrity is only enforced in application code you haven't seen yet.

Connection pooling: the detail that breaks integrations at scale

A database has a finite number of connections it can hold open. An integration that opens a new connection per request, rather than using a pool, can silently work fine in testing and then exhaust the customer's connection limit the moment real traffic hits it — a specific, common way a demo-quality integration fails in production without any code being "wrong" in isolation.

Check your understanding

1. Why is querying the information schema more reliable than existing documentation when investigating an unfamiliar customer database?
Documentation drifts out of sync with reality over time; the live schema, by definition, cannot — it's exactly what the database currently is.
2. Why might a table with many foreign keys pointing into it be riskier to modify than one with few or none?
This is a direct signal of how load-bearing a table is — the more things depend on its current shape, the more careful an integration needs to be before touching it.
3. Why can an integration that opens a new database connection per request work fine in testing but fail in production?
This is a classic scale-revealed failure — the code isn't wrong in isolation, but the pattern doesn't survive the jump from light testing traffic to real production load.

This topic reflects durable database-integration practice — connection pooling limits, schema investigation via information_schema, and the load-bearing-table heuristics here are stable, cross-database concepts rather than fast-changing tooling.
