3.2 Backend essentials

"A useful engineer can define API boundaries, choose storage based on access patterns, and identify where latency, concurrency, and failure handling affect product quality."

TL;DR
Backend depth for an FDE means being able to stand up a real service — routes, request validation, database access, error handling — using whatever the customer's stack already is, not just your personal favorite framework. FastAPI (Python), Express (Node), or a similar equivalent in the customer's chosen language are all fair game; the transferable skill is the underlying pattern, not the specific syntax. Knowing how software behaves after it leaves your local machine — deployment, observability, failure modes — is now considered core to the role, not a separate specialty.

A minimal service, in the shape that transfers across languages

# FastAPI example — the shape is what matters, not the syntax
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class OrderRequest(BaseModel):
    customer_id: str
    amount: float

@app.post("/orders")
def create_order(req: OrderRequest):
    if req.amount <= 0:
        raise HTTPException(status_code=400, detail="amount must be positive")
    # ... write to database, return confirmation
    return {"status": "created", "customer_id": req.customer_id}

The exact same shape — route, request validation, explicit error responses, a clear success path — reappears whether it's written in Express/Node, Spring/Java, or Gin/Go. Learning this pattern once and recognizing it everywhere is more valuable than deep mastery of one framework's specific idioms.

Choosing storage based on access patterns, not habit

A useful backend engineer picks between relational and non-relational storage based on how the data will actually be queried, not by defaulting to whatever they used last time. Relational (PostgreSQL) fits structured data with real relationships and transactional guarantees. Document/NoSQL stores fit flexible, evolving schemas or extremely high write throughput where strict relational consistency isn't the priority. An FDE frequently doesn't get to choose at all — the customer's existing systems dictate storage — which is exactly why understanding tradeoffs conceptually matters more than deep specialization in any one database product.

The 2026 expectation: DevOps basics are now inside "backend," not separate

The scope of "backend developer" has genuinely absorbed containerization and CI/CD basics — writing a working Dockerfile, understanding multi-stage builds, debugging a container that won't start, and having basic CI/CD fluency (build → test → deploy automation) are now considered baseline backend skill, not a separate DevOps specialty. This directly sets up Phase 4's cloud and infrastructure material.

This scope expansion reflects a genuine shift in what "shipping working software" requires — code that works locally but was never packaged or deployed correctly doesn't actually solve the customer's problem.
