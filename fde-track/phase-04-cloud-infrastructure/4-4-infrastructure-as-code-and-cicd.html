4.4 Infrastructure as code & CI/CD

Clicking through a console to create a server is fine for learning. It doesn't scale, it isn't repeatable, and it leaves no record of what changed or why.

TL;DR
Terraform (and similar tools) let you define infrastructure in version-controlled files — reviewable like code, roll-back-able, and reproducible from scratch in minutes. This single skill is specifically named as one of the fastest ways to move from "cloud user" to "cloud engineer" in an interviewer's eyes, and it matters even more for an FDE: a customer's security and compliance team can review a Terraform plan before it runs, which is a much easier conversation than trusting that manual console changes were done correctly.

Try it: run a Terraform plan, see exactly what would change

Why "plan" before "apply" is the whole safety model

terraform plan computes and displays exactly what would change — resources created, modified, or destroyed — without actually touching anything yet. terraform apply executes that plan. This separation matters enormously in a customer environment: you (and often the customer's own infrastructure team) can review the exact diff before anything real happens, catching a mistake that would otherwise only be discovered after a resource was already deleted.

State: the part of IaC that trips up newcomers

Terraform tracks a "state" file recording what it believes currently exists, so it can compute an accurate diff on the next plan. In a customer environment specifically, this state should live in shared, remote storage (not a local file on your laptop) so the whole team — and whoever picks up the engagement after you — is working from the same source of truth about what infrastructure actually exists.

CI/CD: the pipeline that turns "it works" into "it's actually deployed, tested, and safe"

A CI/CD pipeline (GitHub Actions, GitLab CI, Azure DevOps) automates build → test → deploy — running your test suite on every change, and only deploying if those tests pass. For FDE work specifically, this replaces "I tested it manually before I left the customer site" with an automated, repeatable gate that keeps protecting the deployment long after you've moved to the next engagement — directly serving Phase 1.3's "Handoff" stage, since a working CI/CD pipeline is part of what makes a system genuinely sustainable without you actively watching it.

This preview-before-action pattern is exactly the safety model that makes infrastructure changes reviewable — critical when a customer's own team needs confidence in what a change will actually do before it happens.

This connects directly to Phase 1.3's Handoff stage — a state file trapped on your personal laptop breaks the moment you're no longer the only person managing the infrastructure.
