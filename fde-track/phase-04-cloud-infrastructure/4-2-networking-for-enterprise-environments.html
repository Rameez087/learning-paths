4.2 Networking for enterprise environments

Your integration works perfectly on your laptop. It will not work the same way once it has to cross the customer's firewall.

TL;DR
A VPC (Virtual Private Cloud) is an isolated network boundary — the container everything else lives inside. Subnets divide that boundary into public (internet-facing) and private (internal-only) zones. A load balancer distributes traffic across multiple instances. Firewalls and security groups control exactly what traffic is allowed in or out, at a granularity down to specific ports and IP ranges. For an FDE, the practical skill isn't designing this architecture from scratch — it's reading an unfamiliar customer's existing network diagram and correctly predicting where your integration will get blocked before you find out the hard way.

Public subnet vs. private subnet: the distinction that determines your entire architecture

A public subnet has a route to the internet gateway — resources here can be reached directly from outside (a load balancer, a bastion host). A private subnet has no direct internet route — resources here (application servers, databases) are only reachable from inside the VPC or through a controlled path like a NAT gateway. The standard, security-conscious pattern: public-facing components sit in public subnets, everything else — especially databases — sits private, reachable only through the application layer in front of it.

DNS: the layer that quietly breaks integrations

A surprising share of "the integration doesn't work" tickets trace back to DNS — an internal hostname that only resolves inside the customer's network, a stale DNS cache, or a service that's actually reachable but only by an IP address nobody documented. When debugging a connectivity issue, checking whether DNS resolution itself is succeeding (before assuming the actual service is down) is a fast, frequently-skipped diagnostic step.

Reverse proxies and TLS termination

A reverse proxy (nginx, an API gateway, a cloud load balancer) sits in front of your application, often handling TLS termination — decrypting HTTPS traffic once at the edge so your application doesn't have to manage certificates itself. This matters for an FDE specifically because customer environments frequently have their own reverse proxy or WAF (Web Application Firewall) layer in front of anything you deploy — understanding that this layer exists and what it might be rewriting or blocking is often the missing piece when something works locally but not once deployed inside the customer's network.

1. What's the key difference between a public and private subnet?
This routing difference is exactly why sensitive components (databases) are placed in private subnets — there's no direct path in from the internet to attack, only through the controlled application layer in front.
2. Why should DNS resolution be checked early when debugging a connectivity issue, rather than assuming a service is actually down?
This is a fast, frequently-skipped diagnostic step — ruling out DNS early can save significant time compared to investigating the application layer when the actual problem is name resolution.
3. Why does understanding a customer's existing reverse proxy or WAF layer matter for an FDE specifically?
This is exactly the "customer's environment is not clean" reality (Phase 6) — an integration that's technically correct can still fail once it has to pass through infrastructure layers you didn't design and may not initially know exist.
