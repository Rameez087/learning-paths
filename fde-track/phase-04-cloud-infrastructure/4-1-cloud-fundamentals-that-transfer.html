4.1 Cloud fundamentals that transfer

The large majority of enterprises now run more than one cloud provider at once. Learning "AWS" instead of "cloud compute" is learning the wrong layer.

TL;DR
Every major cloud provider offers the same underlying primitives with different names: virtual compute, object storage, managed relational databases, identity and access management, virtual networking. An FDE who understands the concept of IAM, or object storage, or a managed database can pick up a customer's specific provider's console in days — an FDE who only memorized AWS's specific button layout has to relearn everything from scratch the moment a customer runs Azure or GCP instead.

Go deep on one, but learn the concept layer first

Current guidance is specific: go deep on one platform rather than shallow across three for your daily working fluency — but learn the underlying concepts (compute, storage, networking, IAM, cost models) in a way that isn't tied to any single provider's terminology. This is exactly why this topic exists before any provider-specific material: the concept transfers immediately once you understand it once, properly.

Why "which cloud should I learn" is the wrong first question for an FDE

A dedicated cloud engineer might reasonably specialize deeply in one provider. An FDE doesn't get to choose — the customer's existing infrastructure choice dictates which provider you're actually working in in any given engagement. This is precisely why understanding transferable concepts matters more here than it would in a role where you pick your own stack: you need to be productive in whichever cloud the customer already runs, on day one of the engagement.

The mandatory security baseline, regardless of provider

  • Never use the root/owner account for daily work — create scoped accounts or roles instead.
  • Enforce MFA on every account with meaningful access.
  • Use IAM roles, not long-lived static keys, wherever the provider supports it.
  • Keep sensitive resources in private subnets, not directly internet-facing.
  • Enable audit logging (CloudTrail, Azure Activity Log, GCP Audit Logs) — you'll need this the first time something goes wrong and someone asks "what changed."

Check your understanding

1. Why does understanding cloud concepts transfer better than memorizing one provider's specific console and terminology?
This is exactly why the topic is framed around concept-first learning — an FDE who understands "managed relational database" as a concept adapts quickly to RDS, Azure SQL, or Cloud SQL, while someone who only learned button locations has to start over.
2. Why does the standard "go deep on one platform" cloud-learning advice apply differently to an FDE than to a dedicated cloud engineer?
This is a direct consequence of the embedded, customer-driven nature of FDE work — you go where the engagement takes you, which is exactly why the concept layer (not one provider's specifics) is the priority here.
3. Why is enabling audit logging (CloudTrail, Activity Log, etc.) specifically called out as a mandatory baseline, not an optional nicety?
This connects directly to Phase 2.4's debugging-under-pressure material — having a reliable record of changes is exactly what lets you correlate an incident with its actual cause quickly.
