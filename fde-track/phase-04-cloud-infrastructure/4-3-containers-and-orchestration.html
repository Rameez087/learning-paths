4.3 Containers & orchestration

"It works on my machine" stops being a valid excuse the moment your machine and the customer's production server can be made to run literally the same environment.

TL;DR
Docker packages an application with everything it needs to run — dependencies, runtime, configuration — so it behaves identically on your laptop and in production. Kubernetes orchestrates containers at scale: scheduling them across machines, restarting failed ones, and scaling up or down based on load. For an FDE, the practical bar is writing a working Dockerfile and debugging a container that won't start — not deep Kubernetes cluster administration, which is usually a specialized platform team's job even at companies that run Kubernetes extensively.

A minimal Dockerfile, and what each line actually does

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

FROM picks a known-good base image rather than building an OS from scratch. WORKDIR and COPY get your code into the image. Ordering matters for build speed: copying requirements.txt and installing dependencies before copying the rest of the code means Docker can cache that expensive install step — it only re-runs when dependencies actually change, not on every single code edit.

Multi-stage builds: the detail that keeps images small and secure

A multi-stage build uses one stage to compile or build the application (with all the heavy build tools that entails) and a second, much slimmer stage that copies only the final built artifact — leaving compilers, build caches, and dev dependencies behind entirely. This directly matters for an FDE: a smaller final image deploys faster into a customer's environment and has a meaningfully smaller attack surface for their security team to review.

Why Kubernetes cluster administration usually isn't the FDE's job

Most organizations running Kubernetes at any real scale have a dedicated platform or infrastructure team managing the cluster itself — node provisioning, cluster upgrades, network policy at the cluster level. The FDE's practical Kubernetes skill is usually one layer up: understanding pods, deployments, and services well enough to deploy an application onto an existing cluster and debug why a pod won't start, rather than standing up or administering the cluster infrastructure itself.

Check your understanding

1. Why does the order of COPY and RUN commands in a Dockerfile matter for build speed?
Docker's layer caching is order-dependent — putting the rarely-changing dependency install before the frequently-changing application code maximizes how often the cache can be reused.
2. What does a multi-stage Docker build achieve that a single-stage build doesn't?
The value is specifically in what gets left behind — a slim final stage copies only the built artifact, not the entire toolchain used to build it.
3. Why is deep Kubernetes cluster administration usually not part of the FDE's practical skill bar?
This mirrors the calibration principle from Phase 3 — matching depth to what the role actually requires, rather than mastering every adjacent specialization to its fullest extent.
