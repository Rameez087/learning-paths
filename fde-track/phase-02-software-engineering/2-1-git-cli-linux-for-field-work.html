2.1 Git, CLI & Linux for field work

You won't have your usual IDE setup, your usual permissions, or a helpful Slack channel. You will have a terminal.

TL;DR
Field engagements strip away comfort tooling fast: a jump box with no GUI, a locked-down environment where you can't install your preferred editor, a git history left in a confusing state by whoever touched the repo before you. The bar for this phase isn't "know every git flag" — it's being able to diagnose and recover from an unfamiliar Linux environment and a messy git history without needing to ask someone else to do it for you.

Try it: pick the right move for each field scenario

Why "detached HEAD" trips people up specifically in the field

Checking out a tag or a specific commit (common when reproducing a customer-reported bug against an old release) puts you in a detached HEAD state — commits you make there aren't on any branch, and they can look "lost" the moment you check out something else. They're not actually gone: git reflog keeps a local record of every place HEAD has pointed, letting you recover commits that look lost but aren't garbage-collected yet.

The Linux skills that actually matter under field conditions

  • Reading, not just running — ps aux, df -h, du -sh *, journalctl, and tail -f for logs are what you reach for when something's wrong and nobody can explain why yet.
  • Permissions literacy — understanding chmod/chown, sudo policies, and why a customer's security team locked down exactly what they locked down, rather than fighting it blindly.
  • Piping and text processing — grep, awk, sed, and jq for parsing logs and JSON output on a box with no fancy tooling installed.
  • tmux or screen — a long-running process on a remote box needs to survive your SSH session dropping, which it will, at the worst possible moment.

Git operations worth being fluent in, not just aware of

Beyond commit/push/pull: git bisect for finding which commit introduced a regression in an unfamiliar codebase, git stash for quickly parking uncommitted work when you need to switch context fast, git cherry-pick for pulling one specific fix across branches without a full merge, and git reflog as the general safety net for "I thought I lost work" moments.

Check your understanding

1. Why do commits made in a "detached HEAD" state appear to disappear when you check out something else?
The commits still exist in git's object database until garbage collected — reflog is specifically what lets you find and recover them before that happens.
2. Why does tmux or screen matter specifically for field work on remote customer boxes?
Terminal multiplexers decouple a running process from the specific SSH connection that started it — critical when working over unreliable or restricted customer network connections.
3. Why is understanding permissions and sudo policy framed as "literacy" rather than something to fight against?
This connects directly to Phase 6's "the customer's environment is not clean" mindset — working within real constraints, understanding their reasons, is part of the actual job, not an obstacle to route around.

This topic draws on established, durable Linux/git practices rather than fast-changing tooling — the specific commands here have been stable for years and are unlikely to become obsolete.
