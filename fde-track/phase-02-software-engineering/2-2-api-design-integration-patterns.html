2.2 API design & integration patterns

REST is 89% of enterprise API usage — but the customer's ancient SOAP finance system doesn't care what's popular.

TL;DR
Most production systems mix protocols, and the FDE's job is picking the right one per integration point, not having a single favorite. REST remains the foundation for public and web-facing APIs. GraphQL fits complex, client-driven queries. gRPC dominates high-performance internal microservices. Webhooks handle event-driven notifications without polling. SOAP is "still relevant in enterprise and financial sectors" — which for an FDE means: expect to integrate with it, whether or not you'd choose it yourself.

The decision that actually matters: who gets to call the API?

Before picking a protocol, decide the access level — public, partner, or internal — since each carries distinct tradeoffs around documentation, security, and versioning. A public developer API and an internal microservice call have almost nothing in common in terms of what "good API design" means for each. This ordering (access level first, protocol second) is specifically flagged as the right starting point, not the reverse.

2026's mandatory security baseline, regardless of protocol

  • Authentication — OAuth 2.0 + JWT for user-facing APIs, API keys for service-to-service, mTLS for high-security microservices. Never basic auth in production.
  • Authorization — RBAC for most applications, ABAC for complex permission models, and always validated server-side — never trust the client's claim about its own permissions.
  • Rate limiting — per-user and per-IP limits with progressive throttling, returning 429 with a Retry-After header rather than silently dropping requests.
  • Monitoring — logging every request with timestamp, user, endpoint, and response time, alerting on elevated 5xx rates, and tracking p50/p95/p99 latency per endpoint.

Webhooks: the pattern that quietly powers most integrations

Rather than polling a system repeatedly asking "did anything change yet," a webhook lets the source system push a notification the moment something happens. This is efficient and low-latency, but introduces a real FDE-relevant risk: your endpoint needs to handle receiving the same webhook more than once (network retries are common) — which is exactly why the idempotency concepts covered in the Data Science track's pipeline reliability material apply here too, just at the API layer instead of the data layer.

Check your understanding

1. What should be decided before choosing which API protocol to use for an integration?
Access level fundamentally changes what "correct" design looks like — a public API and an internal microservice call have almost nothing in common in their actual requirements.
2. Why must a webhook receiver be built to handle receiving the same event more than once?
This is the same idempotency principle from data pipeline reliability, applied at the API integration layer — a webhook consumer needs to be safe against re-delivery, not just correct on the happy path.
3. Why does 2026 guidance specifically say "never basic auth in production," even though it's simple to implement?
Modern auth guidance favors tokens (JWT, OAuth) specifically because they support expiration, scoping, and revocation in ways that a static username/password pair sent on every request does not.
