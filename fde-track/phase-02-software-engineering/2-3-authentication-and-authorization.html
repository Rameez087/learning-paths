2.3 Authentication & authorization

"OAuth is for delegated access, OIDC is for logging users in, and SAML is for logging users in via XML federation." One sentence, and most of the confusion disappears.

TL;DR
Authentication answers "who are you?" — authorization answers "what can you do?" They're separate concerns solved by separate protocols. OAuth 2.0 is not an authentication protocol — it's for delegated access. OIDC and SAML both handle authentication; OIDC builds on OAuth for modern, mobile-native apps, while SAML is an older XML-based standard many large enterprises still require. Production enterprise SSO is a three-legged stool: SAML or OIDC for login, SCIM for user lifecycle management, and MFA/audit logging for compliance. Most 2026 enterprise procurement checklists require all three — shipping SSO without SCIM still fails security reviews.

Why OIDC is called "mobile-native" and SAML isn't

OIDC and OAuth 2.0 assume REST + JSON over HTTPS, with Authorization Code + PKCE as the recommended flow for every client type — web apps, single-page apps, mobile, desktop, CLIs. For machine-to-machine calls, OAuth's Client Credentials grant has no SAML equivalent at all. The practical consequence for an FDE: if the customer's product has a mobile app, a CLI, or any non-browser client, SAML alone genuinely can't cover it — you'll need OIDC there regardless of what the customer's identity provider prefers for their browser-based tools.

Why SAML still shows up constantly despite the friction

There's a real, non-nostalgic reason regulated enterprises still demand SAML in 2026: procurement and compliance, not technical preference. Many large customers' identity infrastructure was built around SAML years ago, and migrating it is a genuine undertaking a single vendor integration can't force. This is exactly the kind of "customer's environment is not clean" reality Phase 6 covers directly — the FDE has to support what the customer actually runs, not what's cleanest to implement.

SCIM: the lifecycle piece that's easy to forget

SSO alone answers "can this person log in." SCIM (System for Cross-domain Identity Management) is a separate REST API the customer's identity provider calls to create, update, and — critically — deactivate users in your application automatically, in near real time. A common, costly gap: an employee leaves the customer's company, IT deactivates them centrally, but without SCIM they can still log into your specific application because nothing told it to revoke access. This offboarding gap is exactly what most 2026 enterprise security reviews now specifically check for.

RBAC vs. ABAC: two different authorization models

Once someone's authenticated, authorization decides what they can actually do. RBAC (Role-Based Access Control) assigns permissions to roles — "Admin," "Editor," "Viewer" — and users inherit permissions from their assigned role, simple and sufficient for most applications. ABAC (Attribute-Based Access Control) evaluates permissions dynamically against attributes — department, data sensitivity, time of day, request context — needed for more complex permission models than a fixed set of roles can express. Both must be validated server-side; a client claiming "I'm an admin" is never sufficient on its own.

Check your understanding

1. Why is OAuth 2.0 not itself an authentication protocol, despite being central to modern login flows?
This distinction matters practically — OAuth alone tells you a client has permission to access something on a user's behalf, but doesn't itself establish who that user is; OIDC adds that identity layer.
2. Why can SAML alone be insufficient for a product with a mobile app or CLI client?
This is a genuine architectural gap, not a preference — SAML's browser-redirect-based flow doesn't map cleanly onto mobile, CLI, or service-to-service authentication the way OIDC's modern flows do.
3. What specific problem does SCIM solve that SSO alone does not?
This offboarding gap — someone leaves the company but retains access to a specific application because nothing told it to revoke access — is exactly the security review failure SCIM is built to prevent.
