8.3 Design: a customer support agent

The agent needs real tool access — to check order status, issue refunds, update account details. That's exactly where 7.2's "excessive agency" risk stops being theoretical.

The scenario: An e-commerce company wants an AI agent to handle tier-1 support: answering order status questions, processing straightforward refunds under $50, and updating shipping addresses — escalating anything more complex or higher-value to a human agent. The agent needs access to the order management system, the payment processor, and the customer database.
TL;DR
This is where 7.2's excessive agency principle becomes a concrete design decision, not an abstract risk. The agent's tool permissions need to be scoped precisely to the stated task — refund authority capped at exactly $50, no access to modify payment methods, no ability to issue refunds above the threshold even if a user's message tries to talk it into one. The escalation path to a human isn't a fallback bolted on afterward — it's a first-class part of the design from the start.

Why the $50 refund cap has to be enforced outside the model, not inside a prompt

A system prompt instruction like "never refund more than $50" is a suggestion the model usually follows — not a guarantee, given 7.2's point that prompt injection can never be fully eliminated. The actual enforcement has to live in the tool itself: the refund tool's API should hard-reject any refund request over $50 at the code level, regardless of what the model asks for. The model's job is deciding whether to call the tool; the tool's job is being genuinely safe to call, even if the model is somehow manipulated into calling it wrongly.

Designing the escalation path as a real feature, not an apology

A poorly designed escalation just says "I can't help with that" and leaves the customer stranded. A well-designed one hands off with full context: the human agent receiving the escalation should see the conversation history, what the AI agent already tried, and why it escalated — not start from zero. This connects to 7.3's evaluation principle: a system that fails gracefully and informatively is more trustworthy than one that either fails silently or never admits it needs help.

Audit logging every action, especially the ones that touch money

Directly from 7.1 and 7.2: every refund the agent issues, every address change it makes, needs a durable, timestamped log entry — not just for debugging, but because "an AI system moved customer money" is exactly the kind of action a finance or compliance team will want to review after the fact, whether or not anything went wrong.

1. Why should the $50 refund cap be enforced in the refund tool's code, rather than only as an instruction in the system prompt?
This is 7.2's prompt injection limitation applied directly to a design decision — real enforcement has to live in a layer that can't be talked out of its rules the way a model's behavior sometimes can.
2. What makes an escalation-to-human design "well-designed" versus poorly designed, according to this material?
Treating escalation as a first-class feature (with context handoff) rather than an afterthought is what makes the overall system feel trustworthy even when the AI can't complete the task itself.
3. Why does every refund and account change the agent makes need a durable audit log entry?
This connects to 7.1's audit logging requirement — financially consequential actions specifically warrant a durable record regardless of whether an error ever actually occurs.
