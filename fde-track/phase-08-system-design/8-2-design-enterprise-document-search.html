8.2 Design: enterprise document search

The customer's 40,000 internal documents live across SharePoint, a legacy DMS, and a shared drive nobody's cleaned up since 2019.

The scenario: A professional services firm wants employees to search across all internal documents (contracts, past project reports, internal policy documents) using natural language, with answers grounded in the actual source documents — not hallucinated. The documents are scattered across three different systems with different access permissions per document. Some documents are highly confidential and restricted to specific teams.
TL;DR
This is fundamentally a RAG system — the AI Engineering track's Phase 6 covers RAG architecture in full technical depth. What's specifically FDE work here: the ingestion pipeline has to pull from three different source systems with different APIs and permission models (Phase 6.3's legacy investigation skills), and critically, permissions must be enforced at retrieval time, not just at the UI layer — a document a user isn't authorized to see must never enter their retrieved context, connecting directly to 7.2's tenant isolation principle applied to per-user permissions instead of per-tenant.

Why permission-aware retrieval is the design's hardest real constraint

The naive design retrieves the most relevant chunks first, then checks if the user can see each one, hiding unauthorized results from the response. This has the same flaw as 7.2's tenant isolation anti-pattern: the restricted content was already pulled into the retrieval pipeline and potentially into the context sent to the model, even if it's hidden from the final displayed answer. The correct design filters the vector search itself by the requesting user's actual permissions, so unauthorized documents are never retrieved into context at all.

The ingestion pipeline: where 6.3's investigation skills apply directly

Three source systems means three different ingestion connectors, each needing to correctly capture that document's specific permission metadata alongside its content — not just the text. This is exactly 6.3's legacy investigation work: understanding each system's actual permission model (is it role-based? per-document ACLs? group membership?) well enough to translate it correctly into your search index's permission filter, rather than guessing or oversimplifying.

What "grounded, not hallucinated" requires architecturally

Beyond a good RAG pipeline (AI Engineering track), the deliverable this customer actually cares about is trust: every answer needs a visible citation back to the specific source document and section it came from, letting a skeptical user verify the answer themselves rather than trusting the system blindly. This is a direct product requirement flowing from 7.3's "evaluation as a deliverable" mindset — the system needs to be verifiably trustworthy, not just accurate in aggregate.

Stale content: the operational problem after launch

A contract that gets superseded, a policy document that gets updated — if the search index doesn't reflect these changes, employees can be confidently shown outdated information. The design needs an ongoing re-indexing strategy synced to each source system's actual update events (Phase 6.5's webhook/event integration pattern), not just a one-time ingestion at launch.

Check your understanding

1. Why is filtering permissions only at the UI/display layer an insufficient design for this system?
The timing of the filter matters just as much here as it did in 7.2 — hiding something after it's already been fetched into context is a fundamentally weaker guarantee than never fetching it at all.
2. Why does ingesting from three different source systems require applying Phase 6.3's legacy investigation skills specifically?
This is a direct application of the schema/system archaeology discipline — getting permission metadata wrong here doesn't just cause a bug, it causes an actual data access violation.
3. Why does this system specifically need visible citations back to source documents, beyond just being accurate?
Aggregate accuracy isn't the same as verifiable trust for any individual answer — citations let a skeptical user check the specific claim in front of them, which is a distinct and important product requirement.

This worked design applies RAG architecture from the AI Engineering track's Phase 6, permission/tenant-isolation principles from 7.2, and legacy system investigation from 6.3.
