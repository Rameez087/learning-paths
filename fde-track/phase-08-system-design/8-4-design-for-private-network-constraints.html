8.4 Design: private network constraints

A hospital's patient data legally cannot leave their private network. Your AI system still needs to reason over it.

The scenario: A healthcare provider wants an AI system to help clinicians quickly find relevant information in patient records. Regulatory requirements mean patient data must never leave the hospital's private network — not even transiently to a cloud LLM API. The hospital has an internal GPU cluster, but no team experienced in running production ML infrastructure.
TL;DR
This scenario forces a genuinely hard tradeoff between 8.1's constraint-stacking principle and reality: "data can't leave the network" and "we want frontier-model-quality reasoning" can directly conflict, since the best-performing models are typically only available via cloud API. The design has to resolve this honestly — usually by running a capable open-weight model on the hospital's own infrastructure, accepting a real capability tradeoff in exchange for a non-negotiable compliance requirement, rather than pretending the conflict doesn't exist.

Why "de-identify then call cloud" is tempting but genuinely risky here

A hybrid approach — strip identifying information, call a cloud API with the de-identified text, reattach identity afterward — sounds like a clever compromise. The real risk: reliable de-identification of unstructured clinical text is a hard, imperfect problem in its own right, and a compliance team is unlikely to accept "we're pretty confident this removes all identifying information" as sufficient for a legally binding requirement. This is exactly the kind of tradeoff that needs to be surfaced honestly (8.1) rather than presented as a clean solution.

The "no experienced ML infrastructure team" constraint changes the design too

An on-premise deployment on a GPU cluster the hospital already owns still needs someone capable of running it reliably — model serving, monitoring (Phase 5), incident response when it degrades. If the hospital genuinely lacks this expertise, the honest design includes a concrete answer to "who operates this after the FDE leaves" (Phase 1.3's Handoff stage) — perhaps a managed on-premise deployment offering, or a deliberate knowledge-transfer plan, not just "here's a working system, good luck."

Why this scenario is a genuinely good test of FDE judgment

There's no clean, fully-satisfying answer here — every option gives up something real. A junior response might present the on-premise model as strictly correct without acknowledging the real capability tradeoff being made. A stronger response states plainly: "we're trading some model quality for a non-negotiable compliance requirement, here's specifically what that costs in practice, and here's how we'll monitor whether that tradeoff remains acceptable as the system is used in practice."
