6.2 Identity & access at scale

The average enterprise manages over 1,000 applications, with employees accessing 67+ tools daily. Identity is the layer that has to hold all of that together.

TL;DR
Building on 2.3's OAuth/OIDC/SAML/SCIM foundations: at real enterprise scale, identity infrastructure is centered on a directory (Active Directory or LDAP, often for decades of accumulated on-premise accounts) federated out to cloud applications via an identity provider (Okta, Entra ID, Ping). The specific FDE-relevant skill: understanding how a new application gets connected into this existing structure — not designed from scratch, but integrated into infrastructure that predates your engagement by years, sometimes decades.

Active Directory and LDAP: still the foundation underneath everything

A large share of enterprise identity infrastructure still runs on Active Directory (Microsoft's directory service) or LDAP more generally — the accumulated record of every employee account, often going back decades. Modern cloud identity providers don't replace this; they sync with it. Microsoft's own guidance for hybrid environments is specific: define directory synchronization (via Entra Connect Sync or Cloud Sync) and the sign-in method deliberately, rather than assuming a clean cloud-only setup — because for most real enterprises, it isn't clean or cloud-only.

The specific problem SCIM solves at scale, again

Recall 2.3's SCIM lifecycle point — now consider it at the scale of 1,000+ applications and thousands of employees. Without automated provisioning, every new hire, role change, and departure requires someone manually touching every affected application — a process that doesn't scale and reliably produces exactly the security gap 2.3 described (departed employees retaining access somewhere nobody remembered to check). SCIM automates the "joiner, mover, leaver" lifecycle across every connected application at once.

When a legacy system can't support modern protocols

Not every system in a real enterprise supports SAML, OIDC, or SCIM natively — some genuinely can't be upgraded easily. The practical pattern: a gateway or proxy layer that translates between the modern protocol your new application speaks and whatever legacy interface the old system actually exposes, rather than either forcing the legacy system to change or abandoning standard protocols for your new work. This is a real, common piece of FDE integration work, not a hypothetical edge case.

Application Proxy: exposing internal apps without a permanent VPN

A specific modern pattern worth knowing: rather than requiring every user to be on a VPN to reach an internal application, an application proxy (like Entra Application Proxy) can publish that internal app externally while still enforcing the customer's existing access controls — letting remote and external access work without the operational overhead of managing VPN access for every single internal tool.

Check your understanding

1. Why do modern cloud identity providers typically sync with Active Directory or LDAP rather than replacing them?
This connects directly to 6.1's mindset — the customer's real infrastructure has real history, and identity systems are exactly where that history is most durably encoded.
2. Why does SCIM's value increase specifically at the scale of a large enterprise, compared to a small application?
The underlying problem (access not being revoked promptly) exists at any scale, but the sheer volume of applications and personnel changes at enterprise scale makes manual handling genuinely infeasible.
3. What does an application proxy pattern solve that a traditional VPN-only approach doesn't?
This is specifically an operational-overhead reduction — publishing individual apps through a proxy avoids the administrative burden of granting and managing VPN access as the standard path to every internal tool.
