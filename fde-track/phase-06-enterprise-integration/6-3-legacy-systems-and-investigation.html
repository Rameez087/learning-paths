6.3 Legacy systems & investigation

There's a 20-year-old system nobody fully understands, and you have two weeks to integrate with it. This is not a hypothetical.

TL;DR
A legacy system is one where the original builders are gone, the documentation is stale or missing, and the actual behavior lives in the code itself — not in anyone's memory. Investigating one safely means the same schema-archaeology discipline from 3.3, extended to the whole system: observe before touching, find the actual behavior through logs and traffic rather than assumptions, and identify which parts are load-bearing before changing anything near them.

Try it: work through investigating an unfamiliar legacy system

SOAP, WSDL, and other things you'll meet that aren't in most tutorials

SOAP remains genuinely common in enterprise and financial sectors specifically — a real, current fact, not a historical footnote. A WSDL (Web Services Description Language) file describes a SOAP service's available operations and message formats; reading one is closer to reading a formal contract than exploring a REST API's documentation. The practical skill isn't loving SOAP — it's being able to work with it competently when a customer's finance or logistics system speaks nothing else.

Batch files, scheduled jobs, and undocumented cron entries

Many legacy integrations aren't APIs at all — they're a scheduled job that drops a file in a specific directory at 2am, which another system picks up and processes. Before assuming a modern API-based integration is the way forward, check what's actually already running: crontab -l, scheduled task lists, or a review of any existing batch/ETL tooling. Replacing or working alongside an existing batch process well often matters more than the elegance of your new integration's design.

The "nobody knows why this exists" rule

A specific, disciplined habit: when you find something that seems clearly wrong or pointless — a redundant field, a check that seems unnecessary, a weird conditional — resist the urge to "clean it up" immediately. It may be handling an edge case from years ago that isn't documented anywhere but is still actively protecting against a real failure mode. Ask before removing; Chesterton's Fence applies with particular force in systems this old.

This is a current, practical fact rather than a legacy footnote — specific industries genuinely still run on it, which is exactly why it belongs in a skill set built around working with real customer infrastructure.
2. Why should an FDE check for existing scheduled jobs or batch processes before assuming a new API-based integration is the right approach?
This connects directly to 6.1's mindset — understanding what already exists and works (even if unglamorous) takes priority over defaulting to a preferred modern pattern.
3. Why does the "nobody knows why this exists" rule specifically caution against immediately removing seemingly pointless code in a legacy system?
This is Chesterton's Fence applied to legacy systems specifically — the absence of documentation for why something exists is not evidence that it's safe to remove, especially in systems this old and undocumented.
