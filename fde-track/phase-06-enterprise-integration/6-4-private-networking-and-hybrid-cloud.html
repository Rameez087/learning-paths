6.4 Private networking & hybrid cloud

The customer's security team will not open an inbound firewall port for you. Plan the integration assuming that answer from day one.

TL;DR
Real enterprise customers frequently run hybrid infrastructure — some systems on-premise, some in one or more clouds — connected through VPNs, private links, or relay-style patterns that avoid opening inbound firewall rules entirely. A specific, increasingly common pattern: an agent or relay running inside the customer's network makes an outbound connection to your service, avoiding the need for any inbound firewall exception at all — since outbound connections are almost always allowed, while inbound ones require security approval that can take weeks.

Why the outbound-only relay pattern has become genuinely popular

A concrete real-world example: a relay-based connection can let a gateway listen for inbound requests over what is actually an outbound HTTPS connection — meaning no inbound firewall rules are required at all on the customer's side. This matters enormously for FDE timelines: requesting a new inbound firewall exception often means weeks of security review, while an outbound connection frequently needs no special approval, since the customer's network already permits outbound HTTPS traffic by default.

Hybrid cloud is the default assumption, not the exception

Assume the customer runs more than one environment — some combination of on-premise infrastructure and one or more cloud providers — until you've confirmed otherwise. This isn't pessimism; it's simply the statistical default for real enterprises in 2026. Planning an integration around a single, clean cloud environment and then discovering mid-engagement that critical data actually lives on-premise is a specifically avoidable mistake if hybrid complexity is assumed from the start of discovery (Phase 9).

Latency becomes a real design constraint across hybrid boundaries

A call that crosses from your cloud service to an on-premise system (or vice versa) through a VPN tunnel carries real latency that a same-datacenter call doesn't. This isn't just a performance nicety — it can change architectural decisions: whether a call belongs in the synchronous request path (3.4) or should be queued, and how aggressively you can afford to make repeated round-trip calls across that boundary versus batching them.
