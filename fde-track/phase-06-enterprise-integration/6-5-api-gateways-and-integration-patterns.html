6.5 API gateways & integration patterns

A modern integration platform replaces the ESB, the point integrations, the partner gateway, and the batch tool — in a single environment, if you consolidate deliberately instead of adding yet another one-off connection.

TL;DR
An API gateway sits in front of your services, handling cross-cutting concerns centrally — authentication, rate limiting, request routing, logging — so individual services don't each reimplement them. For an FDE, the practical value is specific: a customer's existing gateway is often the correct place to register your new integration, rather than building a parallel path around it. Closing Phase 6, this ties directly back to 6.1's consolidation principle: routing through the existing gateway is itself a small act of not adding new integration debt.

iPaaS: consolidating what used to be many separate tools

A modern Integration Platform as a Service can replace what used to require an ESB (Enterprise Service Bus), a set of individual point integrations, a separate partner gateway, and a batch orchestration tool — all in one environment. This matters for an FDE specifically when a customer is mid-migration: understanding whether the customer already has (or is building toward) a consolidated platform changes whether your new integration should plug into that platform or risk becoming one more point tool that needs retiring later.

Webhooks and events as an alternative to gateway-fronted APIs

Not every integration point is a request-response API behind a gateway — recall 3.4's webhook material. Some enterprise systems specifically publish events (a new order created, a record updated) that your integration subscribes to, rather than you calling them directly. This pattern is common in customer environments with existing enterprise messaging infrastructure (a message bus, an event stream) — plugging into an existing event stream is often less invasive than adding a new synchronous API dependency to a system already under load.

The full Phase 6 synthesis: "not clean" is workable, with the right posture

Across all five topics in this phase, the same underlying discipline recurs: understand what already exists (6.1's inventory-first principle), work with existing identity infrastructure rather than around it (6.2), investigate before touching anything (6.3), plan for realistic hybrid connectivity constraints (6.4), and integrate through existing gateways and patterns rather than adding new debt (6.5). None of this is about avoiding complexity — it's about meeting real complexity with a consistent, disciplined process rather than assumptions.
