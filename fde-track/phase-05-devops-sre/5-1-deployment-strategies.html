5.1 Deployment strategies

Deploying into a customer's production environment for the first time is not the moment to discover your rollback plan doesn't actually work.

TL;DR
Three strategies dominate: rolling deployment (gradually replace old instances with new ones), blue-green (two complete environments, switch traffic all at once with instant rollback), and canary (route a small percentage of real traffic to the new version, watch closely, then ramp up). The right choice for a customer engagement depends on how much risk tolerance the customer has, how reversible a bad deploy would be, and how much infrastructure duplication the engagement can actually afford.

Why "define the rollback plan before deploying" isn't optional in customer engagements

In your own team's infrastructure, a bad deploy is embarrassing but recoverable through familiar channels. In a customer's production environment, a bad deploy with no clear rollback plan can directly damage the trust the entire engagement depends on. The specific discipline: know exactly how to revert — a previous container image tag, a database migration's down script, a feature flag — before you deploy, not as something you figure out under pressure once something's already broken.

Feature flags: decoupling deployment from release

A feature flag lets you deploy new code to production while keeping it inactive until you explicitly turn it on — separating "is the code running" from "is the feature visible to users." This is specifically valuable in customer engagements: you can deploy ahead of a scheduled demo or go-live date with the feature flagged off, then flip it on at exactly the right moment, without a risky last-minute deploy coinciding with the moment everyone's watching.

Database migrations: the deployment risk that's easy to forget

Application code can usually roll back cleanly. A database schema migration often can't — once you've dropped a column or changed a type, going back isn't just "redeploy the old version." The safe pattern for customer environments: additive migrations first (add a new column alongside the old one, backfill data, switch reads/writes over, only then remove the old column in a separate, later deploy) rather than one migration that changes and removes in the same step.

Check your understanding

1. Why does canary deployment specifically help catch a bad release before it affects everyone?
The defining feature is partial, real traffic exposure — enough to get a genuine signal, small enough that a problem affects only a limited slice of users before you catch it.
2. Why is having a clear rollback plan defined before deploying especially important in a customer engagement specifically?
The stakes are different in an embedded customer engagement — trust, not just uptime, is on the line, which is exactly why this discipline gets called out as non-optional here.
3. Why should a database migration that drops a column be split into separate additive and cleanup steps rather than done in one deploy?
This is a specifically named asymmetry — application rollback is often straightforward, while destructive schema changes create a genuinely harder-to-reverse situation, which is why additive-first migration patterns exist.

This topic reflects established deployment-strategy practice (rolling, blue-green, canary) consistent across cloud providers and orchestration tools — durable concepts rather than fast-changing tooling specifics.
