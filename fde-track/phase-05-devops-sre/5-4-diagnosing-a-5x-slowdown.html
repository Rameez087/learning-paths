5.4 Diagnosing a 5x slowdown

The scenario: "Your customer's AI application suddenly becomes 5x slower. Diagnose it." No other information. Where do you actually start?

TL;DR
This scenario deliberately has no single right first move — the discipline is the process, not a memorized answer. Apply 2.4's method: check what changed recently before assuming anything, separate containment from root cause, and use the observability pillars from 5.2 (metrics first for the big picture, traces to localize, logs to confirm) rather than guessing. Below is one realistic path through the investigation — work through it, and notice how each finding narrows the next step rather than requiring you to know the answer upfront.

Try it: run the investigation

Why this scenario resists a memorized playbook

A 5x slowdown could be a database query that lost its index, a downstream dependency (an LLM API, a third-party service) suddenly running slower, a connection pool exhausted under higher load (3.3), a bad deploy that shipped a performance regression, or infrastructure-level resource exhaustion. The actual skill being tested isn't "know the answer to this specific puzzle" — it's demonstrating a systematic narrowing process under uncertainty, using the tools from this phase in the right order.

The narration habit, applied to this exact scenario

Recall 2.4's point about narrating your hypothesis out loud. In a live version of this scenario with a customer watching, saying "metrics show the slowdown is isolated to the checkout service, not global — checking its trace data now" does real work: it shows visible progress even before you've found the actual cause, and it invites correction if someone in the room already knows something you don't yet.

What "done" looks like for this kind of incident

Beyond finding and fixing the immediate cause: confirm the fix actually resolved it by watching the relevant SLI return to normal (5.3) — not just assuming a deploy worked — and write the postmortem while the investigation is still fresh, including the specific detection gap if the customer found it before your monitoring did (a common, humbling, and genuinely useful finding to document honestly).

Check your understanding

1. Why does this "5x slower" scenario deliberately resist a single memorized playbook answer?
This is the point of using this exact scenario as a teaching tool — it forces demonstrating a process (check recent changes, use observability layers in order) rather than pattern-matching to a memorized fix.
2. In what order does this material suggest using the three observability pillars (5.2) during this kind of investigation?
This ordering moves from broad signal (is something actually wrong, and where roughly) to increasingly specific detail (exactly where, exactly why) — matching each pillar's strength to the stage of investigation it fits.
3. Why should you confirm a fix worked by watching the relevant SLI return to normal, rather than just assuming a deploy resolved the issue?
This mirrors the "green DAG run" caution from data engineering — a completed action (deploy) isn't the same claim as a verified outcome (the actual problem being resolved), which is why checking the real signal matters.
