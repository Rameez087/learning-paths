5.2 Monitoring, logging & tracing

"A system is observable if its internal state can be inferred from its outputs." You will not always be there to look inside it directly.

TL;DR
Observability rests on three pillars: metrics (numeric measurements over time — request rate, latency, error rate), logs (discrete, timestamped records of specific events), and traces (the path a single request takes across multiple services). OpenTelemetry (OTel) has become the vendor-neutral standard for instrumenting all three — one SDK, one wire protocol, meaning you can switch observability backends later without touching application code, which matters directly when a customer already has a preferred vendor you need to integrate with.

Why OTel's vendor neutrality matters specifically for FDE work

Instrumentation is the expensive, sticky part of observability — once your code is wired to call a specific vendor's SDK directly, switching later means re-touching every instrumented location. OpenTelemetry standardizes the instrumentation layer itself, turning vendor selection into a reversible decision made independently of application code. For an FDE walking into a customer who already runs Datadog, or New Relic, or a self-hosted Grafana stack, OTel-based instrumentation means your code doesn't need to know or care which backend the customer prefers.

Traces: the pillar that answers "which service actually caused this?"

In a system made of multiple services calling each other, a single slow user request might pass through five different services before returning a response. Metrics can tell you overall latency went up. Logs can tell you individual events. Only a trace — the connected record of that one specific request's full path — can show you exactly which one of those five services added the delay, which is precisely the question Phase 5.4's slowdown diagnosis needs answered.

Structured logging: a small habit with a big debugging payoff

A log line that reads plain text ("order failed") is far harder to search and correlate than a structured log line (JSON with fields like order_id, customer_id, error_code). Structured logs let you query "show me every log line for this specific order_id across every service" instantly — exactly the query you need most during a live incident, and exactly the one unstructured text logs make painfully slow.

Check your understanding

1. What question can a distributed trace answer that metrics and logs alone typically cannot?
Traces are specifically built to follow one request's full journey across service boundaries — metrics show aggregate trends, logs show individual events, but only traces connect the dots for a single request's path.
2. Why does OpenTelemetry's vendor neutrality matter specifically for an FDE moving between different customer engagements?
Since different customers run different observability stacks, standardized instrumentation avoids having to rewrite telemetry code for every new engagement's specific vendor preference.
3. Why does structured (JSON-field) logging make incident response faster than plain-text logging?
The searchability difference is the practical payoff — during a live incident, being able to instantly filter to one specific entity's full activity trail across services is exactly the query structured logging makes fast.
