3.2 Structured output & schemas

From "please return JSON" to output that's physically incapable of being wrong.

TL;DR
There are three tiers of getting structured data out of an LLM, and they differ enormously in reliability: prompted JSON (just ask nicely, ~80–95% reliable), function/tool calling (schema as a strong hint, ~95–99% reliable), and native structured output with constrained decoding (the schema is enforced at the token-sampling level, making invalid output physically unreachable — effectively 100% schema-valid). By 2026, constrained decoding is standard across every major provider, and production systems should default to it.

Why constrained decoding is categorically different

Tiers 1 and 2 both work by asking the model nicely and hoping — the schema is a strong suggestion, but the model is still free to generate whatever token comes next. Constrained decoding changes what's possible at the mechanism level: the inference engine converts your schema into a finite state machine and uses it to mask out every token that would violate the schema, at generation time. The model isn't being asked to comply — it's structurally unable to emit an invalid token, because the invalid options simply aren't in the sampling pool for that position.

What structured output does NOT solve

This is worth being precise about, because it's an easy trap: constrained decoding guarantees the shape is right — correct types, required fields present, enum values valid. It does not guarantee the content is right. A response can be perfectly schema-valid and still contain a hallucinated fact, or violate a business rule the schema can't express (e.g. "end_date must be after start_date"). Those require a separate validation layer on top — commonly libraries like Pydantic or Zod — and ideally, evaluation (Phase 9). Never treat "it parsed" as "it's correct."

Check your understanding

1. What makes Tier 3 (constrained decoding) different from Tier 1 and Tier 2?
Tiers 1 and 2 rely on the model choosing to comply; Tier 3 changes the actual token sampling process so invalid output can't be generated in the first place, regardless of whether the model "wants" to violate the schema.
2. If a response is 100% schema-valid, what does that guarantee?
Schema validity is purely structural. A response can be perfectly valid JSON matching every type and field requirement while still containing a factually wrong or business-rule-violating value — those need separate validation.
3. Why might you still add Pydantic/Zod validation on top of a provider's native structured output?
JSON Schema handles types and structure; rules that span multiple fields (like a date ordering constraint) require an additional validation layer, which is standard defensive practice even with guaranteed schema compliance.
