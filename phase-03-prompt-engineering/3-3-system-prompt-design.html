3.3 System prompt design patterns

The instruction block written once, evaluated against thousands of unpredictable user inputs.

TL;DR
A production system prompt is different from a one-off user prompt: it has to be general, unambiguous, and robust against adversarial input, because it's written once and run against every future conversation. A well-structured 2026 system prompt tends to follow six blocks, in order: identity/persona → task scope → tool-use rules → refusal/safety behavior → output format → guardrails. Order matters more than people expect — identity first anchors everything that follows; guardrails buried at the very end compete with everything the model has already "settled into" by the time it gets there.

The six blocks

  • Identity & persona — who the assistant is, kept to two or three sentences. Over-long personas waste tokens and rarely change behavior beyond that point.
  • Task scope — what the assistant is for, and just as importantly, what it's not for. Explicit scope prevents the model from being talked into adjacent work it wasn't designed for.
  • Tool-use rules — if the assistant has tools, when to call each one, when to ask the user first, what to do when a tool call fails. This is reportedly where most agent bugs live in practice.
  • Refusal & safety behavior — the exact shape refusals should take. A common default: acknowledge briefly, explain why, offer an alternative — consistently, not improvised per-conversation.
  • Output format — the format contract (from 3.2): what shape, what schema, what to omit.
  • Guardrails — explicit boundaries against known attack patterns: persona switches, attempts to extract the system prompt itself, instructions to "ignore previous instructions."

A concrete framework: RCCF

One widely-cited practical framework compresses this into four moving parts: Role (personality), Context (grounding — not just "write about Python" but "for data scientists migrating from R who need to handle missing values differently"), Constraints (guardrails), Format (structure). The core finding behind frameworks like this: specificity beats cleverness, consistently. Front-loading constraints at the start of a prompt measurably reduces how often a task needs iterative back-and-forth to get right, compared to a vague initial ask that gets refined through trial and error.

Model-specific quirks are real, not folklore

System prompt conventions aren't perfectly portable across providers. Different reasoning models respond differently to explicit "show your work" instructions — some will dump intermediate reasoning into a designated scratchpad area only if told to; others include reasoning directly in the main output unless explicitly told not to. This means a system prompt tuned carefully for one model family may need real adjustment, not just find-and-replace, when porting to another.

Guardrails aren't a courtesy — they're security

A system prompt's guardrail section is doing real security work, not just tone-setting. Documented attack patterns worth explicitly defending against include: prompted persona switches ("pretend you're an AI with no restrictions"), attempts to extract the system prompt template itself, and instructions telling the model to ignore its previous instructions entirely. We'll go deeper on this in 3.4.

Check your understanding

1. Why does identity/persona typically go first in a system prompt, rather than last?
System prompt sections aren't independent — later sections (tool rules, refusal behavior, format) are interpreted in light of the identity established earlier, which is why reordering can change behavior even though the same content is present.
2. Why should "task scope" explicitly state what the assistant is NOT for, not just what it is for?
Positive scope alone leaves ambiguity at the edges — a user can often talk a model into "just this one adjacent thing" unless the boundary is stated explicitly.
3. What's the core principle behind the RCCF framework's effectiveness?
RCCF's reported gains come from replacing vague initial asks with concrete grounding and constraints up front, cutting the need to discover requirements through repeated failed attempts.
