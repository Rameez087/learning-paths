7.4 Caching strategies

Two different questions that sound identical to a human can be made to look identical to a cache too.

TL;DR
Beyond prompt-prefix caching (4.4), semantic caching catches a different kind of repetition: two textually different queries that mean the same thing ("what's your return policy" vs. "how do I return an item"). It embeds the incoming query, compares it against previously cached query embeddings, and returns the cached response if similarity clears a threshold — skipping the LLM call entirely. Real published production hit rates run 20–45%, not the 90%+ figures sometimes quoted in marketing material — and even a modest 20% hit rate on a large bill saves real money while cutting cache-hit latency to under 5ms versus multiple seconds for a fresh generation.

Two-layer caching: exact first, semantic second

Production guidance from 2026 converges on a specific order of operations: check an exact-match cache first (hash the full prompt including model, temperature, and other parameters — fast, zero risk of a wrong match), and only fall back to semantic matching if the exact check misses. Semantic caching adds real complexity — an embedding model, a vector store, a similarity threshold to tune — so most teams are advised to start with exact caching and add semantic caching only if the marginal improvement over exact-match alone actually justifies that complexity.

What determines whether the threshold is set right

Typical similarity thresholds sit around 0.85 to 0.95 cosine similarity. Set it too low, and genuinely different questions get served the same cached (wrong) answer — a fast, confidently wrong response is worse than a slow correct one. Set it too high, and the cache barely fires at all, adding embedding and lookup overhead for negligible savings. This threshold isn't a universal constant; production guidance recommends per-template tuning, because different query types have very different natural levels of phrasing variation.

Where semantic caching helps least

Creative writing, open-ended brainstorming, and other tasks where the user genuinely wants a fresh, varied response every time tend to show hit rates under 10% — too low to justify the added architecture. Semantic caching earns its complexity specifically on repetitive, high-volume, fact-based query patterns (customer support FAQs are the canonical example), not on tasks where variety is the point.

Check your understanding

1. What can semantic caching catch that prompt-prefix caching (4.4) cannot?
Prefix caching matches on exact repeated text; semantic caching matches on meaning via embedding similarity, catching paraphrased repeats that prefix caching would treat as entirely unrelated requests.
2. Why do production guides recommend checking an exact-match cache before falling back to semantic matching?
The two-layer approach captures the cheap, risk-free wins first (identical repeated prompts) before reaching for the more complex, threshold-tuned semantic layer.
3. What real risk comes from setting the similarity threshold too low?
A cache hit returns instantly and confidently — if the similarity threshold is too permissive, that speed and confidence get attached to an answer that doesn't actually match what was asked, which is a worse failure mode than a slow correct answer.
