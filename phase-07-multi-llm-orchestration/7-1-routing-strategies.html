7.1 Routing strategies

Access to frontier models is now a commodity. The advantage is in how intelligently you route across them.

TL;DR
A router sits between your application and multiple models, deciding which model handles each incoming request based on task complexity, cost budget, latency requirements, or data sensitivity. This is distinct from orchestration (coordinating multiple steps or tools across a longer workflow, Phase 8) — routing is specifically about picking the right model for a single request. A well-designed router sending roughly 80% of easy, routine requests to cheap, fast models while reserving expensive frontier compute for the genuinely hard 20% commonly outperforms a single-model architecture on cost, latency, and throughput simultaneously — often without sacrificing quality on the easy majority of requests.

What a router actually weighs

  • Task complexity — classification, extraction, and simple formatting rarely need a frontier model; multi-step reasoning, nuanced writing, and high-stakes analysis often do.
  • Cost budget — a cheap model handling 80% of volume changes the total bill dramatically, even if the remaining 20% still uses an expensive model.
  • Latency requirements — a real-time chat interface has a much tighter latency budget than a nightly batch job.
  • Data sensitivity — some organizations route sensitive data only to models or providers meeting specific compliance or hosting requirements.

Beyond a single routing decision: cascades and ensembles

Two more sophisticated patterns build on basic routing:

  • Cascade chains — a request flows through a sequence of increasingly capable (and expensive) models, stopping as soon as a quality threshold is met. Cheap models handle easy cases outright; escalation to a stronger model only happens when the cheap model's output fails a check.
  • Parallel debate / ensemble routing — for high-stakes decisions, multiple models generate independent responses simultaneously, and a judge model synthesizes them. This can meaningfully reduce hallucination rates on factual tasks, at the cost of running several models per request instead of one.

A practical warning: keep the router simple

Practitioner reporting from 2026 production systems converges on a specific caution: the most common mistake is making the routing logic itself too complex — reaching for a fancy AI-based router when simple rules (task type, a lightweight classifier, or explicit keyword matching) handle the large majority of cases reliably. Most teams report a basic routing setup taking less than a day to implement.

Check your understanding

1. What's the distinction between routing and orchestration?
Routing is the narrower, single-decision concept; orchestration (Phase 8's territory) is the broader coordination of an entire multi-step workflow, which may itself involve several routing decisions along the way.
2. In a cascade chain, when does a request escalate to a more expensive model?
The whole value of a cascade is that expensive compute is reserved for cases that actually need it — escalation is conditional on the cheap model's result failing a check, not automatic or random.
3. What's the most commonly reported mistake in building a routing system?
2026 practitioner reporting specifically flags over-engineering the router itself — most task classification can be handled with simple rules or a lightweight classifier rather than an elaborate AI-based routing decision.
