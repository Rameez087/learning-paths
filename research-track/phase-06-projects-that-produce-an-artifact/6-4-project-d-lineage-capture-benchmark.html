6.4 Project D: a lineage capture benchmark

A benchmark of how well open lineage integrations capture column level lineage for data transformations. A pure data engineering question with little prior benchmarking.

TL;DR
Build public or synthetic PySpark pipelines with known ground truth lineage, run lineage tools on them and measure what they capture or miss. The result is an open benchmark and an analysis of failure modes. Check novelty carefully first. Plan 8 to 12 weeks.

Design

Project at a glance

For common PySpark transformation patterns (joins, aggregations, window functions, UDFs, dynamic column names), how complete and correct is the column level lineage captured by OpenLineage style integrations?

Write a suite of small pipelines in which the true column dependencies are known by construction. Run each with the lineage integration enabled. Compare captured lineage with ground truth.

Precision and recall of lineage edges, per transformation pattern. Overhead in runtime and storage. Failure cases catalogued.

The pipeline suite, the ground truth files, a scoring script and a results table. Public repo.

Protect your employer
Do not use work pipelines, schemas or data. Write synthetic pipelines. The research question stands without them, and nothing confidential can leak.

Milestones

Check your understanding

1. Why use synthetic pipelines with known ground truth?
Ground truth by construction enables precision and recall, and nothing private is exposed.
2. Which transformation is likely hardest for static lineage capture?
Opaque code and runtime decided dependencies hide the true lineage.
3. What should you do before committing weeks to this project?
Novelty must be checked, as for any project.

Sources: OpenLineage; Hidden Technical Debt in Machine Learning Systems (Sculley et al.)
