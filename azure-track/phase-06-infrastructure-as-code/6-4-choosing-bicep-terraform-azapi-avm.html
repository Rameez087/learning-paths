6.4 Choosing: Bicep, Terraform, AzAPI and Verified Modules

None of them is the right answer everywhere. Here is how to decide, and how to stay productive whichever you pick.

TL;DR
Pick Bicep for Azure only estates that want first day feature support and no state file. Pick Terraform for multi cloud estates, an existing team skill base, or a rich module ecosystem. Use AzAPI inside Terraform for features azurerm lacks. Azure Verified Modules (AVM) give Microsoft supported, well tested modules for both Bicep and Terraform, so you do not write everything from scratch.

A practical decision path

Decide

1. Do you manage other clouds or SaaS with IaC?

Yes: favour Terraform so you have one workflow. No: continue.

2. Does your team already know one of them well?

Existing skill and existing code usually outweigh theoretical advantages.

3. Do you need new preview Azure features immediately?

Bicep supports them first. With Terraform, add AzAPI.

4. Who will operate state?

If nobody wants to own state storage, locking and access, Bicep removes that burden.

Mixing is allowed but costly
Some teams use Bicep for the Azure landing zone and Terraform for Databricks or SaaS resources. That works, but two toolchains mean two sets of pipelines and skills. Mix only with a reason.

Whichever you choose, start from Azure Verified Modules where they exist, pin versions, and read each module's inputs and defaults. Check the AVM index for current coverage and maturity before depending on a module.

Make the call

A startup deploying only to Azure, two engineers, no existing IaC.
Simple, stateless and well supported for Azure only.
A company managing Azure, GitHub and Databricks workspaces from one repo.
Terraform providers cover all three.

Check your understanding

1. Which tool has no state file?
Bicep relies on Azure as the source of truth.
2. What is AVM?
Microsoft maintained building blocks.
3. When does Terraform win?
Fit to team and estate matters most.
