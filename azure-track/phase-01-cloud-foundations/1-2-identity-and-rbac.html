1.2 Identity and RBAC

Every action in Azure is a request from an identity to a scope. Understand who can do what, and where, before you build anything.

TL;DR
Microsoft Entra ID is the identity service: users, groups, service principals and managed identities. Azure RBAC controls what an identity can do on Azure resources through role assignments: a security principal, a role definition and a scope. Assign roles to groups, at the narrowest scope that works, and prefer least privilege.

Three parts of a role assignment

PartMeaningExample
Security principalWho gets accessA user, group, service principal or managed identity
Role definitionWhat actions are allowedReader, Contributor, Owner, or a custom role
ScopeWhere it appliesManagement group, subscription, resource group or single resource
Assignments at a higher scope are inherited by everything below.

Common built-in roles

RoleCan doUse for
ReaderView resourcesAuditors, read only access
ContributorCreate and manage resources, but not grant accessEngineers deploying infrastructure
OwnerEverything including granting accessFew, trusted administrators
User Access AdministratorManage access onlyDelegated access management
Storage Blob Data Reader and similar data rolesRead data inside a serviceData plane access, separate from management access
Control plane and data plane
Azure RBAC separates managing a resource (control plane: create a storage account) from using its data (data plane: read a blob). Being Contributor on a storage account does not by itself let you read its blobs. Data roles grant that. This catches many beginners out.
Entra roles are different
Microsoft Entra roles (such as Global Administrator) manage the directory itself, not Azure resources. Azure RBAC roles manage Azure resources. They are separate systems, though an Entra administrator can elevate access to Azure in specific cases.

Pick the role and scope

A data analyst needs to read blobs in one storage account and nothing else.
A data plane role at the narrowest scope gives exactly the needed access.
A deployment team needs to create resources in a project's resource group but must not manage who has access.
Contributor can create and manage resources but cannot assign roles.
Ten engineers need the same access, and people join and leave often.
Group based assignment scales and keeps access reviewable.
# grant a group read access on one resource group with the Azure CLI
az role assignment create \
  --assignee-object-id <group-object-id> \
  --assignee-principal-type Group \
  --role "Reader" \
  --scope /subscriptions/<sub-id>/resourceGroups/rg-demo
