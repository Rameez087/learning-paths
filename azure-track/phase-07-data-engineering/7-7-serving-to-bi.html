7.7 Serving to BI: Import, DirectQuery and Direct Lake

The last mile decides whether anyone uses your data. Power BI offers modes with different trade offs.

TL;DR
Power BI semantic models can Import data into memory (fast, scheduled refresh), use DirectQuery (query the source live, always fresh, slower and load on the source), or use Direct Lake on Fabric (reads Delta files from OneLake directly with import like speed and no copy). A semantic model should define measures once so all reports agree.
ModeSpeedFreshnessWatch out for
ImportFastest, in memoryAs fresh as the last refreshSize limits and refresh time
DirectQueryDepends on the sourceLiveSource load, slower visuals, fewer features
Direct LakeNear importReads current Delta dataNeeds Fabric, check fallback to DirectQuery behaviour
  • Model a star schema (7.4) for the semantic layer. It is faster and clearer.
  • Put business logic into measures in the semantic model, not in each report.
  • Use row level security for per user data access.
  • Aggregate large facts to the grain dashboards need.
Check current capabilities
Direct Lake and DirectQuery features change often. Review the current docs on limitations and fallback before deciding.

Pick a mode

A 2 GB dataset, refreshed nightly, many report users.
Import is fastest for moderate data with scheduled freshness.
Gold tables already live as Delta in a Fabric lakehouse and you want fast reports without copying.
Direct Lake reads Delta files in OneLake.

Check your understanding

1. Which mode queries the source live?
Every visual sends queries.
2. Where should business measures be defined?
One definition keeps numbers consistent.
3. What does Direct Lake read?
It avoids copying data into the model.
