Phase 2 · Compute and apps

2.2 App Service

A managed place to run web apps and APIs without managing servers. The first platform service most teams reach for.

TL;DR
App Service runs web apps, APIs and mobile backends on a managed platform. Pick a plan (the compute and price tier), deploy code or a container, use deployment slots for safe releases, and configure app settings, managed identity and scaling. You manage the app, Azure manages the servers.

Concepts

ConceptWhat it is
App Service planThe compute (size, instances, region) that one or more apps share, and what you pay for
Web appYour application running on the plan, as code or a container
Deployment slotA live staging copy of an app that you can swap into production (available on Standard and higher plans)
App settingsConfiguration exposed as environment variables; reference Key Vault for secrets
ScalingScale up (bigger instance) or scale out (more instances), manually or by rule
Managed identityAn identity for the app so it can reach Azure resources without stored secrets

A safe release with slots

1. Deploy to staging

Push the new version to the staging slot. Users still see production.

2. Warm and test

The slot has its own URL. Run smoke tests. Slot specific settings stay with the slot.

3. Swap

Swap staging and production. The swap warms instances first, so there is little or no downtime.

4. Roll back if needed

If something is wrong, swap back. The previous version is now in the staging slot.

# create a plan and web app, then turn on a system assigned managed identity
az appservice plan create -g rg-demo -n plan-demo --sku B1 --is-linux
az webapp create -g rg-demo -p plan-demo -n app-demo-<unique> --runtime "PYTHON:3.12"
az webapp identity assign -g rg-demo -n app-demo-<unique>
When not to use it
If you need to run many small containers with independent scaling or event driven scale to zero, Container Apps may fit better (2.4). For short event triggered code, consider Functions (2.3).

Right feature?

You want to test a release with production settings before users see it.
Slots let you stage, test and swap with minimal downtime.
The app needs a database password and you do not want it in code.
Managed identity and Key Vault keep secrets out of code and config files.

Check your understanding

1. What do you pay for in App Service?
The plan defines the compute, and apps on it share it.
2. What is the benefit of deployment slots?
Slots enable staged, reversible releases.
3. How should an app reach a database without a stored password?
Managed identities remove stored secrets.
