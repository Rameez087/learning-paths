8.3 Agents on Azure

An agent is a model that can call tools in a loop. The hard parts are control, safety and cost, not the loop itself.

TL;DR
An agent combines a model, instructions, tools (functions, search, code execution, APIs) and memory or state, and repeats: decide, act, observe. On Azure you can use the Foundry Agent Service as a managed runtime, or frameworks such as Semantic Kernel, the Microsoft Agent Framework or others, hosted on Container Apps or Functions. Start with the least autonomy that works.
Every extra loop costs tokens and time, and adds a chance to go wrong.
OptionUse when
Plain workflow with model stepsThe steps are known in advance. Prefer this, it is cheaper and testable
Foundry Agent ServiceYou want a managed runtime with built in tools, threads and tracing
Framework on Container AppsYou need custom orchestration, multi agent patterns or portability

Guardrails

  • Give tools least privilege: a read only database role, not the admin one.
  • Require human approval for irreversible actions such as sending email or deleting data.
  • Limit steps and tokens per run, and log every tool call.
  • Treat tool outputs and retrieved text as untrusted: they can contain injected instructions.
  • Evaluate with scenario tests, not only a few demos (8.6).
Check the current product names
Agent products and frameworks in the Microsoft ecosystem have been renamed and merged recently. Confirm the current names and support status in the docs.
