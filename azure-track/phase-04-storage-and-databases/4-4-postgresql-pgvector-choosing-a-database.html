4.4 PostgreSQL, pgvector and choosing a database

Azure Database for PostgreSQL is a managed Postgres. With pgvector it doubles as a vector store, which matters for RAG.

TL;DR
Azure Database for PostgreSQL flexible server runs community PostgreSQL with managed backups, high availability and patching. Many extensions are supported, including pgvector for embeddings and similarity search. It is a strong default when you want open source compatibility. Choosing a database is mostly about access pattern, scale and team skills.

-- pgvector basics
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE docs (id bigserial PRIMARY KEY, body text, embedding vector(1536));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT id, body FROM docs ORDER BY embedding <=> $1 LIMIT 5;
Extensions need enabling
On Azure, extensions must be allow listed on the server before CREATE EXTENSION works. Check the current supported list and versions in the docs.

A single Postgres holding both your relational data and your embeddings keeps joins, transactions and filters simple. A dedicated search service adds richer ranking features and scales retrieval separately. Section 8.2 compares them.

Pick

A small team builds a RAG app and wants relational metadata and vectors in one place.
One database for both keeps the design simple at modest scale.
Hot, simple key value lookups with global users and unpredictable volume.
Partitioned NoSQL suits key based access at scale.
