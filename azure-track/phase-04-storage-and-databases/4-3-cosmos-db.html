4.3 Cosmos DB

Cosmos DB is a globally distributed NoSQL database. You design for the partition key, or you pay for it.

TL;DR
Azure Cosmos DB stores JSON style items in containers and is billed in request units (RU), a normalised cost of each operation. Data is split into logical partitions by the partition key you choose. A good key spreads data and requests evenly, and lets most queries target a single partition. You can pick from five consistency levels between strong and eventual.

Partition key thinking

PropertyGood keyBad key
CardinalityMany distinct values (user id, tenant id)A few values (country with 3 values, status)
DistributionRequests spread evenlyOne value gets most traffic (hot partition)
Query fitMost queries filter on itQueries fan out across all partitions (expensive)

Consistency levels

Session is the default and fits most apps. Stronger means higher latency and cost, weaker means more speed and availability.
RU thinking
Point reads by id and partition key are the cheapest operation. Cross partition queries cost more RUs. Model your data around your access patterns, often denormalising, rather than copying a relational design.

Capacity can be provisioned throughput, autoscale, or serverless for spiky small workloads. Cosmos DB also offers vector search for AI applications. Check current feature support per API before relying on it.

Is Cosmos DB right?

Per user profile documents read by user id at global scale, with low latency.
Point reads by key on a high cardinality partition key are ideal.
Heavy relational reporting with many joins across tables.
Relational engines handle joins and aggregation better.

Check your understanding

1. What is an RU?
Request units measure throughput consumed.
2. What makes a good partition key?
That avoids hot partitions and fan out queries.
3. Which operation is cheapest?
Direct key lookups cost the least.
