7.2 Airflow concepts

Airflow is the de facto orchestration framework for data engineering — here are the four concepts that actually matter.

TL;DR
Airflow lets you define DAGs (7.1) entirely in Python — version-controllable, testable code, not a drag-and-drop UI. Operators encapsulate a unit of work (run a bash command, call Python, trigger a dbt model). Sensors are a special kind of operator that pause and wait for a condition — a file arriving, an API returning a status — before letting the DAG proceed. The Scheduler continuously evaluates every DAG's dependencies and trigger rules against a metadata database to decide what's actually ready to run right now.

Sensors: the patient gatekeepers

A sensor pauses workflow execution until a specific condition is met — waiting for a file to appear in cloud storage, a message to arrive on a queue, or an HTTP endpoint to return a ready status — rather than blindly running a task on a fixed schedule regardless of whether the data it needs has actually shown up yet. This lets pipelines react to real-world events rather than assuming a schedule always lines up with reality.

A minimal real DAG

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

default_args = {
    "owner": "data-team",
    "retries": 2,
    "retry_delay": 300,  # seconds
}

with DAG(
    "daily_orders_pipeline",
    schedule_interval="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    default_args=default_args,
) as dag:

    extract = PythonOperator(task_id="extract_orders", python_callable=extract_fn)
    transform = PythonOperator(task_id="transform_orders", python_callable=transform_fn)
    load = PythonOperator(task_id="load_orders", python_callable=load_fn)

    extract >> transform >> load  # explicit dependency chain

Trace this back to 7.1: retries and retry_delay are exactly the reliability mechanics from 5.5, now expressed as scheduler-level configuration. catchup=False tells Airflow not to backfill every missed historical run since start_date — without it, deploying a new daily DAG with a start date a year ago would trigger 365 backfill runs immediately.

Why "Airflow is the de facto standard" comes with real caveats

Airflow's maturity and ecosystem size are real advantages, but current practitioner sources are candid about genuine friction: setting up an enterprise-grade deployment (custom DSLs, metadata monitoring, dbt integration, a usable UI) can take real time to get right, the learning curve is steep, and debugging a failing DAG is frequently cited as a specifically painful part of the experience. This is exactly why lighter-weight or more opinionated alternatives (Dagster, Prefect, or managed orchestration platforms) have real adoption — Airflow being the default doesn't mean it's frictionless.

What a green DAG run does NOT prove

A specifically important limitation: a DAG run finishing successfully proves the tasks executed without an error — it does not prove the resulting data is fresh, complete, valid, or useful. Airflow (and orchestration generally) stays in its lane: scheduling and running tasks in the right order. Actually checking whether the data is correct is a separate concern, covered fully in Phase 11's data quality and observability material.

Check your understanding

1. What does the catchup=False setting prevent?
Without this setting, a DAG with a start date a year in the past would trigger a full year of backfill runs the moment it's deployed — catchup=False disables that automatic backfilling behavior.
2. What is a sensor specifically designed to do that a regular operator doesn't?
Sensors are a specialized operator subtype built for event-driven waiting — reacting to real-world conditions rather than assuming a fixed schedule always aligns with when data is actually ready.
3. Why doesn't a successfully completed ("green") DAG run guarantee the underlying data is correct?
This is a specifically important scope boundary — Airflow's job is scheduling and execution, not data validation, which is exactly why dedicated data quality tooling (Phase 11) exists as a separate layer.
