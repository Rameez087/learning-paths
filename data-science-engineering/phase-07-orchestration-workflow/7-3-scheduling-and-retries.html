7.3 Scheduling & retries

Transient failures are the normal case, not the exception — the question is whether your pipeline handles them gracefully or pages someone at 3am.

TL;DR
Retry policies (configured per-task or per-DAG) automatically re-attempt a failed task after a delay — critical for transient failures like a brief network blip or a momentarily rate-limited API, which resolve themselves without any human intervention. An SLA (Service Level Agreement) defines an expected completion time for a task or DAG; an SLA miss triggers a callback (an alert, typically) so a team knows a pipeline is running behind before downstream consumers are affected, not after.

Why retries need a backoff, not instant re-attempts

Retrying immediately after a failure often just hits the exact same problem again — if an API is briefly rate-limited, an instant retry likely gets rate-limited too. Exponential backoff (waiting progressively longer between each retry attempt) gives a transient issue real time to resolve before trying again, and avoids compounding the problem by hammering an already-struggling system with immediate retries.

SLA misses: catching lateness before it cascades

An SLA miss callback fires when a task or DAG hasn't completed within its expected time window — this is distinct from a task failure, since a task can be technically still running (not failed) while badly missing its SLA. Catching this early matters specifically because downstream tasks and consumers (a dashboard refresh, a scheduled report) are often depending on this pipeline finishing on time — an SLA alert gives the team a chance to intervene before those consumers are affected, not just a post-mortem after they already were.

Task-level vs. DAG-level retries

Retry policies can be set per-task (a specific flaky API call gets more retries than a stable local computation) or as a DAG-wide default that individual tasks inherit unless overridden. The practical guidance: set retries based on each task's actual failure characteristics — a network call to an external API genuinely benefits from retries; a task failing due to a bug in your own code will just fail identically every time, and retrying it repeatedly only delays noticing the real problem.

Check your understanding

1. Why is exponential backoff preferred over immediate retries?
An instant retry against a briefly rate-limited or overloaded system often just repeats the failure — progressively longer waits give the underlying issue a genuine chance to clear.
2. What does an SLA miss specifically alert on, distinct from a task failure?
SLA misses catch a different failure mode — lateness — that a simple success/failure check wouldn't catch on its own, since a slow-but-still-running task isn't a "failure" in the traditional sense.
3. Why would retrying a task that fails due to a bug in your own code not actually help?
Retries are specifically valuable for transient, external failures — a deterministic bug in your own logic will keep failing identically no matter how many times it's retried, making retries the wrong tool for that failure class.
