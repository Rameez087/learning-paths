7.5 Containerizing data pipelines

Running Airflow on your laptop and running it in production are different engineering problems — containers are what bridges them.

TL;DR
Running Airflow (or any orchestrator) in containers means packaging the webserver, scheduler, workers, and their dependencies into consistent, portable images — deployable via Docker Compose for smaller setups, or Kubernetes for production-scale, auto-scaling deployments. This is the same containerization principle from the AI Engineering track's production phase, applied specifically to orchestration infrastructure: consistent environments, independent scaling of each component, and clean integration with the deployment patterns most modern infrastructure teams already use.

Docker Compose vs. Kubernetes: matching complexity to actual need

  • Docker Compose — ideal for smaller teams running Airflow's components together on a single host with minimal setup. Good for development and smaller production workloads, but doesn't provide the auto-scaling or high-availability features a large deployment needs.
  • Kubernetes (via the KubernetesExecutor) — each task runs in its own pod, scaling workers dynamically based on actual load. This is real added operational complexity, but it's the right fit once task volume or reliability requirements outgrow what a single-host setup can handle.

Git-sync: how DAG code actually gets to the running system

A specific, common pattern in containerized Airflow deployments: rather than baking DAG files directly into the container image (which would require a full image rebuild for every DAG change), a git-sync sidecar continuously pulls the latest DAG definitions from a Git repository into a shared volume the scheduler and workers can read from. This means DAG code changes deploy as fast as a git push, without needing to rebuild and redeploy the entire orchestration platform's container images.

Why this matters for reproducibility (5.5's other half)

Containerizing the orchestrator itself extends 5.5's reproducibility principle one layer down: not just "can I reproduce this pipeline's output," but "can I reproduce the exact execution environment that produced it." A pinned container image plus version-controlled DAG code means a pipeline run from six months ago can be reproduced in an environment that's genuinely identical to what actually ran then — not just similar.

Check your understanding

1. Why might a team choose the KubernetesExecutor over Docker Compose for running Airflow?
This is a scale-driven trade-off — Compose is genuinely simpler and sufficient for smaller workloads, while Kubernetes's added complexity earns its keep once volume or reliability needs grow past what a single host can handle.
2. What problem does a git-sync sidecar solve in a containerized Airflow deployment?
Baking DAGs directly into the image would tie every code change to a slow image rebuild-and-redeploy cycle — git-sync decouples DAG code updates from the container image lifecycle entirely.
3. How does containerizing the orchestrator extend the reproducibility concept from 5.5?
A pinned image plus version-controlled DAG code together mean a past run's environment can be recreated exactly, not just approximately — extending reproducibility from "the logic" to "the actual runtime."
