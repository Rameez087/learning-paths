7.1 DAGs & dependency management

Every orchestration tool you'll touch is built around one idea: some tasks can't start until others finish.

TL;DR
A DAG (Directed Acyclic Graph) is a collection of tasks with explicit dependencies and a defined execution order — directed (dependencies point one way) and acyclic (no task can depend on itself, even indirectly, which would create an infinite loop). This is the foundational structure every major orchestration tool (Airflow, Dagster, Prefect) is built around, because it makes task sequencing and failure handling predictable and repeatable rather than an ad-hoc script with implicit ordering buried in the code.

Try it: run a real DAG and watch dependencies get respected

Why "acyclic" is a hard requirement, not a style preference

If Task C depended on Task A, and Task A depended on Task C, neither could ever start — each is waiting on the other. This is a real, structural failure a DAG's definition rules out by construction: since dependencies only ever point forward, a cycle is simply impossible to express in a valid DAG. Orchestration tools validate this at DAG-definition time specifically to catch this class of error before anything ever runs.

Explicit dependencies vs. implicit ordering

Before DAG-based orchestration became standard, a common pattern was a single script or cron job that ran steps in whatever order they happened to be written — the "dependency" between step 2 and step 3 existed only in the fact that step 2's code appeared first. A DAG makes this dependency an explicit, first-class object: task B literally declares "I depend on task A," which the orchestrator can inspect, visualize, and use to parallelize independent branches automatically.

What this buys you in practice

  • Automatic parallelization — tasks with no dependency on each other can run simultaneously, without anyone manually coding that logic.
  • Precise failure isolation — when a task fails, the orchestrator knows exactly which downstream tasks were depending on it and can hold those back rather than running them against incomplete upstream data.
  • Visual debugging — a DAG's graph structure can be rendered directly as a diagram, making it far easier to reason about a complex pipeline than reading through a long procedural script.

Check your understanding

1. Why must a DAG be acyclic?
A cycle creates a deadlock by definition — every task in the cycle is blocked on another task in the same cycle, so nothing can ever satisfy its dependency and begin.
2. What's the key difference between a DAG's explicit dependencies and a script's implicit ordering?
The explicitness is what enables automatic parallelization and precise failure handling — an orchestrator can't safely parallelize or isolate failures in a script whose ordering is just "whatever line comes next."
3. Why does DAG-based orchestration enable automatic parallelization?
Because dependencies are explicit, the orchestrator can determine which tasks are truly independent and safely run them concurrently — this is a direct benefit of making the dependency graph explicit rather than implicit.
