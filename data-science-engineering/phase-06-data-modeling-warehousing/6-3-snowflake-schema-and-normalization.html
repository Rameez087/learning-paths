6.3 Snowflake schema & normalization

The same information, one extra table deeper — and one extra join every time you need it.

TL;DR
A snowflake schema takes a star schema's flat dimension tables and normalizes them further — splitting dim_product into separate dim_product, dim_category, and dim_subcategory tables linked together, rather than storing category info redundantly inside every product row. This reduces storage redundancy but adds joins to nearly every analytical query — and since star schemas already win on roughly 90% of query workloads, snowflaking is a deliberate trade you make for specific reasons, not a default upgrade.

Why storage redundancy matters less than it used to

Normalization was originally about minimizing redundant storage — genuinely important when storage was expensive. Cloud warehouse storage is now cheap enough that this original motivation carries much less weight; the primary cost that remains is query complexity and speed, which is exactly what star schemas optimize for by keeping dimensions flat even at the cost of some duplicated data (a product's category name repeated across every row that shares that category, for instance).

When snowflaking still earns its cost

  • Very large, frequently-updated dimensions — if a dimension table is enormous and its sub-attributes change independently and often, normalizing can reduce update overhead.
  • Strict data governance requirements — some compliance contexts specifically require normalized structures to avoid any redundant copies of sensitive reference data.
  • Shared reference dimensions across many fact tables — a normalized, centrally-managed category table can be a genuine win when many different stars need to reference the exact same hierarchy consistently.

The practical default for 2026

Given cheap storage and the strong query-performance case for fewer joins, current guidance treats dimensional modeling with a star schema as the default best approach for most warehouse design in 2026 — snowflaking is the exception you reach for when a specific requirement justifies it, not the other way around.

Check your understanding

1. What does a snowflake schema do differently from a star schema?
The fact table structure is unchanged — the difference is entirely in how much the surrounding dimension tables are broken down into further normalized sub-tables.
2. Why does storage redundancy matter less as a design concern in 2026 than it historically did?
The cost trade-off genuinely shifted — cheap storage means the query-speed benefit of fewer joins in a star schema now usually outweighs the storage savings a snowflake schema would provide.
3. What's a legitimate reason to choose a snowflake schema despite the general 2026 default favoring star schemas?
