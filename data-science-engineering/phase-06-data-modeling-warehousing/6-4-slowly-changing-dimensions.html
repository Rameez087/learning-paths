6.4 Slowly changing dimensions

A customer moves cities. Do you overwrite the old address, or keep both — and does the answer change your entire historical revenue-by-region report?

TL;DR
A Slowly Changing Dimension (SCD) is a dimension attribute that changes occasionally rather than constantly — a customer's address, a product's category, an employee's department. Type 1 simply overwrites the old value with the new one — simple, but it destroys history: any report re-run after the change silently reflects the new value even for old transactions. Type 2 preserves full history by inserting a new row for every change, with effective-date ranges marking which row was "current" at any point in time. Type 2 is described as the most common production pattern specifically because it preserves accurate historical reporting — at the cost of real complexity in partition management.

Why Type 1's simplicity has a real cost

With Type 1, once the customer's city is overwritten, every historical fact row referencing that customer now shows "Denver" — including transactions that genuinely happened while they lived in Austin. A "revenue by city" report re-run after the change will misattribute all of that customer's historical revenue to Denver, silently rewriting history. Type 1 is the right choice specifically when you don't care about historical accuracy for that attribute — a corrected typo in a name, for instance, where there's no value in remembering the old (wrong) spelling.

How Type 2 actually works

Instead of updating the existing row, a Type 2 change inserts a brand-new row for the customer with the new city, marks the old row's end_date as the change date, and sets the new row's start_date accordingly with an open-ended (or far-future) end_date and an is_current flag. Historical fact rows keep pointing at the surrogate key of whichever version of the customer was current when that transaction actually happened — so a "revenue by city" report correctly attributes old revenue to Austin and new revenue to Denver.

Late-arriving data adds real complexity

A specifically named complication: if a fact row arrives late — say, a transaction from three weeks ago is only now being loaded — the pipeline has to search Type 2 history to find which version of the dimension was actually effective at that transaction's real date, not just attach it to whatever's currently marked "current." Getting this wrong silently misattributes historical facts to the wrong dimension version.

Check your understanding

1. What's the fundamental trade-off between SCD Type 1 and Type 2?
Type 2 is specifically named as the most common production pattern precisely because most analytical use cases need accurate historical attribution, which Type 1's overwrite behavior can't provide.
2. Why can Type 1 silently corrupt a "revenue by city" report after a customer moves?
This is exactly the mechanism — because Type 1 has no historical row for "Austin," every fact row referencing this customer, past or future, now joins to the current "Denver" value.
3. Why does late-arriving data specifically complicate Type 2 dimension handling?
Simply attaching a late fact to whatever dimension version is "current" today would misattribute it — correct handling means looking up the dimension version that was actually current back when the event genuinely occurred.
