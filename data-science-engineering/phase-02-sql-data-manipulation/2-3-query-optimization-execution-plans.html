2.3 Query optimization & execution plans

The same query, on the same data, can take 3 seconds or 3 milliseconds — the difference is almost always an index.

TL;DR
An execution plan is a report from the database's query optimizer showing exactly how it intends to run your query — whether it'll scan an entire table or use an index, which join algorithm it picked, and the estimated cost of each step. The single most common fix for a slow query: add an index on the columns actually used to filter or join, and avoid wrapping an indexed column in a function (like YEAR(order_date)), which forces the database to evaluate that function on every row — defeating the index entirely.

Try it: same query, index on or off

SELECT * FROM orders WHERE customer_id = 1001 AND order_date >= '2026-01-01'

No index
Index on customer_id

The classic non-sargable mistake

-- Non-sargable: wraps the indexed column in a function
SELECT * FROM orders WHERE YEAR(order_date) = 2026;
-- The database must compute YEAR() for every single row before
-- it can even check the condition — the index on order_date is useless here.

-- Sargable: filters the raw column directly, index-friendly
SELECT * FROM orders
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01';

"Sargable" (Search ARGument ABLE) describes a condition the database can use an index to evaluate directly. The rewritten version above expresses exactly the same logical filter, but lets the optimizer use a range scan on the index instead of computing a function on every row in the table.

Reading an execution plan: what to actually look for

  • Full table scan vs. index scan — a full scan reads every row; an index scan jumps directly to relevant rows. A full scan on a large table is the first thing to investigate.
  • Join algorithm — commonly Hash Join (builds a hash table from one side, good for large unsorted sets) or Nested Loop (checks every row in one table against every row in another, fine for small tables, disastrous at scale).
  • Estimated vs. actual row counts — a huge gap between what the optimizer expected and what actually happened usually means outdated statistics, which can cause the optimizer to pick a bad plan.

Other common fixes, roughly in order of impact

  1. Add a missing index on filter/join columns
  2. Avoid SELECT * — only retrieve columns you actually need
  3. Update stale statistics so the optimizer's row-count estimates are accurate
  4. Avoid wildcard characters at the start of a LIKE pattern ('%text' can't use a standard index; 'text%' often can)
  5. Break an overly complex query into smaller CTEs or temp tables so the optimizer has an easier job at each step

Check your understanding

1. Why does wrapping an indexed column in a function (like YEAR(order_date)) defeat the index?
A "sargable" condition lets the database use the index's stored order directly; wrapping the column in a function forces a per-row computation, which is exactly what an index is meant to avoid.
2. What does a large gap between an execution plan's estimated and actual row counts usually indicate?
The optimizer relies on statistics about data distribution to choose a plan — stale statistics mean its estimates are wrong, which can lead it to pick a join algorithm or scan type that's actually worse for the real data.
3. Why is a Nested Loop join fine for small tables but potentially disastrous at scale?
The row-by-row comparison cost scales as roughly the product of both table sizes — fine when both are small, prohibitively expensive once either grows large.
