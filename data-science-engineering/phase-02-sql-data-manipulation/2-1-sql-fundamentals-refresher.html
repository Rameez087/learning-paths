2.1 SQL fundamentals refresher

SQL shows up in 79.4% of data engineer job postings and 30-60% of data scientist ones. It's the one skill nobody gets to skip.

TL;DR
SQL is a declarative language — you describe what data you want, not the steps to fetch it, and the database's query optimizer figures out the actual execution steps (more on this in 2.3). The clauses you write in a query and the order the database actually executes them in are different — this mismatch is the single most common source of confusion for people learning SQL, and understanding it unlocks why certain things (like using a column alias in a WHERE clause) don't work the way you'd expect.

Why this execution order actually matters

Because WHERE executes before SELECT, you can't filter on a column alias defined in your SELECT clause — the database hasn't computed it yet at the point WHERE runs. This is exactly why a query like SELECT price * qty AS total FROM orders WHERE total > 100 fails on most databases, while the same filter in a HAVING clause (which runs after aggregation) or wrapped in a CTE works fine. 

-- Fails: WHERE runs before SELECT computes the alias
SELECT price * qty AS total FROM orders WHERE total > 100;

-- Works: filter on the raw expression directly
SELECT price * qty AS total FROM orders WHERE price * qty > 100;

-- Also works: wrap it in a CTE, then filter the CTE's output
WITH order_totals AS (
    SELECT *, price * qty AS total FROM orders
)
SELECT * FROM order_totals WHERE total > 100;

Joins, refreshed

  • INNER JOIN — only rows with a match in both tables.
  • LEFT JOIN — all rows from the left table, matched data from the right where it exists, NULL where it doesn't.
  • Self-join — a table joined to itself, used for comparing rows within the same table (e.g. finding employees who earn more than their manager).
  • Anti-join — rows in one table with no match in another (commonly written as a LEFT JOIN ... WHERE right.id IS NULL), used for "find customers who never ordered" type questions.

Modern SQL features worth knowing exist

A few features that show up increasingly in 2026 SQL dialects and interviews: MERGE (an upsert — insert or update in one statement, minimizing round-trips), LATERAL JOIN (lets a subquery reference a preceding table in the same FROM clause — useful for "top N per group" queries), and MATERIALIZED VIEW (caches a complex query's result and refreshes it asynchronously, trading some staleness for much faster repeated reads).

Check your understanding

1. Why can't you filter using a column alias defined in the SELECT clause within the same query's WHERE clause?
The written order (SELECT first) and the execution order (WHERE before SELECT) are different — this mismatch is exactly why the alias isn't available yet when WHERE runs.
2. What does an anti-join typically answer?
An anti-join specifically surfaces absence — rows with no counterpart in the other table — commonly implemented as a LEFT JOIN filtered to only the unmatched rows.
3. What does a MATERIALIZED VIEW trade for faster repeated reads?
Caching a complex query's result means that result can lag behind the live underlying data until the next refresh — a deliberate trade of staleness for read speed.
