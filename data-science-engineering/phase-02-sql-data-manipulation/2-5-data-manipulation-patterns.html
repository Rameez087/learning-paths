2.5 Data manipulation patterns

"Gaps and islands," sessionization, and pivoting — the patterns that separate a SQL user from someone who can actually solve a novel problem with it.

TL;DR
These three patterns recur across real analytics work and technical interviews alike, and all three build directly on 2.2's window functions: gaps and islands (find consecutive runs in a sequence — active-user streaks, uptime periods), sessionization (group individual events into sessions based on a time-gap threshold), and pivoting (turning row values into columns, or vice versa). None of these require exotic SQL features — just window functions applied with the right trick.

Try it: find the "islands" of consecutive dates

A user's login dates. Click to group them into consecutive-day streaks ("islands"):

The gaps-and-islands trick

WITH numbered AS (
    SELECT
        login_date,
        ROW_NUMBER() OVER (ORDER BY login_date) AS rn
    FROM logins
),
grouped AS (
    SELECT
        login_date,
        login_date - (rn * INTERVAL '1 day') AS island_key
    FROM numbered
)
SELECT island_key, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end
FROM grouped
GROUP BY island_key;

The insight: for dates in a consecutive run, subtracting an ever-increasing row number (assigned in date order) from each date produces the same resulting value for every date in that run — because the row number and the date both increase by exactly 1 each day within an unbroken streak. That constant value becomes a grouping key for the whole island, with no gap-detection logic needed beyond that one subtraction.

Sessionization: grouping events by a time gap

WITH events_with_prev AS (
    SELECT
        user_id,
        event_time,
        LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time) AS prev_time
    FROM page_views
),
flagged AS (
    SELECT *,
        CASE WHEN event_time - prev_time > INTERVAL '30 minutes' OR prev_time IS NULL
             THEN 1 ELSE 0 END AS is_new_session
    FROM events_with_prev
)
SELECT *,
    SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_time) AS session_id
FROM flagged;

This uses 2.2's LAG() to compare each event to the one before it for the same user. Whenever the gap exceeds a threshold (30 minutes here), that row is flagged as starting a new session; a running SUM() of those flags becomes a unique, increasing session ID for each user.

Pivoting: rows to columns

Turning distinct row values into their own columns — e.g. transforming a long (month, category, amount) table into one row per month with a column per category — is usually done with conditional aggregation when a dedicated PIVOT keyword isn't available or convenient: 

SELECT
    month,
    SUM(CASE WHEN category = 'Electronics' THEN amount ELSE 0 END) AS electronics,
    SUM(CASE WHEN category = 'Groceries' THEN amount ELSE 0 END) AS groceries
FROM sales
GROUP BY month;

Check your understanding

1. In the gaps-and-islands technique, why does subtracting the row number from the date produce a constant value within a consecutive streak?
This is the entire trick — the two values move in lockstep during a consecutive run, so their difference is invariant only within that run, changing as soon as a gap breaks the sequence.
2. What determines when a new session starts in the sessionization pattern?
Sessionization is specifically time-gap-based, using LAG() to compare consecutive events per user and flagging a new session whenever too much time has passed since the last one.
3. What technique does the conditional-aggregation pivot example rely on?
Each output column effectively asks "sum the amount, but only count it if the category matches this one, otherwise count zero" — a straightforward CASE-inside-aggregate pattern, not a window function or recursion.
