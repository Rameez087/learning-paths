2.4 Pandas vs. Polars vs. SQL

Three tools that can all answer the same question. The right one depends on where your data already lives and how much of it there is.

TL;DR
SQL operates directly where data already lives (a database or warehouse) — no data movement needed, and the query optimizer (2.3) handles performance. Pandas is Python's original DataFrame library — flexible and ubiquitous, but single-threaded by default and can struggle past a few million rows. Polars is a newer, Rust-based DataFrame library built for multi-core parallelism and lazy evaluation from the ground up — commonly benchmarked at large multiples faster than pandas on the same hardware for comparable operations, particularly with its streaming engine enabled for datasets larger than memory.

Why Polars is fast: lazy evaluation

Pandas executes each operation immediately, one line at a time — "eager" evaluation. Polars supports lazy evaluation: you build up a chain of operations (filter, group, aggregate) without running any of them yet, and Polars' query optimizer looks at the entire chain at once before executing — similar in spirit to how a SQL database's optimizer plans a whole query rather than running each clause independently. This lets Polars skip unnecessary work (like reading columns that get filtered out later) that pandas' eager, line-by-line execution can't see coming. 

import polars as pl

# Lazy: nothing executes yet, Polars just builds a plan
result = (
    pl.scan_csv("orders.csv")
    .filter(pl.col("amount") > 100)
    .group_by("customer_id")
    .agg(pl.col("amount").sum())
)

# .collect() triggers actual execution, using the optimized plan
df = result.collect()

Migrating from pandas: the syntax is close, not identical

Polars deliberately mirrors pandas' general shape (DataFrames, method chaining, similar verbs), which shortens the learning curve — but the API isn't a drop-in replacement. Common differences: Polars expressions (pl.col("x")) are more explicit than pandas' implicit column references, and Polars doesn't have a traditional index the way pandas does. Migration is usually described as a real but manageable effort, not a rewrite from scratch.

Why "just use SQL" is often the right default

If your data already lives in a warehouse, pulling it into Python (pandas or Polars) just to filter and aggregate it means moving potentially large amounts of data across the network for no reason — the warehouse's query engine can do the same work where the data already sits, typically faster, and the result you pull back can be a small, already-aggregated table instead of the full raw dataset. This is exactly ELT's underlying logic from Phase 1: do the transformation work as close to the data as possible.
