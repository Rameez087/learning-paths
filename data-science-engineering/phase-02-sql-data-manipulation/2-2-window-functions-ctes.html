2.2 Window functions & CTEs

The tools that let you answer "how does this row compare to its neighbors" without losing a single row.

TL;DR
A window function performs a calculation across a set of related rows — but unlike GROUP BY, it doesn't collapse those rows into one output row. Each original row survives, now carrying an extra computed value (a rank, a running total, the previous row's value). A CTE (WITH clause) is a named, temporary result set that makes multi-step logic readable — and it's largely superseded plain subqueries for anything beyond the simplest case, especially recursive logic like traversing an org chart.

The signature clause: PARTITION BY and ORDER BY

SELECT
    employee,
    department,
    salary,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees;

PARTITION BY divides rows into groups (here, by department) — the window function resets for each group. ORDER BY inside the OVER() clause determines the order rows are processed in within each partition — critical for ranking, running totals, and LAG/LEAD (which need to know what "previous" and "next" mean).

A subtlety worth internalizing: execution timing

From 2.1's execution order: window functions run after WHERE, GROUP BY, and HAVING, but before ORDER BY and LIMIT. This means you cannot filter directly on a window function's result inside the same query's WHERE clause — exactly the same alias-timing problem from 2.1. The fix is identical: wrap the query in a CTE, then filter the CTE's output. 

-- Fails: can't filter on dept_rank in the same query's WHERE
SELECT employee, RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees WHERE dept_rank = 1;

-- Works: compute in a CTE, then filter the CTE's output
WITH ranked AS (
    SELECT employee, department, salary,
           RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
    FROM employees
)
SELECT * FROM ranked WHERE dept_rank = 1;

Recursive CTEs: the hardest common interview pattern

A recursive CTE references itself, letting you traverse hierarchical data — an org chart, a category tree, a bill-of-materials — without knowing the depth in advance. This is consistently flagged as one of the harder SQL patterns, showing up more in senior and staff interviews than junior ones, alongside "sessionization" (grouping user events into sessions based on time gaps) and "gaps and islands" (finding consecutive date or number sequences) — we'll build these exact patterns hands-on in 2.5.

Check your understanding

1. What's the key difference between a window function and GROUP BY?
This is the defining distinction — GROUP BY reduces the row count, a window function does not, which is exactly why you can rank or compute a running total without losing per-row detail.
2. Why can't a window function's result be filtered directly in the same query's WHERE clause?
This mirrors 2.1's alias-timing issue exactly — the fix is the same: wrap the window function in a CTE, then filter that CTE's output in an outer query.
3. What makes a recursive CTE useful for org-chart or category-tree data specifically?
The self-referencing structure is exactly what lets a recursive CTE walk arbitrarily deep hierarchies without the query needing to know the depth in advance.
