8.4 Streaming with Kafka

The messaging backbone that decouples "something happened" from "something needs to process it," at massive scale.

TL;DR
Kafka is a distributed messaging platform organized around topics (named streams of events), which are split into partitions for parallelism — Kafka's partition concept mirrors Spark's directly (8.3), and the two are frequently used together, with Spark Structured Streaming consuming directly from Kafka topics. A consumer group lets multiple consumers split the work of reading a topic's partitions, each partition read by exactly one consumer within the group at a time, enabling horizontally scaled, parallel consumption of a single stream.

Why Kafka partitions and Spark partitions are the same underlying idea

Both use partitioning specifically to enable parallel processing — Kafka partitions a topic so multiple consumers can read it simultaneously; Spark partitions a dataset so multiple executors can process it simultaneously. When Spark Structured Streaming reads from Kafka, this alignment is deliberate: Spark can map Kafka partitions to its own internal partitions, keeping the parallelism consistent end-to-end rather than introducing an unnecessary reshuffling step between the two systems.

Exactly-once semantics: genuinely achievable, with the right setup

Recall 5.4's pragmatic "at-least-once + idempotent consumers" default. Kafka's Direct Stream API specifically enables exactly-once semantics when configured correctly — tracking exactly which offsets have been read from each partition, combined with idempotent or transactional writes on the output side. Getting genuine exactly-once end-to-end still requires deliberate configuration across both the read and write sides; it's achievable, not automatic by default.

Checkpointing: surviving a restart without reprocessing everything

A streaming job needs to remember where it left off if it crashes or restarts — checkpointing stores the stream's processing state (including consumed offsets) to durable storage like HDFS or S3 periodically. Incremental checkpointing minimizes the write overhead of this process, and storing checkpoints in fast-access storage keeps the added latency small relative to the resilience benefit gained.

Micro-batching vs. continuous processing: a real latency trade-off

Structured Streaming's default mode processes data in small micro-batches, which introduces some latency overhead from batch scheduling, job initialization, and task coordination at each micro-batch boundary. A continuous processing mode (available for specific use cases) removes batch boundaries entirely for event-by-event execution, trading some of Structured Streaming's simpler semantics for meaningfully lower latency — a genuine trade-off to make deliberately, not a strictly-better upgrade.

Check your understanding

1. What does a Kafka consumer group enable?
This is the mechanism that enables horizontally scaled, parallel consumption — the group coordinates so partitions are distributed across its member consumers rather than duplicated redundantly.
2. Why does checkpointing matter for a streaming job's resilience?
Without a durable record of processing progress, a restart after a crash would have no way to know what's already been processed — checkpointing is specifically what makes safe resumption possible.
3. What's the trade-off between micro-batch and continuous processing modes?
This is a genuine, deliberate trade-off — micro-batching's simplicity comes at a real latency cost from per-batch coordination overhead, which continuous processing avoids at the cost of some structural simplicity.
