8.1 Distributed computing fundamentals

One machine, no matter how powerful, eventually can't hold your data or finish the job in time. Distributed computing is what happens next.

TL;DR
Distributed computing splits both data and computation across many machines working in parallel, rather than relying on one increasingly powerful single machine. The core idea: partition the data into chunks, send the same computation to each chunk simultaneously on a different worker, then combine the partial results. This is what makes processing terabytes or petabytes of data in a reasonable time possible — and it's the foundational concept underneath Spark (8.2), Kafka (8.4), and every genuinely "big data" tool in this phase.

Why this isn't just "buy a bigger computer"

Vertical scaling (a more powerful single machine) hits real physical and economic limits — there's a ceiling on how much RAM and CPU a single machine can practically hold, and the cost curve gets steep well before that ceiling. Horizontal scaling (more machines working together) has a much higher practical ceiling and, critically, degrades more gracefully — losing one worker out of a hundred is a minor event; losing your only machine is total failure.

The trade-off distributed systems introduce

Splitting work across machines introduces real coordination costs that a single machine never has to deal with: network communication between workers, the need to combine partial results correctly, and handling a worker failing mid-job without losing the whole computation. This is exactly why distributed frameworks like Spark exist — they handle this coordination complexity so you can write code that looks similar to single-machine code while it actually runs across a cluster.

Data locality: moving computation, not data

A key principle distributed systems exploit: moving a small piece of code to where a large chunk of data already sits is far cheaper than moving that large chunk of data across the network to a central place to be processed. This "bring compute to the data" philosophy is baked into how Spark schedules tasks — it tries to run each task's computation on the worker node that already holds the relevant data partition, minimizing network transfer.

Check your understanding

1. What is the core mechanism that makes distributed computing faster for large datasets?
Parallelism across many workers, each handling a portion of the data simultaneously, is the fundamental speedup mechanism — not any change to individual machine speed.
2. Why does horizontal scaling degrade more gracefully than vertical scaling when a failure occurs?
A distributed system with many workers can typically continue functioning (perhaps more slowly) when one node fails, while a single powerful machine represents a single point of total failure.
3. What does "moving computation to the data" (data locality) avoid?
Since code is typically much smaller than the data it processes, sending the (small) computation to the (large) data's location minimizes network transfer far more than the reverse would.
