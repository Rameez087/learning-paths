8.2 Spark architecture

The dominant engine for distributed data processing — one driver, many executors, and a query optimizer doing more work than you'd expect.

TL;DR
Spark's architecture has a driver (coordinates the whole application, builds the execution plan) and executors (worker processes that actually run tasks and report results back). Your code — usually written against the DataFrame API rather than the lower-level RDD API — gets translated into a logical plan, optimized by Spark's Catalyst optimizer, and compiled into a physical execution plan structured as a DAG (8.1's concept, now inside a single Spark job) of stages separated by shuffle boundaries.

DataFrames over RDDs: why the higher-level API won

RDDs (Resilient Distributed Datasets) are Spark's original, low-level data structure — immutable, partitioned collections with lineage tracking for fault recovery. DataFrames sit on top, adding schema awareness that lets Spark's Catalyst optimizer reason about the actual structure of your data and apply optimizations automatically. Current guidance is direct: prefer DataFrames over RDDs for better performance in nearly all cases — RDDs remain foundational under the hood but are rarely the right level to write application code against anymore.

Adaptive Query Execution: optimizing mid-flight

A significant Spark 3+ feature: Adaptive Query Execution (AQE) can adjust a query's execution plan during a run, based on actual runtime statistics rather than only the estimates made before execution started. Two concrete capabilities this enables: coalescing shuffle partitions that turned out smaller than expected (reducing overhead), and splitting skewed partitions that turned out much larger than others (balancing load across executors). This replaces a lot of manual trial-and-error tuning that earlier Spark versions required.

Structured Streaming: one API for batch and streaming

Spark's modern streaming API lets you use the same DataFrame operations for both batch and streaming data, processing streams internally as a sequence of small micro-batches — this means learning Spark once covers both processing modes, rather than needing an entirely separate mental model and API for streaming versus batch work.

Check your understanding

1. What is the driver's role in a Spark application?
The driver is the central coordinator — it plans and orchestrates, while executors (running on worker nodes) are what actually carry out the assigned tasks.
2. Why is the DataFrame API generally preferred over the lower-level RDD API?
The optimizer needs to understand the structure of the data to make good decisions — DataFrames' schema awareness is exactly what unlocks this, which is why they're recommended over the schema-less RDD API for most work.
3. What specific problem does Adaptive Query Execution's partition-splitting capability solve?
AQE's defining feature is adjusting based on real runtime statistics — skew that wasn't apparent before execution started can be detected and corrected mid-flight, which pre-execution planning alone couldn't do.
