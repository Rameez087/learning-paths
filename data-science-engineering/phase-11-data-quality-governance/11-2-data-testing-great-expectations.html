11.2 Data testing & Great Expectations

dbt tests alone catch roughly 80% of data quality issues at the transformation layer — the remaining 20% is what full observability is for.

TL;DR
dbt tests (not null, unique, referential integrity, accepted values) run directly inside your transformation pipeline (Phase 2's SQL, Phase 6's warehousing) and catch the large majority of structural data quality problems cheaply. Great Expectations (and similar tools like Soda) go further with richer, custom validation rules — "this column's values should fall within this range," "this column's null rate shouldn't exceed 2%" — run as explicit pipeline steps. Beyond individual tests, full data observability watches four specific pillars continuously: freshness, volume, schema, and distribution.

A simple dbt test, and what it actually catches

# schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: customer_id
        tests:
          - not_null
          - relationships:
              to: ref('dim_customer')
              field: customer_id
      - name: order_status
        tests:
          - accepted_values:
              values: ['pending', 'shipped', 'delivered', 'cancelled']

This one file catches four distinct real-world failure modes: duplicate order IDs, missing required fields, orphaned foreign keys pointing at customers that don't exist (a broken join in 6.2's dimensional model), and an unexpected status value that would silently break any downstream logic branching on the status field.

Great Expectations: richer rules beyond dbt's built-ins

Great Expectations lets you define an "expectation suite" — custom, often statistical rules beyond dbt's structural checks: a column's values should fall within a specific numeric range, a column's null rate shouldn't exceed a threshold, or a column's distribution shouldn't shift dramatically from a known-good baseline. These run as explicit validation steps integrated into the orchestrator (Phase 7), the same pattern used for data contract enforcement (11.1).

Where "root cause analysis" comes in

When a test fails or an observability pillar flags an anomaly, the next question is always "why, and what's actually affected downstream." This is exactly where data lineage (11.3) becomes essential — a failing test tells you something's wrong, lineage tells you the blast radius of what depends on the broken data.

Check your understanding

1. What kind of data quality problem does a dbt "relationships" test specifically catch?
The relationships test specifically validates referential integrity — that every foreign key value in one table actually corresponds to a real row in the referenced table.
2. Why might a team use Great Expectations in addition to dbt's built-in tests?
dbt's built-in tests cover structural checks (uniqueness, nullability, referential integrity) well, while Great Expectations extends into more customizable, statistical validation that dbt's simpler test types don't cover.
3. Why does data lineage matter as a follow-up to a failed data quality test?
Testing and lineage answer different questions — "is something wrong" versus "what depends on the thing that's wrong" — and both are needed to actually respond to a data quality incident effectively.
