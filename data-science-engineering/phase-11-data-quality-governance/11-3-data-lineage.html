11.3 Data lineage

"If I change this table, who will it break?" — the single most common question in any production data platform, and lineage is the only reliable way to answer it.

TL;DR
Data lineage maps the dependency graph between datasets — which raw sources feed which transformations, which transformations feed which downstream tables, dashboards, and models. This turns "what will break if I change this?" from a guess into a direct graph traversal. Lineage is built one of two ways: query log parsing (inferring dependencies by analyzing the SQL queries actually run against the warehouse — the more common approach) or manifest-based lineage (declared explicitly, as dbt does through its model references).

Try it: trace the blast radius of a change

The four practical uses lineage actually serves

  • Impact analysis — before changing a table's schema, see exactly what downstream assets depend on it, avoiding the "surprise breakage" problem from 11.1.
  • Root cause analysis — when a dashboard shows wrong numbers, trace backward through lineage to find which upstream table or transformation actually introduced the error.
  • Finding unused data — identifying tables with no downstream consumers at all, candidates for deprecation and cleanup.
  • Migration planning — understanding the full dependency graph before moving a dataset to a new platform or restructuring a pipeline.

Column-level vs. table-level lineage

Table-level lineage shows "table B depends on table A" — useful, but coarse. Column-level lineage goes further, tracking exactly which specific columns in table A feed which specific columns in table B. This finer granularity matters specifically when a change only affects one column: table-level lineage would flag every downstream consumer of the whole table as potentially at risk, while column-level lineage can correctly identify that only consumers of that one specific column actually need attention.

Lineage increasingly extends beyond human consumers

A notable 2026 development: lineage and metadata systems are increasingly framed as serving AI agents directly, not just human data engineers — giving an agent (a coding assistant, an analytics copilot) the same governed context about data dependencies that a human analyst would need before trusting or modifying a dataset. This is a natural extension of lineage's core purpose: whoever (or whatever) is about to depend on or change a dataset benefits from knowing its dependency graph first.

Check your understanding

1. What question does data lineage most directly answer?
This is lineage's defining practical use — turning impact analysis from institutional knowledge or guesswork into a direct, queryable graph traversal.
2. What's the key advantage of column-level lineage over table-level lineage?
The finer granularity avoids false-positive impact warnings — table-level lineage would over-flag consumers who only use unaffected columns, creating unnecessary alarm and investigation work.
3. How do query log parsing and manifest-based lineage differ in how they build the dependency graph?
One approach observes actual usage after the fact (query logs); the other relies on dependencies being declared upfront as part of the transformation code itself (dbt's ref() function) — different mechanisms for building the same kind of graph.
