5.5 Idempotency & reliability

The single property that separates pipelines you can safely retry from pipelines you're afraid to touch at 3am.

TL;DR
An idempotent pipeline produces the same result no matter how many times you run it on the same input — meaning a failed run can always be safely retried, and a backfill never creates duplicates. Pipelines break most often for two specifically named reasons: unhandled schema changes at the source, and missing idempotency, where re-running a failed pipeline silently creates duplicate records. Building idempotency in from the start is consistently named among the highest-impact practices for production reliability.

The core techniques

  • Stable keys and upserts instead of blind inserts — an upsert (update if exists, insert if not) means re-running the same batch never creates a second copy of a record that already succeeded.
  • Delete-write pattern for partitions — delete the relevant partition or date range before rewriting it, ensuring only the latest, correct version of that slice persists, regardless of how many times the job runs.
  • Watermarking — tracking the highest timestamp or offset successfully processed so far, so a retry knows exactly where to resume rather than reprocessing everything or guessing.
  • State stores for streaming — in streaming pipelines specifically, maintaining a state store or using upsert strategies prevents replayed or late-arriving events from creating duplicate records for the same underlying event.

Idempotency and reproducibility work together

A closely related property: given the exact same versioned code, configuration, and input data, a reproducible pipeline can rebuild its outputs for any specific past point in time. Idempotency handles safe re-runs; reproducibility handles safe historical reconstruction. Together, these two properties are what make audits, debugging, and experimentation dramatically less risky — you can confidently ask "what would this pipeline have produced last Tuesday" and get a trustworthy answer.

A real complication: backfills can overwhelm the source

Even a perfectly idempotent pipeline can run into trouble during a large backfill: if the source is an operational database not built for large analytical scans, pulling the full historical dataset can crash or severely degrade it. Practical mitigations include processing the backfill in smaller, throttled date-range chunks with deliberate pauses between them — or, better, using CDC (5.4) from the start so a full historical re-extraction is rarely needed at all.

Check your understanding

1. What does it mean for a pipeline to be idempotent?
Idempotency is specifically about safe repetition — the defining property is that re-running doesn't change the outcome or create duplicates, which is exactly what makes retries safe.
2. Why does an upsert prevent the duplicate-record problem that a blind insert creates on retry?
The key/matching logic in an upsert is what makes a retry safe — it checks for an existing match before deciding whether to update or insert, unlike a blind insert that always adds a new row.
3. Why might using CDC from the start reduce the risk large backfills pose to a source system?
The backfill risk specifically arises from needing to pull an entire historical dataset at once — if CDC has been keeping the data continuously synced, that large one-time pull is far less often necessary.
