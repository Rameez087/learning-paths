1.4 Your first data pipeline

Everything from 1.1–1.3, made real in about twenty lines of Python.

TL;DR
A minimal but genuine ELT pipeline: extract raw data from a source (a CSV here — an API or database in a real system), load it untransformed into a queryable store, then transform it with SQL once it's already loaded — the ELT order from 1.2, not ETL. This example uses DuckDB, a fast, zero-setup embedded database that's become a popular choice specifically for local development and small-to-medium analytical workloads, precisely because it needs no server to run.

Why this small example already demonstrates the real pattern

  

    Production pipelines add scale, scheduling, and failure handling on top of this — but the
    fundamental shape doesn't change. Extract stays "get raw data from somewhere." Load stays "put
    it somewhere queryable, untransformed." Transform stays "write SQL (or dbt models, in a real
    stack) that turns raw rows into clean, business-meaningful tables." A production version of
    this exact pipeline would swap the CSV for an API or a source database (Phase 5), DuckDB for
    Snowflake or BigQuery (Phase 6), and add Airflow or Dagster to run it on a schedule with
    retries (Phase 7) — but you'd recognize every stage.
  


  
What "raw" data staying raw actually buys you

  

    Notice the transform step doesn't modify the original raw_orders table — it
    creates a new clean_orders view or table derived from it. If a bug is later found
    in the transformation logic (say, the discount calculation was wrong), you can just re-run a
    fixed transform against the still-intact raw data — no need to re-extract from the original
    source. This is the concrete, practical payoff of ELT's "keep raw data around" principle from
    1.2, not just an abstract preference.

1. In the ELT pipeline above, what does the "load" step do to the data?

      

        
        
        
      

      
This is the defining feature of ELT — load happens before transform, so the raw data lands intact and untouched, ready to be transformed (possibly more than once, in different ways) afterward.

    

    

      
2. Why does keeping the raw table intact after transformation matter practically?

      

        
        
        
      

      
This is the concrete payoff of ELT's core principle — the raw table becomes a safety net and a flexible source for any future transformation, not just the current one.

    

    

      
3. What would change if this example were scaled into a production pipeline?

      

        
        
        
      

      
The underlying pattern is genuinely the same at any scale — what changes is the specific tools filling each role (API instead of CSV, warehouse instead of DuckDB, orchestrator instead of manual execution).
