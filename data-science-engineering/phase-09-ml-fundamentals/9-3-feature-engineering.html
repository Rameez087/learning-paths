9.3 Feature engineering

A better feature often beats a fancier algorithm — this is where SQL (Phase 2) and ML meet.

TL;DR
Feature engineering is the process of transforming raw data into the inputs a model can actually learn from effectively — encoding categorical variables numerically, scaling numeric ranges, creating new derived features from domain knowledge (day-of-week from a timestamp, ratio features from two existing columns), and handling missing values thoughtfully rather than blindly. Feature selection — removing irrelevant or redundant features — is a closely related practice that simplifies the model and reduces variance (9.4), directly improving how well it generalizes to new data.

Why raw categorical text can't go directly into most models

A column like city containing "Austin", "Denver", "Chicago" has no inherent numeric meaning — most ML algorithms need numeric input. One-hot encoding creates a separate binary column per category (is_austin, is_denver, is_chicago). Label encoding assigns each category an arbitrary integer instead — simpler, but risks implying a false ordering (Chicago=2 isn't "more" than Austin=0) unless the algorithm is specifically robust to that, like tree-based models.

Feature engineering is where domain knowledge actually pays off

A raw timestamp column is rarely useful directly, but deriving day-of-week, hour-of-day, or "is this a holiday" from it can capture genuinely predictive patterns a model couldn't infer on its own from the raw timestamp value. This is the concrete point where subject-matter expertise about the business problem translates directly into model performance — no algorithm, however sophisticated, can invent a feature idea that requires knowing something specific about how the business actually works.

Leakage: the feature engineering mistake that inflates results falsely

A feature "leaks" information from the future or from the target itself if it wouldn't actually be available at prediction time in production. A classic example: including "total amount refunded" as a feature when predicting whether an order will be returned — this information wouldn't exist until after the return already happened. Leaked features can make a model look impressively accurate during development while being completely unusable in production, because that information genuinely isn't available when a real prediction is needed.

Check your understanding

1. What risk does label encoding introduce that one-hot encoding avoids?
Assigning integers to categories can be misread by algorithms sensitive to magnitude as implying "more" or "less," even when the categories have no true order — this is exactly the risk one-hot encoding avoids by using independent binary columns instead.
2. Why can deriving day-of-week from a timestamp improve model performance?
This is the core value of feature engineering — translating domain knowledge (weekly patterns exist) into a form the model can actually use directly, rather than hoping the model discovers the pattern from raw data.
3. Why is a leaked feature dangerous even though it can make a model look highly accurate during development?
The danger is specifically the gap between development-time accuracy (using information that shouldn't be available) and production reality (where that information doesn't exist yet) — the model's apparent skill is an illusion.
