11.4 Incident response & production readiness

The runtime is healthy. The logs are moving. The output is formatted correctly. The work quality is dead. That's still an incident.

TL;DR
AI incidents don't look like classical outages — there's rarely one broken commit mapping to one clean rollback. A widely cited 2026 framework structures response around six steps: detect, triage, contain, evaluate, fix, review — across four common incident classes: hallucination, jailbreak, drift, and PII leak. The loop-closing step matters as much as the fix itself: every real incident's post-mortem should become a permanent new entry in the golden dataset (9.1), so the same failure is caught automatically before it ships again.

The illustrative cost of not having this wired up in advance

A documented shape of failure: groundedness drops 9% at 4pm on a Tuesday, caused by a prompt change that shipped at that exact moment. But there's no eval gate watching production in real time — detection instead comes from customer complaints starting the following Friday. That's a 72-hour lag from incident to detection, then 4 more hours from detection to an actual fix. By the time the rollback ships, roughly 5,800 user sessions have already received degraded responses. The post-mortem's own conclusion: none of the missing pieces were exotic — most had been on the original launch plan and gotten deferred.

Why "roll back to the last commit" doesn't map cleanly here

A broken software endpoint usually traces to one commit and one clean rollback. An LLM quality regression can trace to any of several independent layers, each requiring a genuinely different fix: a prompt edit, a silent model-version push from the provider (11.3), a retrieval re-index after a corpus change, or an upstream tool contract change — and several of these can produce the exact same symptom on a small slice of traffic before anyone notices. The response process has to be built to identify which layer actually changed, not just to have a generic "revert" button.

The first five minutes: blast-radius control, not root cause

Specific guidance for the opening of an incident: your job in the first five minutes is not root-cause analysis — it's containing the blast radius. If the incident touches money, customer communications, records, or permissions, the recommended default is to hit a kill switch or roll back immediately, rather than trying to understand the full cause first. Root-cause investigation happens after containment, not instead of it.

The permanent payoff: every incident becomes a regression test

This closes the loop back to Phase 9 directly: an incident real enough to actually hurt is real enough to deserve becoming a permanent entry in the golden dataset — using the same input/context/tool-response pattern that produced the failure. This is what prevents the exact same failure mode from silently shipping again in six months.

Check your understanding

1. Why doesn't the classical "one commit, one rollback" incident model fit most LLM production failures?
Multiple distinct layers can produce the identical user-visible symptom, which is exactly why an effective response process has to identify which layer actually changed rather than assuming a single rollback fixes everything.
2. What is the recommended priority in the first five minutes of a real incident?
Containment and root-cause analysis are sequenced deliberately — stopping the bleeding (kill switch, rollback) comes first, especially when money, records, or permissions are involved, with deeper investigation following afterward.
3. Why does a real incident's post-mortem specifically need to become a golden dataset entry?
This is the loop-closing step from both this page and 9.3's offline/online eval discussion — a real failure that isn't captured as a future regression test can simply happen again unnoticed.
