11.2 Monitoring & observability

"The response reads well" is not the same claim as "the agent actually did the right thing."

TL;DR
Traditional monitoring (latency, error rate, uptime) doesn't capture LLM-specific failure — an agent can hallucinate, answer a different question than asked, or skip a tool and make something up, and the response can still read perfectly well and return a healthy status code. LLM observability adds a layer on top: a tree of spans recording every LLM call, tool invocation, and retrieval step in a multi-step run, letting you reconstruct exactly what an agent did rather than just what it returned. One 2026 industry survey found 89% of teams running some form of agent observability, yet a majority still cite quality visibility as the top barrier to shipping agents reliably.

Why classical monitoring falls short for LLMs

Classical distributed tracing was built for a world where the same input reliably produces the same output and roughly the same latency. LLMs break that assumption structurally — output is non-deterministic even with identical input, and a "successful" response (valid format, fast, no error) can still be substantively wrong in a way no infrastructure metric would ever flag. This is exactly the same insight from 11.1's deployment discussion, extended into ongoing production monitoring rather than just the rollout window.

The four things a trace needs to capture

  • LLM calls — the prompt sent, the response received, tokens used, latency.
  • Tool invocations — which tool was called, with what arguments, what result came back (8.2's tool contracts, now logged in production).
  • Retrieval steps — what was retrieved for a RAG-backed query (Phase 6), and how relevant it actually was.
  • Reasoning/decision points — for agents, the intermediate thoughts and branch decisions from the ReAct loop (8.1), not just the final output.

Without all four captured as nested, parent-child-linked spans, reconstructing what an agent actually did during a multi-step failure is close to impossible — you're left staring at a final wrong answer with no way to see which of the several steps that produced it actually went wrong.

Monitoring vs. observability — a real distinction, not just jargon

Monitoring tracks a fixed, predefined set of metrics — latency, cost, uptime. Observability goes further: it captures the full execution trace of a workflow, letting you reconstruct and debug a failure you didn't specifically anticipate ahead of time, including non-deterministic ones that a simple log line could never fully explain. You need both — monitoring for always-on alerting against known thresholds, observability for actually understanding a novel failure once one shows up.

Check your understanding

1. Why can't "the response reads well" reliably indicate that an agent worked correctly?
Fluency and correctness are separate properties — a confidently wrong answer reads exactly as well as a correct one, which is precisely why span-level tracing matters more than just checking the final output.
2. What's the key difference between monitoring and observability, as used in this context?
Monitoring is good for always-on alerting against known thresholds (latency, cost); observability is what lets you reconstruct and understand a specific, possibly novel failure after the fact.
3. Why does a trace need to capture reasoning/decision points, not just the final LLM output?
This connects directly to the ReAct loop from 8.1 — without visibility into the individual thought/action/observation steps, a wrong final answer gives you no way to localize which step in the chain actually went wrong.
