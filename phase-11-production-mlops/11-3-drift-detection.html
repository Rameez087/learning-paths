11.3 Drift detection

Nothing in your logs is broken. Nothing in your APM dashboard is firing. The model is quietly getting worse anyway.

TL;DR
LLM drift is unintended change in production behavior over time, and it comes in several distinct flavors: data drift (the input distribution shifts — users start asking about things the system wasn't built for), concept drift (the relationship between input and correct output changes — the same question now warrants a different answer), model drift (a provider silently updates the underlying model's weights, and behavior shifts without any change on your side), and eval-score drift (a rolling quality score trends down for any combination of the above reasons). Crucially, drift is invisible to error-rate dashboards and infrastructure monitoring — it's visible only to a system that's actively scoring production traces over time.

Try it: watch a groundedness score quietly decay

The illustrative incident this reflects

A support agent scores 89% groundedness in production one day. The next day it's at 81%. The prompt hasn't changed. The model ID in the config hasn't changed. The document corpus feeding retrieval hasn't changed. Latency is normal, error rate is zero, and nothing in the standard APM dashboard is firing. The only visible signal is a rolling-mean groundedness score computed from evaluated production traces — and by the end of the week it's down to 76%. The eventual finding: the model provider quietly rolled out a weight update mid-week. Nothing in the application changed at all; the underlying model itself did.

Data drift vs. concept drift — a real, useful distinction

  • Data drift (covariate shift) — the input distribution changes, but the correct mapping from input to output hasn't. Users start asking about a new product category the system wasn't built for. This can exist without actually harming the model, if the shift happens to be in something the model doesn't rely on.
  • Concept drift — the underlying rule mapping inputs to correct outputs itself changes. A returns policy changes, so the same customer question now warrants a genuinely different correct answer than it did last month. This is harder to detect because the input distribution can look completely stable while the model quietly gets more wrong answers.

Reducing alert noise: joint conditions

A single drift signal in isolation — input distribution shift alone, or a quality score dip alone — generates a lot of false-positive noise on its own. Current guidance recommends alerting on the joint condition: both an input distribution shift and a corresponding evaluator score drop together, which cuts alert noise sharply compared to firing on either signal independently.

The one piece of restraint that shows up consistently in 2026 guidance

Detecting drift is only useful if it changes what you actually do next — and the most consistently repeated advice across current practitioner sources is specifically restraint: don't retrain or roll back reflexively the moment drift is flagged. Confirm the drift is real, and confirm it's genuinely degrading a meaningful evaluation metric, before taking action. A false-positive-driven retrain or rollback wastes real engineering effort and can introduce its own regression.

Check your understanding

1. Why was the illustrative groundedness-score drop invisible to standard APM dashboards?
This is the central point of drift detection — infrastructure health metrics and content quality metrics are entirely separate signals, and drift specifically shows up only in the latter.
2. What makes concept drift harder to detect than data drift?
Because the inputs themselves haven't visibly shifted, monitoring input distributions alone won't catch concept drift — it requires actually checking output correctness against the current, possibly-changed ground truth.
3. Why is alerting on a joint condition (input shift AND score drop) recommended over either signal alone?
Data drift alone can be harmless if it's in a feature the model doesn't rely on — requiring both signals together is a practical filter for genuinely actionable drift versus noise.
