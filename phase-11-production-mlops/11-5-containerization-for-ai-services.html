11.5 Containerization for AI services

Roughly 87% of ML models reportedly die in the gap between "works in a notebook" and "serves live traffic." Containerization is what closes that gap.

TL;DR
For most AI engineers building on top of hosted APIs (Phases 4-8 of this track), the containerization job is straightforward: package your application — the RAG pipeline, the agent, the API wrapper — into a Docker image so it runs identically in development, staging, and production, then orchestrate it with Kubernetes for scaling and reliability. This is a distinct, narrower skill from containerizing the model-serving layer itself (running an open-weight model on GPUs with something like vLLM), which is closer to specialized ML infrastructure work. Both are listed as core skills in 2026 AI engineering job postings, but most application-layer engineers primarily need the first one.

Why containerize your application layer at all

  • Environment consistency — the same container runs identically in development, staging, and production, eliminating "works on my machine" as a category of bug.
  • Dependency isolation — Python package versions, system libraries, and any native dependencies are bundled together, avoiding the classic version-conflict problem.
  • Independent scaling — your API layer, your vector database, and your frontend can each scale independently based on their own load, rather than being locked to the same deployment unit.
  • Orchestration-native — a containerized service plugs directly into the canary and rollback patterns from 11.1, and the tracing/observability tooling from 11.2, without extra glue code.

A minimal Dockerfile for a RAG/agent API service

FROM python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Never bake API keys into the image — inject at runtime
ENV ANTHROPIC_API_KEY=""

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Two details worth internalizing: never hardcode a secret into the image itself (same principle as 1.5's environment-variable guidance, now at the infrastructure layer — a leaked image is just as dangerous as leaked source code) and pin dependency versions explicitly so a rebuild six months from now doesn't silently pull incompatible package updates.

When you actually need GPU-aware container orchestration

If your work involves self-hosting an open-weight model (rather than calling a provider's API), a different and more specialized layer applies: GPU passthrough via the NVIDIA Container Toolkit, an inference engine like vLLM handling request batching and KV-cache management, and Kubernetes scaling on custom metrics like queue depth rather than plain CPU/memory usage — because unlike a stateless web service, each model replica loads the entire model into GPU memory, so scaling means adding whole replicas, not distributing load more finely across existing ones. This is a real, distinct specialization, and most application-layer AI engineers building on hosted APIs won't need to go this deep — but it's worth knowing the line exists, since job postings sometimes blur the two skill sets together.

Check your understanding

1. For most AI engineers building on hosted LLM APIs, what does "containerization" primarily mean?
These are genuinely different skill sets — application-layer containerization is broadly needed, while GPU-aware model-serving containerization is a more specialized track for teams self-hosting open-weight models.
2. Why shouldn't an API key ever be baked directly into a Docker image?
This is the same principle from 1.5's API key guidance, applied one layer down — an image can end up in a registry or shared accidentally just as easily as a code repository can.
3. Why does scaling a self-hosted LLM inference service differ from scaling a typical stateless web service?
A stateless web service can often handle more load per instance up to some CPU/memory ceiling; an LLM inference replica's entire capacity is bounded by having a full model resident in GPU memory, making the scaling unit fundamentally coarser.
