5.2 Vector index internals: HNSW vs IVF

Searching a million vectors one at a time would take forever — here's how it actually stays fast.

TL;DR
Comparing your query vector against every single stored vector (exact search) doesn't scale past a small collection. Production vector databases use approximate nearest neighbor (ANN) indexes instead — trading a small amount of accuracy for enormous speed gains. The two dominant approaches: HNSW (a navigable graph structure, fast queries, memory-hungry) and IVF (partitioning vectors into clusters searched selectively, far less memory, better suited to very large collections). Most production databases default to HNSW unless memory becomes the binding constraint.

HNSW: navigable small-world graphs

HNSW (Hierarchical Navigable Small World) builds a multi-layer graph where each vector is a node connected to its approximate neighbors. A search starts at a sparse top layer and "zooms in" through progressively denser layers, following the graph's edges toward the query's actual nearest neighbors — similar in spirit to how a highway system lets you get roughly to the right city fast before switching to local roads for the final approach. This produces very fast, high-recall queries, at the cost of memory: HNSW maintains many edges per node, and that graph structure has to live in memory for fast traversal.

IVF: cluster first, search selectively

IVF (Inverted File index) takes a different approach: it partitions the entire vector space into a number of clusters ahead of time (via a clustering algorithm like k-means). At query time, instead of searching everything, it identifies the handful of clusters closest to the query vector and only searches inside those — skipping the vast majority of the collection entirely. This uses meaningfully less memory than HNSW, because it stores far fewer connections per vector, which is why IVF is often the choice for very large corpora where an HNSW graph simply wouldn't fit comfortably in memory.

Hybrid indexes: getting both

Some production systems combine a vector index (HNSW or IVF) with a traditional keyword index (like BM25, an inverted index over exact terms) in the same query path — this is the foundation of hybrid search, covered next in 5.3, because vector search alone genuinely struggles with exact-match queries like error codes, IDs, or specific numbers that don't carry rich "semantic meaning" the way prose does.

Check your understanding

1. Why do production vector databases use approximate nearest neighbor search instead of exact search?
ANN indexes are explicitly a speed/accuracy trade-off — they sacrifice a small, usually acceptable amount of recall for search times that make million-plus vector collections practical to query in real time.
2. What's the core mechanism that makes IVF use less memory than HNSW?
HNSW's memory cost comes from maintaining many graph edges per node; IVF's clustering approach doesn't need that dense connectivity, which is the direct source of its lower memory footprint.
3. Why does vector search alone struggle with a query like an exact error code?
An embedding captures meaning, not exact tokens — a query for a specific error code can retrieve semantically related but not textually matching content, which is exactly the gap hybrid search (combining vector + keyword search) is designed to close.
