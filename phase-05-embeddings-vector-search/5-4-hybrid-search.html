5.4 Hybrid search

Semantic search finds meaning. Keyword search finds exact strings. Real queries often need both.

TL;DR
Vector search excels at conceptual, paraphrased queries but genuinely struggles with exact matches — error codes, product IDs, specific numbers — because embeddings capture meaning, not literal tokens. Hybrid search runs both a vector search and a traditional keyword search (typically BM25, a scoring algorithm over an inverted index) in parallel, then merges the results. Reported enterprise data shows hybrid search improving recall by around 17%, and a large majority of enterprises using it report meaningfully better query accuracy versus vector search alone.

Why vector search alone misses exact matches

An embedding represents overall meaning — "kafka error code 504" and "kafka timeout in distributed systems" can land close together in vector space because they're conceptually related, even though only one of them contains the literal string "504" the user actually typed. For a query that's fundamentally about an exact identifier, that conceptual closeness is the wrong signal — the user wants the document containing that specific code, not documents about vaguely similar topics.

How the two search paths combine

A common architecture keeps the vector index and a keyword index (an inverted index, using an algorithm like BM25) as two separate systems, each optimized for its own kind of matching — not redundant storage, but purpose-specific indexing. Both run against the same query, and their result sets get merged and re-ranked (often the reranking step covered in Phase 6) before the final top results are handed to the LLM.

The cost of doing this

Maintaining two indexes over the same underlying content is more operational overhead than a single vector index — a single source of truth typically feeds pipelines that keep both indexes synchronized. Enterprises report tolerating this added complexity specifically because the accuracy gain is large enough to justify it, not because it's free.

Check your understanding

1. Why does a query like "error code 504" often fail with vector search alone?
A document about "timeout in distributed systems" can be conceptually close to "error code 504" in embedding space without containing the literal code — exact-match precision isn't what vector similarity optimizes for.
2. What does BM25 provide that a vector index doesn't?
BM25 is a keyword-scoring algorithm over an inverted index — its strength is exact and near-exact term matching, which is precisely the case vector search handles poorly.
3. Why do production hybrid search systems generally maintain two separate indexes rather than one combined structure?
This is a deliberate trade-off, not a limitation — the reported recall improvement from combining both search types is large enough that teams accept the extra operational overhead of keeping two indexes synchronized.
