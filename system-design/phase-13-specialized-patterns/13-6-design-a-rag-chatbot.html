13.6 Design a RAG chatbot

Chirp adds an AI assistant that answers questions using your own post history. The final capstone — and a direct bridge to your AI Engineering track.

TL;DR
Requirements: answer user questions grounded in their actual Chirp data (not the model's general knowledge), stay current as new posts are made, respond fast, control cost. The architecture is a genuine synthesis of nearly everything in this track: an embedding pipeline (async, Chapter 7's workers) converts posts into vectors stored in a specialized vector index (11.4's database taxonomy, extended one type further), a retrieval step finds relevant content for a given question (11.5's search fundamentals, applied to semantic similarity instead of exact-match), and the LLM generates an answer grounded in what was retrieved.

Try it: walk through the retrieval pipeline

Why embedding generation is asynchronous, one more time

Recall Chapter 7.1: computing something expensive inside the critical request path blocks everything else. Converting a new post into a vector embedding is exactly this kind of work — it happens via a background worker (7.2) the moment a post is created, never inside the user's actual posting request. By the time anyone asks a question referencing that post, its embedding is already sitting in the vector index, ready to be retrieved instantly.

The deep-dive: keeping the index fresh without re-embedding everything

A new post needs its own new embedding — but recall Chapter 4.4's cache invalidation lesson: when a post is edited or deleted, its old embedding needs to be updated or removed too, or the chatbot will confidently answer using outdated information. This is the same targeted invalidation instinct as 4.4, applied to a vector index instead of a Redis cache — invalidate precisely what changed, not the whole index.

Cost control: rate limiting applied to a genuinely different resource

Unlike most of Chirp's features, each chatbot query has a real, non-trivial cost per request (the LLM call itself). This makes Chapter 11.2's rate-limiting algorithms directly relevant again, but for a new reason — not just protecting server capacity, but directly controlling real dollar cost per user, a concern that barely existed anywhere else in this track.

Why this problem belongs at the very end of this track

A RAG chatbot isn't really one new technique — it's a genuine composition of nearly every primitive covered across all thirteen phases: async processing (7), a specialized database type (11.4), search fundamentals (11.5), targeted cache invalidation (4.4), and cost-aware rate limiting (11.2), applied together toward a single new capability. Recognizing a complex, unfamiliar-looking system as a composition of already-known primitives — rather than something requiring entirely new knowledge — is the actual, final demonstration of everything this whole track was built to teach.
