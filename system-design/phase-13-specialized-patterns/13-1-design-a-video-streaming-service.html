13.1 Design a video streaming service

Chirp's video posts (Chapter 7.1) at YouTube/Netflix scale — the same transcoding problem, now with the actual delivery pipeline built out fully.

TL;DR
Requirements: upload a video once, let it stream smoothly to viewers with wildly different connection speeds and devices. The core technique is adaptive bitrate streaming: transcode (Chapter 7.1's exact process) each video into multiple quality versions (240p up to 4K), split into short chunks, and let the viewer's player automatically switch quality mid-stream based on their real-time connection speed — never fully buffering the highest quality if the network can't sustain it.

Try it: watch adaptive bitrate respond to connection speed

Why transcoding into multiple versions upfront, not on demand

Transcoding is genuinely expensive (7.1's exact bottleneck) — doing it once per upload, into a fixed set of quality tiers, asynchronously via background workers (7.2's pattern), means every subsequent view is just serving pre-computed files, never repeating that expensive work per viewer. This is the same "don't recompute what hasn't changed" instinct from Chapter 4.2's caching, applied to computation instead of database queries.

The deep-dive: CDN placement is almost the whole game here

Recall Chapter 9's core lesson: physical distance has a real, unavoidable latency floor. Video is enormously bandwidth-heavy compared to Chirp's text posts, which makes CDN edge placement (9.2) even more critical here than for any other pattern in this track — the overwhelming majority of a streaming service's engineering effort in practice goes into CDN strategy and chunk caching, not the transcoding pipeline itself.

View counting: a deceptively tricky consistency problem

A view counter seems trivial but has a real design question hiding in it: should it update in real time (expensive at scale, exactly 4.1's original read-storm problem if done naively) or batch-update periodically (cheaper, but counts lag behind reality)? Most real platforms batch view count updates — the same acceptable-staleness trade-off from 4.2 and 12.6, chosen once again for the same underlying reason.

Check your understanding

1. Why does adaptive bitrate streaming transcode a video into multiple quality versions rather than serving one fixed quality to everyone?
This is the core technique the whole topic is built around — accommodating real-world variance in viewer conditions rather than assuming uniform playback conditions.
2. Why does transcoding happen once, upfront, per upload rather than being computed fresh for each viewer?
This directly reuses the "don't recompute what hasn't changed" principle from Chapter 4.2's caching discussion, applied to computation rather than database reads.
3. Why do most real video platforms batch-update view counts rather than updating them in true real time?
This is another instance of the track's recurring staleness-for-performance trade-off, applied to yet another new context — reinforcing that this isn't a one-off decision but a general, reusable pattern.
