13.3 Design Dropbox

File sync at scale — genuinely the same core idea as Chapter 5's replication, applied to files a user actively edits on multiple devices instead of database rows.

TL;DR
Requirements: keep files in sync across a user's devices, upload efficiently, handle offline edits. The core technique is chunking: split each file into fixed-size blocks, hash each block, and only upload blocks that have actually changed — editing one paragraph of a large document re-uploads a few KB, not the whole file. This directly reuses 11.5's hashing instinct (a bloom filter's cheap existence check) for a genuinely different purpose: cheaply detecting which specific parts of a large file are actually new.

Try it: see chunking avoid re-uploading unchanged data

Why chunk-level, not file-level, change detection

Re-uploading an entire 500MB video file because one 10KB metadata field changed would be a genuinely wasteful design — chunking breaks the file into smaller pieces specifically so only the pieces that actually changed need to move over the network. This is the same underlying principle as Chapter 4's caching (avoid redoing work that's already correct) applied at the level of file content instead of computed query results.

The deep-dive: conflict resolution when the same file changes on two devices while offline

Recall Chapter 9.3's cross-region conflict: two writable copies of the same data can diverge. File sync has almost the exact same shape — a laptop and a phone both edit the same file while offline, then both reconnect. A real system typically keeps both versions (creating a "conflicted copy" file) rather than silently discarding one — the same honest acknowledgment from 9.3 that automatic conflict resolution can't always determine the "right" answer, so surfacing the conflict to the user is sometimes the more honest choice than guessing.

Metadata vs. content: two different storage problems, cleanly separated

File content (the actual bytes) is naturally suited to object storage optimized for large blobs. File metadata (name, folder structure, sharing permissions, version history) is naturally relational — clear structure, relationships between files and folders, exactly Chirp's default database type from 11.4. Separating these, rather than cramming file bytes into a relational database, mirrors Chapter 8's principle of matching each piece of data to the storage that actually fits its shape.
