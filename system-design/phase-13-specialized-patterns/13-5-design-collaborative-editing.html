13.5 Design collaborative editing

Two people editing the same Chirp draft post simultaneously — genuinely the hardest consistency problem in this entire track, made concrete.

TL;DR
Requirements: multiple users edit the same document simultaneously, with every user seeing a consistent, correctly-merged result in real time (Google Docs, Figma). Unlike Chapter 9.3's conflict resolution (pick a winner, or surface a conflict to the user), collaborative editing needs to merge genuinely simultaneous, character-level edits automatically and correctly. The two real techniques: Operational Transformation (OT), transforming each incoming edit against every other edit that happened concurrently so they compose correctly, and CRDTs (Conflict-free Replicated Data Types), data structures mathematically designed so concurrent edits always merge consistently, no matter what order they arrive in.

Try it: watch two simultaneous edits merge correctly

Why this problem is harder than every earlier consistency challenge in this track

Chapter 9.3's cross-region conflicts were resolved by picking a winner or surfacing an explicit conflict — acceptable because losing or delaying a bio update is low-stakes. Losing a sentence someone just typed into a shared document is a fundamentally worse outcome. This is precisely why collaborative editing needs a genuinely different class of technique — not picking a winner, but mathematically guaranteeing both edits survive and compose correctly.

The deep-dive: why transforming edits, not just timestamping them, is necessary

If User A inserts a word at position 5, and User B simultaneously deletes text at position 3, naively applying both edits in arrival order corrupts the document — B's delete was computed against a document that didn't yet include A's insert. Operational Transformation solves this by mathematically adjusting each incoming operation's position based on what else happened concurrently, so applying them in either order still produces the same, correct final document — a property called convergence.

Why real-time collaborative editing still needs Chapter 12.3's WebSockets

Every edit needs to reach every other collaborator's screen the instant it happens — exactly the persistent, bidirectional connection requirement from Chapter 12.3's chat design. This is a genuine, direct reuse of an earlier capstone's networking model, not a coincidence: any feature requiring instant multi-user synchronization tends to need the same underlying connection type.
