3.3 Deep dive: load balancing algorithms

Round robin got Chirp through Saturday. It's not the algorithm every load balancer should always use — here's why, and what the alternatives actually do differently.

TL;DR
Four algorithms cover the large majority of real load balancing decisions: round robin (cycle through servers evenly, simplest), least connections (send to whichever server currently has the fewest active requests — better when requests take genuinely different amounts of time), weighted variants of either (account for servers with different capacities), and IP hash / consistent hashing (the same client always routes to the same server — useful when a server needs to remember something about a specific client). Health checks run underneath all of them, removing a failed server from rotation automatically.

Why round robin can quietly create an imbalance

Round robin assumes every request costs roughly the same amount of work — true for many of Chirp's endpoints, but not all of them. A request to load a simple profile page and a request to process a video upload are wildly different in cost. If server 2 happens to get several expensive video-upload requests in a row purely by the luck of the rotation, it can end up doing meaningfully more work than servers 1, 3, and 4 — even though round robin gave each of them the exact same number of requests.

Health checks: the mechanism underneath every algorithm

# Simplified health check logic, run periodically against every server
def health_check(server):
    try:
        response = http_get(f"http://{server}/health", timeout=2)
        return response.status_code == 200
    except TimeoutError:
        return False

# Every 5 seconds, the load balancer re-checks each server
# and removes any failing server from the active rotation
for server in server_pool:
    if not health_check(server):
        remove_from_rotation(server)
    else:
        add_to_rotation(server)  # re-add if it recovers

This is what actually delivers on 3.2's resilience claim — a server crashing doesn't just mean it stops receiving new traffic eventually, it means the load balancer actively detects the failure within seconds and routes around it, without anyone needing to intervene manually.

IP hash: when "any server can handle any request" stops being true

Every algorithm so far assumes any server can equally handle any request — true for Chirp's app servers right now, since they're stateless copies of the same code with no server-specific memory. IP hash exists for the opposite case: when a server needs to remember something specific about a client across multiple requests (an in-progress file upload, a WebSocket connection). Foreshadowing directly: Chirp's next chapter is about to hit exactly this "server needs to remember something" problem, for a different reason than uploads.

Check your understanding

1. Why can round robin create an uneven workload even though it distributes an equal number of requests to each server?
This is exactly why least-connections exists as an alternative — it reacts to actual current load rather than just counting requests distributed.
2. How do health checks deliver on the resilience benefit claimed for horizontal scaling in 3.2?
This is the concrete mechanism underneath the abstract resilience claim — without automated health checks, a failed server would keep receiving traffic it can't handle until someone noticed manually.
3. What specific situation does IP hash routing solve that round robin and least-connections don't?
This is a genuinely distinct use case — algorithms that route freely assume statelessness, while IP hash specifically solves the case where that assumption breaks down.

This deep dive reflects standard, durable load balancing algorithm behavior consistent across major implementations (Nginx, HAProxy, AWS/GCP/Azure load balancers) — stable concepts despite differing product names.
