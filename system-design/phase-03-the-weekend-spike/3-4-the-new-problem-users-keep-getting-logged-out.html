New Problem

3.4 The new problem: users keep getting logged out

The spike is handled. Now support is getting a strange new complaint: "I log in, then two clicks later, I'm logged out again. Happens randomly."

"Getting a handful of tickets a day now — 'randomly logged out.' Can't reproduce it consistently myself. Weirdly, it seems to happen more to people clicking around fast." — support lead, in the bug tracker
TL;DR
When a user logs in, the app server that handled that specific request stored their session (who they are, that they're authenticated) in its own local memory — a leftover assumption from the single-server days. Now that there are four app servers behind a load balancer, the next request from that same user might get routed to a completely different server that has never heard of their session, and gets treated as logged out. This is 3.3's "any server can handle any request" assumption breaking, for a new reason: the app servers aren't actually fully stateless yet.

Try it: watch a session break across servers

Why this didn't happen before Chapter 3

With one app server, every request from every user always landed on the exact same machine — so storing session data in that server's local memory worked perfectly, by accident. It was never actually a good pattern; it just happened to work because there was only ever one place a request could go. Horizontal scaling didn't introduce a new bug into the session logic — it exposed an assumption that was always fragile, the moment it stopped being true.

Two real fixes, and why one is clearly better here

  • Sticky sessions — configure the load balancer to always route a given user's requests to the same server (this is exactly 3.3's IP hash routing, applied to solve this specific problem). Simple to set up, but it undermines even distribution and means losing that one server logs out everyone whose session lived there.
  • Externalize the session entirely — store session data somewhere all four app servers can read from equally (a shared store like Redis), so it genuinely doesn't matter which server handles any given request. This is the pattern that scales cleanly — it's what makes the app servers actually stateless, not just accidentally stateless when there was only one of them.

Chirp goes with externalizing sessions to Redis. It's slightly more setup than flipping a sticky-session switch, but it doesn't create a new fragile dependency on any one specific server, and it sets up cleanly for every future chapter where more app servers get added.

The pattern this chapter teaches, stated plainly

Anything an app server "remembers" about a specific user between requests needs to live somewhere every server can access equally — not in any one server's local memory. This single principle (statelessness) is one of the most load-bearing ideas in this entire track; it's what makes horizontal scaling actually work cleanly, and it'll come up again directly in Phase 7's background job workers and Phase 8's service decomposition.

Check your understanding

1. Why does storing session data in an app server's local memory break once there are multiple servers behind a load balancer?
This is the direct mechanism — local memory is, by definition, local to one specific machine, which becomes a real problem the moment more than one machine exists.
2. Why did this session problem never occur back when Chirp ran on a single app server?
This is an important distinction — horizontal scaling didn't create a new bug, it exposed a fragile assumption that was always there but never mattered until the environment changed.
3. Why does externalizing session storage to a shared store (like Redis) scale better than sticky sessions?
This sets up the statelessness principle that recurs throughout the rest of the track — a genuinely stateless app layer is more resilient and easier to scale than one relying on sticky routing.

This chapter reflects standard, durable distributed-systems practice around session externalization and application statelessness — a foundational pattern underlying nearly all horizontally-scaled web architectures.
