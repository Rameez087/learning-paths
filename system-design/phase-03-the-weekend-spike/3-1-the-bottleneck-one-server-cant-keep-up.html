3.1 The bottleneck: one server can't keep up

A local influencer posted about Chirp on a Friday night. By Saturday morning, the app server was returning 502 errors to roughly one in six requests.

⚠ Alert
Request queue depth on the app server spiked to 1,400 pending requests at peak. Error rate hit 17% for 40 minutes. The app server's own CPU sat at 96%+ throughout — this time it's a capacity problem, not a contention problem, since the database is on its own machine now (Chapter 2) and its CPU stayed under 30%.
"We're trending?! Amazing news except the app is falling over. Every request is timing out. I don't think a bigger server fixes this fast enough even if I upgrade it right now." — you, Saturday morning, from your phone
TL;DR
Even with the database separated out (Chapter 2) and the app server vertically scaled up (Chapter 2.3), one app server has a genuine, real ceiling on how many concurrent requests it can process at once. A traffic spike — the exact kind Chirp just got, unpredictably, from a viral moment — can blow straight past that ceiling in minutes, and there's no time to provision a bigger machine fast enough to matter. This is the moment vertical scaling's second real limitation shows up: it isn't just expensive at the high end, it's also slow to react to a spike, since resizing a running server usually means a restart.

Why one server can never fully absorb an unpredictable spike

Every server, no matter its size, has a maximum number of requests it can process per second before new requests start queuing faster than old ones finish. Once that queue starts growing, response times climb for everyone — including requests that would otherwise have been fast — because they're now waiting in line behind a backlog. Past a certain queue depth, the server (or a proxy in front of it) starts actively rejecting requests rather than accepting more it can't handle, which is exactly the 502 errors real Chirp users saw.

Why this is a genuinely different problem from Chapter 2's

Chapter 2's bottleneck was resource contention between two processes sharing one machine — solved by giving each its own hardware. This bottleneck is different: even with the app server having its CPU entirely to itself, there's simply more concurrent work arriving than one machine, however large, can process at once. Bigger hardware helps somewhat, but the real fix is structural: stop relying on exactly one machine to absorb all traffic, no matter how big that one machine gets.

Why unpredictability makes this worse than steady growth

Chapters 1 and 2's growth was gradual — user count climbing over weeks, giving time to notice trends and react. A viral spike is different: traffic can 20x within an hour, with zero advance warning. Any fix that depends on a human noticing a graph and manually provisioning more capacity is too slow for this specific failure mode. The fix needs to already exist, ready to absorb a sudden spike, not be something reactively built after the fact.
