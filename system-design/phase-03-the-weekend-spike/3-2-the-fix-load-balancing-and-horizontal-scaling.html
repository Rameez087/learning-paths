3.2 The fix: load balancing & horizontal scaling

Instead of one bigger server, four normal ones — and something in front deciding which one each request goes to.

"Put 4 app servers behind a load balancer this week. Ran a simulated version of Saturday's traffic against it this morning. Zero errors. Actually kind of nervous how well it worked." — you, the following Wednesday
TL;DR
Horizontal scaling means running multiple copies of the app server instead of one bigger one. A load balancer sits in front of them, receiving every incoming request and routing it to whichever app server should handle it — spreading the total load across as many machines as are running. This directly solves 3.1's capacity ceiling (more machines means more total throughput) and, as a genuine side benefit, finally kills Chapter 1's original single-point-of-failure risk for the app layer — one server going down no longer takes Chirp down completely.

Try it: watch a load balancer distribute a spike

Why more, smaller machines beat one bigger one here

Four servers each capable of 1,200 requests/second give roughly 4,800 requests/second total — comparable to (often cheaper than) the largest single-machine tier from Chapter 2.3's cost curve, but with a genuinely different risk profile: losing one of four servers means losing 25% of capacity, not 100% of it. This is horizontal scaling's real advantage over vertical scaling — it improves both capacity and resilience at once, rather than trading one for the other.

How the load balancer actually decides where a request goes

The simplest strategy, round robin, sends each new request to the next server in line, cycling through them evenly. It's a reasonable default, but not always the best — a more sophisticated load balancer can route based on which server currently has the fewest active connections, or perform periodic health checks and stop sending traffic to a server that's stopped responding correctly. The specific algorithm matters enough that it gets its own full treatment next.

The load balancer is now doing a genuinely important job

Worth naming honestly: the load balancer itself is now a component every single request passes through. If it's not itself resilient (usually achieved by running more than one, in an active-passive or active-active setup), it becomes a new single point of failure — just moved one layer up instead of eliminated. Most managed cloud load balancers handle this transparently, but it's a real detail, not a hand-wave, and worth remembering later in this track when the same "don't just move the bottleneck" pattern shows up again.
