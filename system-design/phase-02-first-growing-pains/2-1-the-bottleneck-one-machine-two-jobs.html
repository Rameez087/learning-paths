2.1 The bottleneck: one machine, two jobs

Chirp crossed 8,000 users this week. The app feels sluggish — not down, just slow, in a way that gets worse every day.

⚠ Alert
p95 response time has climbed from 80ms to 640ms over the last two weeks, with no single deploy that explains it. CPU usage on the server sits at 91% during peak hours.
"Feed is taking almost a full second to load for some users. Nothing changed in the code. I think we're just... out of room?" — you, in the team Slack
TL;DR
The Chirp application and its Postgres database are still running on the same server, and they're now genuinely fighting over the same finite resources — CPU cycles, RAM, and disk I/O. Every incoming request needs the application to do work and the database to do work, on hardware that has to split its attention between both. This wasn't a problem at 500 users because there was plenty of slack in the system. At 8,000 users, that slack is gone.

Why this specific failure mode, and not a crash

Nothing is actually broken in the sense of throwing errors. Every request the application handles needs to run its own logic (parsing, validation, business rules) and wait for the database to read or write data — and both of those are now competing for the same CPU cores and the same limited RAM. When the application process is busy handling a spike of incoming requests, the database gets less CPU time to execute queries. When the database is mid-query on a large read, the application has less room to process the next request. Neither side is "wrong" — they're both doing exactly what they should, on hardware that can't give either of them full attention anymore.

Why this specific number — 8,000 users — isn't a magic threshold

There's nothing special about 8,000 as a universal number; it's specific to Chirp's server size, its query patterns, and how much work each request actually does. A more write-heavy app, or one running on a smaller server, would hit this same contention wall at a much lower user count. A read-light app on a beefier server could push well past 8,000 before feeling it. What matters is the underlying mechanism — two resource-hungry processes sharing one finite machine — not the specific number at which any particular app hits it.

The diagnostic habit worth building here

Before reaching for any fix, the useful question is always "what resource is actually saturated, and by what." Watching CPU usage climb toward 90%+ while response times degrade is a specific, legible signal — it's not "the app is slow" in some vague sense, it's "the machine is out of CPU headroom, and both processes need CPU." That specificity is exactly what points toward the right fix rather than a guess.
