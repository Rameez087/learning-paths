2.2 The fix: splitting app and database

The fix here isn't clever. It's the most obvious move available — and it's obvious precisely because the bottleneck was so precisely diagnosed.

"Moved Postgres onto its own droplet last night. App server CPU dropped to 34%. DB server sits around 40%. Feed loads in under 100ms again." — you, the next morning
TL;DR
Move the database onto its own dedicated machine. Now the application has its CPU and RAM entirely to itself, and so does the database — they still talk to each other constantly, but over the network instead of fighting for the same local resources. This single move is usually the very first scaling step any growing system takes, because it directly addresses the exact contention diagnosed in 2.1 without introducing any new moving parts yet.

The trade-off this fix introduces, honestly stated

Separating the database onto its own machine removes resource contention, but it adds something that wasn't there before: network latency between the app and the database. A query that used to be a local function call is now a network round trip — typically still fast (often under a millisecond on the same data center's internal network), but not literally free the way an in-process call was. This is the first real instance of a pattern that recurs throughout this entire track: every fix trades one problem for a smaller, different one.

Why this is now two machines to operate, not one

A less obvious cost: there are now two things to monitor, patch, back up, and pay for instead of one. This is a genuinely real operational cost, and it's worth being honest about it rather than presenting this fix as strictly free. It's simply a cost worth paying at this scale — the contention problem from 2.1 was actively degrading the product for real users, while "one more server to manage" is an ongoing but manageable line item.

Configuration, not just placement

Splitting the machines only pays off if each one is actually tuned for its job. A database server benefits from memory configured for its specific workload (query caching, connection pooling settings) — configuration that would have been a compromise on a shared machine where the application also needed its own share of memory. Separation doesn't just remove contention; it unlocks tuning that wasn't previously possible.
