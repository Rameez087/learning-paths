1.2 The fragility nobody notices yet

One server means one thing: if it goes down, Chirp goes down completely. At 500 users, that's a real risk you're choosing to accept — knowingly, not by accident.

"Quick heads up — I restarted the server to apply a security patch and Chirp was down for about 90 seconds. Nobody seemed to notice. But if this happens during a bigger traffic moment, that's a different story." — you, three weeks after launch
TL;DR
A single point of failure is any one component whose failure takes down the whole system. Chirp's single server is currently a single point of failure for everything — the application, the database, and even local file storage all live and die together. At 500 users, this is a genuinely acceptable trade-off: the alternative (redundancy) costs real money and real complexity, for a failure that, if it happens, affects very few people for a short time. The question this chapter sets up: at what point does that trade-off stop making sense?

Why "just add a backup server" isn't actually the next move

The intuitive fix for a single point of failure is redundancy — a second server ready to take over. But at Chirp's current scale, this solves a problem that isn't actually the pressing one yet. As you'll see starting next chapter, the single server's real first failure mode isn't going to be "it crashes" — it's going to be "the app and the database start actively fighting each other for the same CPU and memory," which redundancy alone wouldn't fix anyway. Availability and capacity are different problems, and Chirp is about to hit the capacity problem first.

What "acceptable risk" actually means in system design

Every architectural decision in this track is a trade-off, not a pursuit of some theoretical "correct" design. Accepting a single point of failure at 500 users isn't a mistake to feel bad about — it's a deliberate, reasonable choice given the actual cost of failure at this scale versus the cost of preventing it. The skill this track is building isn't "always choose maximum resilience" — it's recognizing exactly when a given trade-off stops making sense, which is a different threshold for every system, every team, and every moment in that system's growth.

What's about to happen

Chirp's user count is about to climb — not because of some external event, but because the product is genuinely working. And the very first crack won't be a dramatic outage. It'll be something quieter and more specific: two processes on the same machine, quietly getting in each other's way.
