6.1 The bottleneck: one database can't hold everyone

Read replicas fixed the read problem beautifully. Nobody thought to ask what happens when the data itself simply won't fit anymore.

⚠ Alert
Primary database storage is at 89% of its maximum volume size. Write latency on the posts table has climbed 3x over the last month as its index has grown past what fits comfortably in memory. Replicas are healthy — this is a primary-side problem replication can't help with.
"This is a new kind of bottleneck. It's not that we're doing too much work at once — the database is running out of actual room. And every replica just faithfully copies the same, ever-growing dataset, so more replicas don't help even a little." — you, in the infra channel
TL;DR
Read replicas (Chapter 5) solve read throughput by adding more machines that can each answer queries — but every replica holds a full, identical copy of the same growing dataset. As the total volume of posts, users, and follows keeps climbing into the tens of millions of rows, the data itself eventually exceeds what a single primary machine can store and index efficiently, and writes — which still all go to that one primary — start slowing down as a direct consequence. This is a genuinely different constraint than anything solved so far: not too many requests, but too much data.

Why a growing index specifically slows writes down

Every insert into a table needs to update that table's indexes so future lookups stay fast. When an index is small enough to sit entirely in RAM, this update is nearly instant. Once the index grows past available memory, updating it starts requiring disk access — dramatically slower than memory access — and every single write now pays that cost. This is a specific, mechanical reason storage growth translates directly into write slowness, not just a vague "big data is slow" intuition.

Why read replicas were never going to solve this

A replica's entire purpose is holding a faithful, complete copy of the primary's data — that's what makes it useful for reads in the first place. Adding a fourth or fifth replica doesn't shrink the dataset each one has to hold; it just adds another machine storing the exact same growing volume. This is worth stating plainly: replication and the storage-ceiling problem are almost entirely orthogonal — solving one genuinely does nothing for the other.

What's actually needed: splitting the data itself, not just the traffic

Every fix so far has added more machines to share work — more app servers sharing requests, more replicas sharing reads. What Chirp needs now is fundamentally different: more machines each holding a portion of the data, so no single machine needs to store or index the entire dataset alone. That's the idea the next page introduces.
