6.2 The fix: sharding Chirp's data

Instead of one database holding everyone, eight databases each holding an eighth of everyone — and a rule for knowing exactly which eighth.

"Split users and their posts across 8 shards, keyed by user ID. Each shard is now a fifth the size it would've been on one server, and write latency is back to normal. The tricky part wasn't the sharding itself — it was making sure every single query knows which shard to look in." — you, post-migration notes
TL;DR
Sharding (or horizontal partitioning) splits one large dataset across multiple independent databases, each holding only a portion of the total data. A shard key — Chirp uses user_id — deterministically decides which shard any given piece of data lives on, so the application always knows exactly where to look without having to search every shard. This directly solves 6.1's storage ceiling: each shard now only needs to store and index a fraction of the total dataset, restoring fast writes.

The simplest sharding scheme, and its very real problem

def get_shard(user_id, num_shards=8):
    return user_id % num_shards  # simplest possible approach

Modulo-based sharding is genuinely simple and works — until the number of shards ever needs to change. Going from 8 shards to 9 changes the result of user_id % num_shards for the overwhelming majority of existing user IDs, meaning nearly every piece of data would need to be physically moved to a different shard just to add one more machine. This is a real, serious problem for a system that fully intends to keep growing — and it's exactly what the next page's deep dive on consistent hashing solves properly.

Why user_id specifically, and not something else

Chirp's most common queries — "get this user's posts," "get this user's feed," "update this user's profile" — are almost all naturally scoped to one user. Choosing user_id as the shard key means the overwhelming majority of real queries only ever need to touch one shard, which is exactly what makes sharding pay off cleanly. Choosing a poor shard key — something that doesn't align with how data is actually queried — can force many queries to check every shard, which erases most of sharding's benefit. This choice is worth taking seriously and is very hard to change later.

What sharding costs, honestly

Every shard is now its own independent database with its own connection pool, its own replicas (Chapter 5's fix still applies — each shard can have its own read replicas), and its own operational overhead. Cross-shard operations — anything that needs data from more than one shard at once — become genuinely harder, a cost this chapter is about to make very concrete in 6.4.

Check your understanding

1. Why does sharding by user_id directly solve 6.1's storage ceiling problem?
This is the direct mechanism — splitting the data itself (not just adding copies of it) is what actually reduces the per-machine storage and indexing burden.
2. What's the specific, serious problem with simple modulo-based sharding (user_id % num_shards)?
This specific fragility — around growing or shrinking the shard count — is exactly what consistent hashing (next page) is designed to solve.
3. Why does choosing the right shard key matter so much for whether sharding actually pays off?
This is a genuinely consequential design decision — the shard key needs to match real query patterns, and it's specifically flagged as hard to change once data is already distributed by it.
