12.4 Design Uber's dispatch system

Not a Chirp feature this time — a genuinely different domain, testing whether the underlying toolkit actually transfers to a problem shaped nothing like a social app.

TL;DR
Requirements: match riders to nearby available drivers, track live driver locations, handle constant location updates efficiently. The central new challenge is geospatial indexing — finding "drivers near this point" is a fundamentally different query shape than anything in Chirp's story, and a normal database index (11.5) doesn't handle 2D proximity well at all. Geohashing solves this by encoding latitude/longitude into a string where nearby locations naturally share string prefixes, turning a proximity search into a fast prefix lookup — the same underlying instinct as an inverted index (11.5), applied to physical space instead of text.

Why constant location updates are exactly Chapter 7's problem, relocated

Every active driver's app sends a location update every few seconds — at scale, this is a genuinely massive write volume, structurally identical to Chapter 7's realization that some work doesn't need to happen synchronously. Location updates flow through a message queue (7.2's pattern exactly) into a fast-write-optimized store (11.4's wide-column type is a natural fit here, given the write-heavy, simpler-query shape), rather than blocking anything on the critical matching path.

The deep-dive: matching as a multi-objective, not just "nearest"

A naive design matches the geographically closest driver — but a real system weighs multiple factors: driver rating, current trip completion time, fairness (avoiding always picking the same top driver), and surge pricing zones. This is worth naming explicitly as a real, additional layer of complexity beyond pure proximity search — the geospatial index narrows candidates to "nearby drivers," and a separate scoring step picks the actual best match among those candidates.

Consistency requirements here look different from Chirp's

Recall 11.3's CAP/PACELC framework: a social feed can tolerate serving slightly stale data (Chirp's actual choices throughout this track). A ride match generally can't — two riders being matched to the same driver simultaneously is a genuinely bad outcome, not a minor inconsistency. This pushes dispatch's core matching decision toward favoring consistency, even at some latency cost, a different point on the same trade-off spectrum Chirp navigated differently throughout its own story.
