12.5 Design a rate limiter

Chapter 11.2 covered the algorithms. This is the harder question interviewers actually ask next: where does the counter live when there are 8 app servers, not 1?

TL;DR
Requirements: limit each user (or API key) to N requests per time window, enforced correctly across every one of Chirp's app servers (Chapter 3) — not per-server, which would let a user get N times the intended limit just by having requests spread across the load balancer. This means the token bucket's state (11.2) can't live in any single app server's local memory — exactly Chapter 3.4's statelessness lesson, applied to rate limiting specifically: the counter needs to live in a shared, fast store every app server can check and update atomically.

Try it: watch a distributed counter stay correct across servers

Why Redis specifically, and the atomicity requirement

Redis is the natural fit — it's already Chirp's shared, fast key-value store (Chapter 4), and critically, it supports atomic increment operations. Atomicity matters precisely because two app servers could receive requests from the same user at nearly the same instant; without an atomic "increment and check" operation, both servers could read the counter as "9 of 10 used," both allow the request, and the user ends up making 11 requests against a limit of 10 — a classic race condition this design has to specifically prevent.

Where to enforce it: API gateway vs. each individual service

Recall Chapter 8's service split — should rate limiting live in a central API gateway (one place, consistent enforcement, but a potential bottleneck of its own) or in each individual service (more resilient to the gateway itself failing, but duplicated logic and configuration across every service)? Most real systems choose the gateway for user-facing limits and add service-level limits specifically for internal protection — directly echoing 10.2's point that rate limiting protects against internal traffic storms too, not just external abuse.

The response contract: telling the client what happened

A rate-limited request should return 429 Too Many Requests (11.1's status code conventions) along with a Retry-After header telling the client exactly how long to wait — letting a well-behaved client back off intelligently instead of immediately retrying and making the situation worse, which connects directly back to 10.2's concern about retry storms.
