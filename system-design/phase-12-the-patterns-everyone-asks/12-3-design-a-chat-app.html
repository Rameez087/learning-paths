12.3 Design a chat app

Chirp added DMs. Unlike a feed, this needs a persistent, two-way connection — a genuinely different networking model than anything built so far.

TL;DR
Requirements: real-time one-on-one and group messaging, delivery confirmation, message ordering. HTTP request-response (used everywhere else in this track) doesn't fit — there's no "request" when a message needs to arrive the instant it's sent. WebSockets provide a persistent, two-way connection between client and server, letting the server push a message the moment it arrives rather than waiting for the client to ask. This is exactly Chapter 3.3's IP-hash/sticky-session scenario, but now it's not just useful — it's required: a user's WebSocket connection has to stay pinned to one specific server for its entire duration.

Try it: compare delivery guarantee strategies

Why chat specifically breaks the stateless assumption from Chapter 3.4

Recall Chapter 3.4's fix: making app servers stateless so any server can handle any request. A WebSocket connection genuinely can't work that way — the connection itself is a stateful, long-lived link to one specific server. The practical resolution: the connection is sticky to one server, but the actual message data and delivery state still live in a shared store (11.4's key-value pattern), so if that specific server goes down, the user simply reconnects to a different one and picks up their message history from the shared store.

The deep-dive: message ordering across a distributed system

Two messages sent close together need to display in the order they were actually sent, even if they're processed by different servers or arrive slightly out of order over the network. The practical fix: assign each message a sequence number (or a precise timestamp with a tiebreaker) at the point it's accepted by the system, and have clients sort by that sequence number rather than trusting network arrival order — a specific, concrete instance of the coordination challenges named abstractly in 11.6.

Delivery guarantees: read receipts as a specific idempotency problem

"Delivered" and "read" receipts need the exact same at-least-once-delivery handling from Chapter 7.3 — a receipt message might be delivered twice due to a network retry, and the UI needs to handle a duplicate "read" event gracefully (setting a boolean to true twice is actually naturally idempotent here, a helpful case where the operation's own nature avoids needing extra deduplication logic).

Check your understanding

1. Why does a chat app require WebSockets instead of the standard HTTP request-response pattern used elsewhere in Chirp?
This is the core networking-model shift this topic introduces — genuinely real-time push delivery needs a different connection model than request-response.
2. How does chat's need for sticky WebSocket connections get reconciled with Chapter 3.4's statelessness principle?
This shows how a genuine exception to an earlier principle (statelessness) gets handled thoughtfully rather than simply ignored — the stateful part is minimized and isolated.
3. Why is "read" receipt handling described as naturally idempotent, unlike the double-notification bug from Chapter 7.3?
This is a subtle but genuine distinction — some operations are naturally idempotent by their own definition, while others (like sending a notification) require deliberate deduplication logic to become safe against redelivery.
