12.1 Design a URL shortener

The "hello world" of system design interviews — and a genuinely good test of whether you reach for Chirp's actual toolkit or overcomplicate a fundamentally simple problem.

TL;DR
Requirements: given a long URL, generate a short, unique code (chirp.ly/a8F3k1) that redirects to it; reads (redirects) vastly outnumber writes (new short URLs), the same read-heavy shape as Chapter 4.1. Core design: a key-generation service produces unique short codes (base62-encoded, avoiding predictable sequential IDs), stored in a key-value database (11.4) mapping short code → long URL, with Chapter 4's caching in front for the hot redirects, and a CDN-adjacent edge layer for genuinely global low-latency redirects (Chapter 9's pattern).

Try it: generate a short code from base62 encoding

Why base62 encoding, specifically

A monotonically increasing integer ID (from a database auto-increment, or a distributed ID generator) is simple to guarantee unique — but encoding it directly in decimal would make URLs unnecessarily long. Base62 (using 0-9, a-z, A-Z — 62 characters) packs the same unique number into far fewer characters: a 6-character base62 string can represent over 56 billion unique values, comfortably covering realistic scale while staying short and shareable.

The deep-dive: avoiding a single point of ID generation, Chapter 6's lesson applied

A single database auto-increment column is simple but becomes exactly Chapter 6.1's storage and write-throughput bottleneck at real scale, and Chapter 2's single point of failure risk. The practical fix mirrors Chapter 6.2 directly: pre-allocate blocks of IDs to different servers (server A gets IDs 1-1000, server B gets 1001-2000), so ID generation itself is sharded and doesn't require a single coordinated counter for every single request.

Trade-offs worth stating explicitly (the "Evaluate" step from 11.8)

  • Sequential vs. random short codes: sequential IDs are simpler but let anyone guess how many URLs exist and enumerate them; random codes need a collision check but avoid this leak.
  • Custom aliases: supporting user-chosen short codes ("chirp.ly/my-launch") means checking availability against the same key-value store — directly reusing 11.5's bloom-filter-as-cheap-gatekeeper pattern.
  • Redirect type: a 301 (permanent) redirect lets browsers cache it, reducing load but making click analytics harder to track; a 302 (temporary) redirect hits the server every time, the opposite trade-off.

Check your understanding

1. Why does base62 encoding produce a much shorter URL than encoding the same numeric ID in decimal?
This is the direct mathematical reason — more possible symbols per position means fewer positions needed to represent the same range of values.
2. Why does a single database auto-increment column for ID generation become a real problem at scale, and what earlier chapter's fix applies?
This is the whole point of Phase 12 — applying the track's actual toolkit to a new named problem, rather than treating it as an unrelated fresh challenge.
3. What's the real trade-off between using a 301 versus a 302 redirect for a shortened URL?
This is a genuine, real product trade-off — caching efficiency versus analytics visibility, with no universally correct answer.
