12.6 Design search autocomplete

Closing the loop on Chapter 6.4's cross-shard search problem — and a genuinely different data structure than anything used so far.

TL;DR
Requirements: as a user types, suggest completions in real time (under ~100ms), ranked by popularity. This isn't the same problem as 11.5's inverted index (finding documents containing a word) — it's specifically about efficiently finding all known terms that start with a given prefix. A trie (prefix tree) is the natural fit: each node represents one character, and walking down the tree following the typed characters lands exactly on the branch containing every valid completion — turning "find all terms starting with 'chi'" into a single tree traversal instead of scanning anything.

Try it: walk a trie character by character

Why this finally, honestly resolves 6.4's cross-shard search problem

Recall Chapter 6.4 explicitly deferring this: scatter-gather search across every shard doesn't scale, and the real fix was "a separate, purpose-built search index." This is that fix, made concrete: a dedicated trie (or a similar prefix structure) built and maintained independently of Chirp's sharded transactional database, updated asynchronously (Chapter 7's pattern) as new popular search terms emerge, rather than querying the actual sharded post data on every keystroke.

The deep-dive: ranking suggestions, not just finding them

A trie efficiently finds all valid completions, but showing the top 5 by actual popularity requires each node to also track aggregate popularity of everything beneath it — precomputed and cached (Chapter 4's caching principle, applied to a different data structure) rather than calculated fresh on every keystroke, since recomputing popularity rankings in real time for every character typed would reintroduce exactly the kind of unnecessary repeated work Chapter 4.1 originally solved.

Keeping suggestions fresh without querying live data

Popular search terms change over time — a background job (Chapter 7's async workers again) periodically rebuilds or updates the trie from recent search logs, rather than the trie being perfectly real-time accurate. This is the same acceptable-staleness trade-off from Chapters 4.2 and 5.2, applied once more: slightly-stale suggestions are a fine trade for consistently fast response times on every keystroke.
