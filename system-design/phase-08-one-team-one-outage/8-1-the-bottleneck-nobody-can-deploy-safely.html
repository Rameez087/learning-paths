8.1 The bottleneck: nobody can deploy safely

Chirp has 40 engineers now. A one-line fix to the notification-preferences page just took down the entire feed for six minutes.

⚠ Alert
A deploy touching only notification settings code caused a full outage — an unrelated import error at module load time crashed the entire application process, taking every feature down simultaneously, not just notifications.
"This is the fourth time this quarter an unrelated bug has taken down something completely different. We have 40 engineers now, all deploying the exact same codebase, and every single deploy is a bet that nobody's change — anywhere in this enormous application — breaks anything else." — you, in the incident retro
TL;DR
Chirp is now one large application (a monolith) with dozens of engineers all committing to the same codebase and deploying the same single artifact together. This creates a specific, organizational bottleneck distinct from every earlier chapter: it's not that any machine lacks capacity, it's that the codebase itself has become the constraint — a bug in notification code can crash the feed, a slow database migration for one feature blocks deploying an unrelated bug fix, and every team's changes are coupled to every other team's changes purely by living in the same process.

Why this bottleneck is organizational, not just technical

Every earlier chapter's bottleneck was purely a machine running out of some resource — CPU, connections, storage. This one is different: the actual constraint is how many people can safely make changes to one shared codebase at once without stepping on each other. A team might have a perfectly correct, well-tested change ready to ship, and still be blocked because someone else's unrelated, in-progress change is currently causing test failures on the shared main branch.

Why this problem didn't exist at Chapter 1's scale

With one or two engineers, coordination overhead is nearly invisible — everyone roughly knows what everyone else is working on. As team size grows, the number of possible ways one person's change can interact badly with another's grows much faster than the team size itself. This is exactly why this bottleneck appears specifically around the 10 million user mark for Chirp — not because of user count directly, but because reaching that scale realistically requires the larger engineering team whose size is the actual cause.

What the fix needs to actually solve

The goal isn't simply "write better tests" or "review code more carefully" — those help, but don't address the structural issue: unrelated features are coupled together purely by sharing one process and one deploy. What's needed is a way for different parts of Chirp to be built, tested, deployed, and — critically — allowed to fail independently of each other.
