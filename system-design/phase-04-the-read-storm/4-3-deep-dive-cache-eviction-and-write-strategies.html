4.3 Deep dive: cache eviction & write strategies

Redis has finite memory. When it fills up, something has to be thrown out — the question is what, and getting it wrong quietly undoes most of caching's benefit.

TL;DR
Eviction policies decide what to remove when a cache is full: LRU (Least Recently Used — evict whatever hasn't been touched in the longest time) is the most common default, and it works because access patterns are rarely uniform — some content stays genuinely popular. Separately, write strategies decide how the cache stays in sync with the database when data changes: write-through (update both at once, safer but slower), write-behind (update the cache immediately, database later, faster but riskier), and cache-aside (4.2's pattern — the application manages both explicitly).

Try it: watch LRU eviction in action

Why LRU specifically, and not "just evict randomly"

LRU exploits a genuinely common real-world pattern called temporal locality: something accessed recently is disproportionately likely to be accessed again soon. A user who just refreshed their feed will probably refresh it again within the next minute; a user who hasn't opened Chirp in three days probably won't in the next thirty seconds either. Evicting the least-recently-used entry specifically protects the entries most likely to be requested again, which random eviction wouldn't do any better than chance.

Write-through vs. write-behind: the actual trade-off

Write-through updates the cache and the database in the same operation, before confirming success to whoever made the write — slower per write, but the cache is never out of sync with the database, even for a moment. Write-behind updates the cache immediately and writes to the database asynchronously, shortly after — faster writes, but a real window exists where a crash between the two steps could lose the write entirely. For something like a new Chirp post, that risk is usually unacceptable; for a less critical metric like a view counter, it's often a perfectly reasonable trade.

Why Chirp's feed cache uses cache-aside, not write-through

Chirp's feed cache doesn't get directly written to when a new post is created — instead, it simply expires after 60 seconds (4.2) and gets recomputed fresh on the next request. This is the cache-aside pattern: the application, not the cache infrastructure itself, decides when to read from cache, when to fall through to the database, and when to let old entries expire naturally. It's simpler to reason about than keeping every cache entry perfectly synchronized on every single write — at the direct cost of exactly the staleness window the next chapter is about to make painfully visible.

1. Why does LRU eviction generally outperform random eviction for a cache like Chirp's?
This is the specific real-world pattern (temporal locality) that makes recency a genuinely useful signal for predicting future access, rather than an arbitrary heuristic.
2. What real risk does write-behind caching introduce that write-through avoids?
This is a genuine, real trade-off — faster writes in exchange for a real (if often small) window of data-loss risk, which is why the choice depends on how critical the specific data actually is.
3. Why does Chirp's feed cache use expiration-based cache-aside rather than actively updating the cache on every new post?

This deep dive reflects standard, durable caching theory (LRU/LFU eviction, write-through/write-behind/cache-aside patterns) consistent across Redis, Memcached, and most production caching systems.
