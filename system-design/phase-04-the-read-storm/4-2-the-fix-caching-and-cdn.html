4.2 The fix: caching & CDN

Remember the answer instead of recomputing it. That's the entire idea — the details are in exactly how and where to remember it.

"Added Redis in front of the database for feed queries. Database CPU dropped from 88% to 19% almost immediately. Also moved profile pictures and post images to a CDN — those were never supposed to be hitting our server directly in the first place." — you, deploy notes
TL;DR
A cache (Redis, in Chirp's case) sits between the app servers and the database, storing the results of expensive, frequently-repeated queries in fast memory. When a feed is requested, the app checks the cache first — if the answer is there ("a cache hit"), it returns instantly without touching the database at all. Only on a miss does it fall through to the real database, then stores that result in the cache for next time. A CDN (Content Delivery Network) does something related but different: it caches static files (images, videos, CSS) at servers physically distributed close to users worldwide, so a user in Tokyo doesn't fetch a profile picture from a server in Virginia every single time.

The cache-aside pattern, in code

def get_feed(user_id):
    cache_key = f"feed:{user_id}"
    cached = redis.get(cache_key)
    if cached is not None:
        return cached  # cache hit — database never touched

    # cache miss — compute the real answer
    feed = database.query_feed(user_id)
    redis.set(cache_key, feed, expire_seconds=60)  # remember it briefly
    return feed

The expire_seconds=60 matters more than it looks: it's a deliberate choice about how stale a cached feed is allowed to get before being recomputed. Sixty seconds means a feed might be up to a minute out of date — an acceptable trade-off Chirp is choosing deliberately, not an accident.

Why CDN is a genuinely separate idea from application caching

Redis caches the results of database queries — dynamic, personalized data that changes per user. A CDN caches static files that are identical for everyone — the same profile picture, the same uploaded video, regardless of who's requesting it. This difference is why they're different pieces of infrastructure solving genuinely different problems, even though both are colloquially called "caching."

What this fix doesn't do

Caching is a genuine, major win — but it's a mitigation for read load, not a solution to every future database problem. The database still holds the actual source of truth, still handles every write, and still needs to answer every cache miss. Chapters 5 and 6 pick up exactly where this leaves off — what happens as the underlying dataset itself keeps growing, independent of how well reads are cached.
