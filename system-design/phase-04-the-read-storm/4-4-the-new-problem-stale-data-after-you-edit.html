4.4 The new problem: stale data after you edit

"I deleted an embarrassing typo from my post 10 seconds ago. It's still showing the typo. Is this app broken?"

"Getting a weird spike of tickets — people editing or deleting posts and still seeing the old version for up to a minute afterward. Nothing's actually broken, but try explaining 'cache expiration window' to a confused user." — support lead
TL;DR
This is 4.2's 60-second cache expiration, showing up exactly where it was always going to: a user edits or deletes a post, the database updates instantly and correctly, but their cached feed — computed just before the edit — doesn't know that yet, and won't be recomputed until it naturally expires. This is cache invalidation: the general problem of making a cache reflect a change the moment it happens, rather than waiting for a timer. Famously called one of the two genuinely hard problems in computer science for a reason — it's a real, recurring tension, not a bug to casually patch out.

Try it: watch the staleness window play out

Why this specific trade-off is a real, deliberate choice — not an oversight

4.2's 60-second expiration was chosen precisely because most feed content doesn't need to be correct to the millisecond — a slightly stale view of other people's posts is a fine trade-off for a much lighter database. The problem is that "slightly stale" includes the exact case a user notices most: their own recent edit, which they know should already be reflected because they just made it themselves. The trade-off was reasonable in aggregate; it's just visible in one specific, emotionally noticeable case.

The fix: active invalidation for the cases that actually matter

Rather than shortening the expiration window for everyone (which would bring back much of 4.1's original database load), Chirp adds targeted active invalidation: the moment a user edits or deletes their own post, the application explicitly clears that specific user's cached feed entry immediately, rather than waiting for the 60-second timer. The next request for their feed becomes a guaranteed cache miss, forcing a fresh, correct read — but only for the one case that actually needs immediate correctness, leaving the broader 60-second window intact for everything else. 

def edit_post(post_id, user_id, new_content):
    database.update_post(post_id, new_content)
    redis.delete(f"feed:{user_id}")  # invalidate immediately, don't wait for expiry
    # anyone who follows this user will still see the stale
    # version briefly — a smaller, separately accepted trade-off

Why this doesn't fully solve the problem — and why that's the honest answer

Invalidating the editor's own cache fixes the most emotionally sharp case, but anyone who follows that user still sees a stale cached version of their feed until it naturally expires — invalidating every follower's cache on every edit would reintroduce exactly the database load problem this chapter exists to solve. This is the genuinely honest shape of cache invalidation: there's rarely a fix that's both instantly correct for everyone and cheap — only better and worse places to draw the line based on which staleness actually hurts most.
