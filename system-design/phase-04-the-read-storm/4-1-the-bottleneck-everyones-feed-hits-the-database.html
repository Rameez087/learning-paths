4.1 The bottleneck: everyone's feed hits the database

Four app servers fixed the capacity problem. Now the database — still just one machine — is the thing quietly running out of room.

⚠ Alert
Database CPU sits at 88% sustained, not just during spikes. The single most frequent query — "get the 20 most recent posts from people I follow" — now runs an average of 340 times per second and accounts for roughly 70% of total database load.
"The app servers are fine — barely breaking a sweat. It's the database. Every single person who opens Chirp triggers the exact same expensive query, just with a different user ID." — you, looking at query stats
TL;DR
Four app servers successfully spread out the application work (Chapter 3), but every one of those servers still ultimately asks the same single database to do the same expensive read — computing a personalized feed — over and over, for every user, on every refresh. The database has become the new bottleneck precisely because the app layer got faster at generating requests for it to serve. This is a specific, common pattern: fixing one bottleneck routes more traffic into whatever's next in line.

Why this is fundamentally a read problem, not a write problem

Chirp's users post far less often than they scroll — a typical user might create one post a day but refresh their feed dozens of times. This is an extremely common, almost universal pattern in real applications: reads vastly outnumber writes. It matters here specifically because it points toward a very targeted fix — one that speeds up repeated, identical reads without needing to touch how writes work at all.

Why more read replicas of the database isn't (yet) the obvious answer

A tempting first instinct is Chapter 2's playbook again — add more database capacity. But notice what's actually being computed here: the exact same feed query, for popular combinations of followed accounts, gets run again and again within seconds of the previous identical run. Paying to recompute an answer that hasn't changed since the last time it was computed is wasteful in a way that adding more database horsepower doesn't actually solve — it just makes the waste faster.

What would actually help: not recomputing what hasn't changed

If a feed's answer was already computed 400 milliseconds ago and nothing in it has changed since, the database shouldn't need to redo that work at all — something should just remember the answer and hand it back. This is the exact shape of problem caching exists to solve, and it's what the next page introduces.

Check your understanding

1. Why did the database become the bottleneck specifically after Chapter 3's load balancing fix, rather than before it?
This is a genuinely common pattern worth naming explicitly — solving a bottleneck at one layer often reveals (or worsens) a bottleneck at the next layer downstream.
2. Why does the fact that "reads vastly outnumber writes" matter for choosing the right fix here?
Recognizing the workload's actual shape (read-heavy) is what makes the eventual fix well-targeted rather than a generic "add more resources" response.
3. Why is simply adding more database capacity described as making "the waste faster" rather than solving the real problem?
This distinction — treating the symptom (not enough capacity) versus the actual cause (unnecessary repeated computation) — is exactly what motivates caching as the targeted fix on the next page.
