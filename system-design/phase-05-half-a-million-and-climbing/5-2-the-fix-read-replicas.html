5.2 The fix: read replicas

One database for writes. Several copies, kept in sync automatically, just for reads.

"Spun up 3 read replicas this week. Writes still go through the primary exclusively — reads get spread across the replicas. Primary's CPU dropped from 92% to 31%." — you, infra notes
TL;DR
A read replica is a continuously-updated copy of the primary database, receiving a stream of every change the primary makes and applying them locally — replication. All writes still go to exactly one primary database (avoiding 5.1's write-consistency problem entirely), but reads now get distributed across the primary plus however many replicas exist. This is horizontal scaling (Chapter 3's core idea) applied to the database layer instead of the app layer — more machines sharing the read workload, rather than one bigger machine trying to absorb all of it.

How replication actually works, mechanically

The primary database records every write as an entry in a sequential log (Postgres calls this the write-ahead log). Each replica continuously streams and replays that log, applying the same changes in the same order the primary made them — effectively "replaying" the primary's history to stay in sync. This streaming happens asynchronously by default: the primary doesn't wait for a replica to confirm it received an update before considering the write complete.

Why "asynchronous by default" is a deliberate, named choice

The alternative — synchronous replication, where the primary waits for at least one replica to confirm receipt before acknowledging a write as successful — genuinely guarantees replicas are never behind, at the direct cost of every write becoming slower (it now has to wait on a network round trip to at least one other machine). Chirp chooses asynchronous replication specifically because write speed matters more here than replica freshness — a trade-off worth stating explicitly, since it's about to have a very visible consequence.

How the application knows where to send each query

def get_feed(user_id):
    # reads: route to any available replica
    return replica_pool.query("SELECT ... FROM posts WHERE ...")

def create_post(user_id, content):
    # writes: always go to the primary, never a replica
    return primary_db.execute("INSERT INTO posts ...")

This read/write split needs to be explicit in the application code (or handled by a proxy layer that does it automatically) — nothing about a "database" inherently knows which of its copies should receive which type of query. Getting this routing wrong (accidentally sending a write to a replica) either fails outright or silently doesn't do what was intended, depending on how the replica's permissions are configured.

Check your understanding

1. Why do all writes still go to exactly one primary database, even after adding read replicas?
This directly resolves 5.1's setup — the fix deliberately keeps the write side simple (one source of truth) while only distributing the read side, which is the part that actually needed to scale.
2. What does choosing asynchronous replication over synchronous replication trade away, and what does it gain?
This is a genuinely real, deliberate trade-off — and naming it explicitly here is exactly what sets up the next page's bug as a predictable consequence, not a surprise.
3. Why must the application code (or a proxy layer) explicitly decide whether a query goes to the primary or a replica?
This is a practical detail worth taking seriously — read/write routing is an explicit responsibility, not something that happens automatically just because replicas exist.
