New Problem

5.3 The new problem: "I just posted but can't see it"

A user posts, immediately refreshes to make sure it worked, and — for a fraction of a second — sees nothing. Then refreshes again and it's there.

"Getting scattered reports of posts 'disappearing' right after being made, then reappearing seconds later. Nothing's actually lost — I checked the primary directly, the post's there instantly. It's specifically the read replicas that are a beat behind." — you, investigating
TL;DR
This is 5.2's asynchronous replication trade-off, now visible to real users. The primary database has the new post the instant it's written. But the load balancer might route the user's very next read (checking that their post succeeded) to a replica that hasn't caught up yet — replication lag, usually just milliseconds, but non-zero. This specific scenario — reading your own just-made write and not seeing it — has a name: read-after-write consistency, and it's one of the most common, most user-visible symptoms of asynchronous replication anywhere it's used.

Try it: watch the lag window in real time

Why this specific bug is worse than 4.4's stale-cache problem, psychologically

4.4's staleness was about seeing an old version of content. This is different and sharper: the user's action appears to have failed, even though it actually succeeded instantly. A user who just posted and sees nothing reasonably wonders if they need to post again — and a duplicate post from an anxious retry is a real, avoidable consequence of not handling this case deliberately.

The fix: route a user back to the primary for their own recent writes

A specific, targeted pattern: immediately after a user writes something, route their next few reads back to the primary database (which always has the latest data) instead of a replica, for a short window — often just a few seconds, or until their session's known "last write" timestamp is confirmed to have propagated. Everyone else's reads still go to replicas as normal; only the person whose own action needs to be immediately, reliably visible gets the special treatment. 

def get_feed(user_id, session):
    if session.get("last_write_at") and time_since(session["last_write_at"]) < 5:
        # user wrote something in the last 5 seconds — read their own
        # data from the primary to guarantee they see it
        return primary_db.query_feed(user_id)
    return replica_pool.query_feed(user_id)  # normal case: any replica is fine

Why this doesn't need to apply to every read, everywhere

Routing every single read to the primary "just to be safe" would completely undo Chapter 5.2's fix — the primary would immediately become the bottleneck again, exactly as in 5.1. The targeted version only protects the one specific case that actually matters: a user checking on their own extremely recent action. Everyone reading everyone else's older content is entirely unaffected by lag windows measured in milliseconds, and keeps getting served by replicas as intended.

The pattern this chapter reinforces, one more time

Same shape as 4.4: a real, deliberate trade-off (asynchronous replication for write speed) produces a real, narrow edge case (a user briefly not seeing their own write) that gets a targeted fix rather than reversing the original trade-off wholesale. This specific discipline — protect the one case that hurts, without undoing the broader win — is going to keep showing up for the rest of this track.
