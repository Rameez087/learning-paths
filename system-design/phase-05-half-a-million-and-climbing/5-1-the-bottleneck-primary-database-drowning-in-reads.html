5.1 The bottleneck: primary database drowning in reads

Caching bought real headroom. Half a million users later, even a 90%+ cache hit rate isn't enough — because the 10% that misses has gotten enormous in absolute terms.

⚠ Alert
Cache hit rate holds steady at 91% — the caching layer is working exactly as designed. But at current volume, that remaining 9% of requests still represents over 4,500 database reads per second, and the single primary database is once again running hot.
"This one's frustrating because nothing's actually wrong. Cache hit rate looks great on the dashboard. But 9% of a much bigger number is still a big number, and it's all landing on one database." — you, looking at the metrics
TL;DR
Caching (Chapter 4) reduced the percentage of requests hitting the database, not the absolute ceiling of how many the single database can handle. As Chirp's total traffic keeps growing, the same 9% cache-miss rate translates into a steadily larger raw number of database reads — and that number has now caught back up to the primary database's real capacity. This is a specific, recurring shape in this track: a fix reduces a problem's rate, but growth eventually outpaces even a reduced rate.

Why this bottleneck feels different from Chapter 4.1's

Chapter 4's problem was redundant work — the same answer, recomputed unnecessarily, over and over. This one is different: every single one of these database reads is a genuinely unique request, for genuinely different data, that caching correctly identified as not reusable. There's no wasted computation to eliminate here — the database is being asked to do real work, just more of it than one machine can keep up with. This distinction matters because it rules out "add more caching" as the fix; the problem this time is real, unavoidable read volume.

Why one primary database is a genuine structural limit here

Vertical scaling the primary database (Chapter 2.3's playbook) can push this ceiling higher, but it's the same cost curve and hard limit from before — a temporary reprieve, not a lasting fix. What's actually needed is a way to serve more simultaneous reads without asking one machine to answer all of them itself — while still keeping exactly one authoritative place where writes happen, since having multiple databases independently accepting writes to the same data would create a much harder consistency problem than the one currently being solved.
