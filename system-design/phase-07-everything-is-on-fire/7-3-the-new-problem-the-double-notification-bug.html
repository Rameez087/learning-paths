7.3 The new problem: the double-notification bug

"Why did I get notified twice that the same person liked my post?" A support ticket that seems trivial and is actually pointing at a genuinely deep distributed systems problem.

"Investigated the duplicate notification reports. Here's what's happening: a worker picks up a message, starts processing it, and right before it finishes and acknowledges completion — it crashes. The queue, having never received that acknowledgment, assumes the job failed and redelivers the exact same message to a different worker. Which then sends the notification again." — you, in the postmortem doc
TL;DR
Message queues make a deliberate, honest choice here: when in doubt about whether a message was actually processed, redeliver it rather than risk silently losing it. This is called at-least-once delivery, and it's the practical default nearly every real message queue uses — the alternative (guaranteeing exactly-once delivery in a distributed system) is a famously, genuinely hard problem, not a solved one any queue can promise for free. The consequence: any worker needs to be written assuming it might receive and process the exact same message more than once.

Try it: make the notification worker idempotent

Idempotency: the fix, and the word worth knowing precisely

An operation is idempotent if running it multiple times produces the exact same result as running it once. "Set the account balance to $500" is idempotent — running it five times leaves the balance at $500. "Add $50 to the account balance" is not — running it five times adds $250. The notification worker's bug is exactly this: sending a notification is not naturally idempotent, so redelivery causes a real, visible duplicate.

The fix in code: a deduplication check before acting

def process_notification(message):
    idempotency_key = message["notification_id"]  # unique per logical notification

    if redis.exists(f"processed:{idempotency_key}"):
        return  # already handled — this is a redelivery, safely ignore it

    send_push_notification(message["user_id"], message["content"])
    redis.set(f"processed:{idempotency_key}", True, expire_seconds=86400)

This makes the worker safe to run against the same message any number of times — the first delivery sends the notification and records that it did; every subsequent redelivery of that same logical message checks the record, sees it's already handled, and does nothing further.

Why this same idea already showed up once, and will again

Recall webhook handling from earlier system design thinking, and idempotent API design more broadly (this gets its own full treatment in Phase 11's toolbox) — "handle duplicate delivery safely" is a recurring requirement anywhere at-least-once delivery is the honest default, which is most distributed messaging in practice. Recognizing this pattern once means recognizing it everywhere it reappears, rather than treating each instance as a brand-new problem.

Why "just guarantee exactly-once" isn't the actual fix

It's tempting to wish the queue itself would simply guarantee each message is delivered exactly once, eliminating the need for this workaround entirely. In practice, true exactly-once delivery across a genuinely distributed system (where networks can fail, machines can crash mid-operation) is not something any real system can honestly promise for free — building idempotent consumers is the practical, honest way production systems actually achieve the same user-visible outcome (no duplicates) without pretending the underlying distributed-systems problem doesn't exist.

Check your understanding

1. Why do message queues default to at-least-once delivery instead of guaranteeing exactly-once?
This is an honest engineering trade-off, not an oversight — choosing to occasionally over-deliver rather than risk silently losing a message reflects a real, deliberate design philosophy.
2. Why is "add $50 to the account balance" not idempotent, while "set the account balance to $500" is?
This is the precise definition at work — idempotency is about whether repeated execution changes the outcome beyond the first execution, which is exactly what distinguishes these two operations.
3. Why is building idempotent consumers described as the practical, honest fix rather than a workaround to eventually replace?
This is a durable, foundational distributed-systems reality, not a stopgap — idempotency at the consumer level is how production systems genuinely and honestly handle at-least-once delivery's implications.
