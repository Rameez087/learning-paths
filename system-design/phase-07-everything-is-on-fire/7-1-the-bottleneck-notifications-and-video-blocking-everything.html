7.1 The bottleneck: notifications and video blocking everything

Chirp added video posts last quarter. A user uploads a 30-second clip — and the app server that received the upload sits there, doing nothing else, for 4 full seconds while it processes it.

⚠ Alert
p99 latency on the post-creation endpoint has climbed to 3.8 seconds — dominated entirely by video transcoding and notification fan-out happening synchronously, inside the same request that's supposed to just confirm "your post was created."
"A user uploads a video, and the request handling that upload doesn't return until we've transcoded it AND fanned out a notification to all their followers. One popular user posting a video ties up an app server thread for 4+ seconds doing work that has nothing to do with 'did the post save successfully.'" — you, staring at a flame graph
TL;DR
Some of Chirp's work genuinely doesn't need to happen before responding to the user — transcoding an uploaded video into multiple resolutions, sending push notifications to followers, generating a thumbnail — but it's currently all running synchronously, inside the exact same request-response cycle that's supposed to just confirm the post was saved. Every app server thread doing this slow work is a thread not available to handle anyone else's request in the meantime, which is a genuinely different bottleneck than anything sharding or caching addresses: it's not too much data or too many identical queries, it's requests taking far too long because they're doing work that was never actually urgent.

Why this specific problem didn't exist before video

A text-only post is nearly instant to save — a single fast database write, done. Video processing (transcoding to multiple resolutions and bitrates for different devices and connection speeds) is genuinely computationally expensive, taking seconds rather than milliseconds. Notification fan-out — writing a "new post" entry into every follower's notification feed — also scales with follower count, and for a popular account can mean touching millions of rows. Neither of these existed as a meaningful cost when Chirp was text-only; both arrived together as real product features with real, unavoidable computational weight.

The question that reveals the fix: does the user need to wait for this?

A user posting a video needs to know their post was accepted — that has to be fast. They do not need the transcoding or the notification fan-out to be done before seeing "post created" — they need those things to happen eventually, correctly, without blocking the confirmation they're actually waiting on. This distinction — what must complete before responding, versus what can happen afterward — is the entire design question the next page's fix is built around.
