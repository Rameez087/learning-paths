11.13 Log-based brokers vs. task queues

A correction, honestly stated: what Chapter 7.2 called a "message queue" is really a task queue. Here's the genuinely different alternative — and when Chirp would actually need it.

TL;DR
A task queue (SQS-style — what Chapter 7.2 actually built) hands each message to exactly one worker, which processes it and it's gone — perfect for "do this piece of work once." A log-based broker (Kafka-style) is a genuinely different structure: an ordered, durable, replayable log that multiple independent consumers can each read through at their own pace, each keeping their own position — none of them "consume" the message away from the others. The right choice depends on a specific question: does exactly one thing need to happen in response to this event, or might several different, decoupled things need to react to it, now or later?

Try it: pick the right tool for each Chirp scenario

Why Chapter 7.2's task queue was still the right call for that problem

Video transcoding and notification fan-out are genuinely single-purpose: one video gets transcoded once, by one worker; that's exactly what a task queue is built for, and reaching for Kafka there would have been unnecessary complexity. This isn't walking back 7.2's decision — it's naming precisely what was built, so the distinction is available when a genuinely different situation shows up.

Where Chirp would actually need a log-based broker

Imagine Chirp later wants an analytics pipeline tracking engagement trends, a fraud-detection system watching for suspicious posting patterns, and a search indexer keeping 12.6's autocomplete trie fresh — all three genuinely need to react to the exact same "new post created" event, independently, without knowing about each other or coordinating deploy schedules. A task queue can't do this cleanly (once one worker consumes the message, it's gone). A log-based broker handles it naturally: three consumer groups, each reading the same "new post" log independently, each at their own pace.

The replay property: the other genuinely distinct capability

Because a log-based broker retains messages for a configured period rather than deleting them on consumption, a brand-new consumer (say, a new analytics service launched next quarter) can read the entire recent history of "new post" events from the beginning — recovering data that existed before the consumer itself did. A task queue offers nothing like this; once a task is consumed, it's genuinely gone.
