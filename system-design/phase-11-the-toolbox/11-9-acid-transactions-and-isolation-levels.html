11.9 ACID transactions & isolation levels

Chirp never explicitly dealt with this — every fix so far sidestepped it. Here's the concept underneath "a database operation either fully happens or doesn't happen at all."

TL;DR
A transaction groups multiple operations so they succeed or fail as one unit. ACID names the guarantee: Atomicity (all-or-nothing), Consistency (the database moves between valid states), Isolation (concurrent transactions don't interfere), Durability (a committed transaction survives a crash). Isolation is the genuinely interesting one in practice — full isolation (Serializable) is expensive, so most real databases default to a weaker level (Read Committed or Snapshot Isolation) that allows certain rare anomalies in exchange for speed. Choosing an isolation level is choosing exactly which anomalies you're willing to risk.

Where Chirp actually needed this and quietly avoided it

Recall Chapter 6.2: sharding by user_id means a single user's data lives on one shard, so most of Chirp's operations only ever touch one shard — genuinely a transaction within a single database, handled by Postgres automatically. But "follow this user" updates two things at once: the follower's following-count and the followed user's follower-count — and after sharding, those two counts can live on different shards. This is exactly the multi-object, cross-shard problem that motivated Chapter 8.3's saga pattern: a true ACID transaction can't span two independent databases, so the saga's compensating-action approach is the practical answer when a single transaction genuinely isn't available.

Why "Serializable" is expensive enough that most systems avoid it by default

Serializable isolation guarantees transactions behave exactly as if they ran one at a time, in some order — the strongest, simplest-to-reason-about guarantee. Achieving it usually means either literally running transactions one at a time (fine for small, fast transactions; a throughput ceiling for anything else) or detecting conflicts and aborting one of two transactions that collide — meaning the application needs to handle retries. Most production systems default to Read Committed or Snapshot Isolation specifically because full serializability's throughput cost isn't worth it for the majority of operations, which don't actually need it.

The anomaly that's easy to miss: write skew

Two transactions each read the same data, each independently decide their own write is safe based on what they read, and both commit — producing a result neither transaction would have allowed if it had seen the other's write first. A classic example: two on-call engineers each check "is anyone else on call right now," each sees no one else, and both remove themselves — leaving nobody on call, even though the rule was "always at least one person." Snapshot Isolation, despite sounding strong, does not prevent this — only full Serializable isolation does.
