11.11 B-trees vs. LSM-trees

Chapter 6.1 described an index outgrowing RAM and slowing writes down. Here's exactly what's happening inside the database when that occurs — and the alternative design built specifically to avoid it.

TL;DR
B-trees (what Postgres, MySQL, and most relational databases use by default) update data in place — a write finds the exact right spot on disk and modifies it directly, keeping the tree balanced. LSM-trees (used by Cassandra, RocksDB, and most databases built for very high write volume) never modify data in place — writes always go to an in-memory buffer first, which periodically flushes to disk as a new, immutable file; a background process called compaction later merges old files together and discards outdated data. This single design choice — update in place vs. append and merge later — is the real mechanism behind most storage engines' write-performance differences.

Try it: compare the write path for each

The precise mechanism behind Chapter 6.1's write slowdown

A B-tree write has to locate the exact leaf node responsible for the new value — a lookup that's fast while the tree fits in memory, but requires real disk reads once it doesn't, since finding the right spot to write means first reading several tree nodes from disk to navigate down to it. This is precisely 6.1's mechanism, now explained down to the actual data structure: it's not that writes are "slow" in some vague sense, it's that a B-tree write genuinely requires disk reads before the disk write can even happen, once the tree outgrows RAM.

Why LSM-trees would have avoided 6.1's specific problem

An LSM-tree write never needs to locate anything on disk first — it just appends to an in-memory buffer, an operation that stays fast regardless of total data size. This is exactly why databases built for extremely high write throughput (Cassandra, the kind of database that might genuinely suit Chapter 7's high-volume location updates or event logging) default to LSM-trees rather than B-trees — the write path is structurally insulated from the "index outgrew memory" problem that motivated Chirp's actual fix (splitting the database, then sharding).

The trade-off LSM-trees make in exchange: read cost and compaction overhead

Nothing is free. Because data isn't organized in one place, a read might need to check the in-memory buffer and several on-disk files before finding (or ruling out) a key — exactly the scenario where 11.5's bloom filters earn their keep, letting a read skip checking files that definitely don't contain the key. Compaction itself also consumes real background CPU and I/O, a genuine operational cost paid in exchange for that fast write path.
