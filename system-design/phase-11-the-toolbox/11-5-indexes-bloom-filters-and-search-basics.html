11.5 Indexes, bloom filters & search basics

Chapter 6.1 mentioned indexes growing too large for memory. Here's what an index actually is, and two more tricks that solve genuinely different problems.

TL;DR
A database index is a separate, sorted data structure (usually a B-tree) that lets the database find rows matching a condition without scanning every row — dramatically faster reads, at the cost of slightly slower writes (the index itself needs updating too, exactly 6.1's mechanism). A bloom filter is a compact, probabilistic structure answering "might this item exist?" — it can have false positives, but never false negatives, making it a very cheap first check before an expensive lookup. An inverted index (the core of search) maps each word to every document containing it, the opposite direction from a normal index — enabling fast full-text search.

Try it: play with a bloom filter

Why an index speeds reads but slows writes — the same mechanism from 6.1

Recall Chapter 6.1's mechanical explanation: every insert has to update every relevant index, not just the underlying table. A well-indexed table can answer "find this user's posts" almost instantly by looking up the index rather than scanning millions of rows — but that speed is bought by doing extra work on every write. Choosing which columns to index is a real trade-off: index too little, and reads stay slow; index too much, and writes suffer, exactly the tension 6.1 lived through directly.

Where a bloom filter earns its place: a cheap gatekeeper before an expensive check

A concrete real use: before checking whether a username is already taken (a real database query), first check a bloom filter containing all taken usernames. If the filter says "no," it's genuinely, guaranteed not taken — skip the database call entirely. If it says "maybe," only then do the real, more expensive database check. Since most username attempts during signup are actually available, this cheap first filter meaningfully reduces load on the real database — the exact same "avoid unnecessary expensive work" instinct from Chapter 4's caching, applied to a different kind of question (existence, not value).

Inverted indexes: the actual foundation of search

A normal index maps a row to its values. An inverted index flips this: it maps each distinct word to every document containing it. Searching for "weekend" becomes a fast lookup of the word "weekend" in the inverted index, instantly returning every matching post — instead of scanning every post's text for the word. This is the foundational structure behind Elasticsearch and virtually every real search engine, and it's exactly what Phase 12.6's search-autocomplete capstone builds on directly.
