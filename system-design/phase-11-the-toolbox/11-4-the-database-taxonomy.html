11.4 The database taxonomy

Chirp used Postgres for everything. Real systems often don't — different data shapes genuinely want different databases.

TL;DR
Relational (SQL) — structured, related tables with strong consistency guarantees; Chirp's default choice throughout this track. Document stores (MongoDB) — flexible, nested JSON-like records, good when data doesn't fit a rigid schema. Key-value stores (Redis, DynamoDB) — extremely fast lookups by a single key; Chirp's cache since Chapter 4 is exactly this. Wide-column (Cassandra) — built for massive write throughput across many machines. Graph databases (Neo4j) — optimized for relationship-heavy queries, like "friends of friends." Time-series (InfluxDB) — optimized for timestamped metrics data, like the very dashboards used throughout this track's incident banners.

Try it: match a data shape to its natural database type

Why Chirp could get away with "just Postgres" for so long

Relational databases are genuinely flexible generalists — capable of reasonably handling most of Chirp's actual data shapes (posts, users, follows) without needing a specialized database for each. The specialized types earn their place specifically when a workload's shape becomes extreme enough that a generalist database's trade-offs start to hurt — massive write volume (wide-column), deeply relationship-heavy queries at scale (graph), or genuinely schema-flexible data (document).

Where Chirp actually would benefit from a specialized database, honestly

The social graph (who follows whom) is exactly the kind of data a graph database handles more naturally than relational joins — "find mutual follows" or "suggest people you might know" queries get expensive in pure SQL as the graph grows, and get more natural in a database built specifically for graph traversal. This is a genuine, honest gap in Chirp's story worth naming: the narrative simplified to Postgres throughout, but a real system at Chirp's scale would very plausibly introduce a graph database specifically for the social graph.

The actual decision framework, not just a lookup table

The real question for any dataset: what's the dominant access pattern? Looking up one record by a known key (key-value)? Complex queries across related structured data (relational)? Traversing relationships (graph)? Extremely high write volume with simpler queries (wide-column)? Matching the database to the actual dominant pattern, rather than defaulting to whatever's already in use, is the transferable skill — not memorizing which specific product name goes with which label.
