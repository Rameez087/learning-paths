11.2 Rate limiting algorithms

Chapter 10.2 introduced rate limiting conceptually. Here's what's actually inside the box — four real algorithms, each with a genuinely different trade-off.

TL;DR
Token bucket: a bucket refills with tokens at a steady rate; each request consumes one; allows controlled bursts up to the bucket's capacity. Leaky bucket: requests queue and are processed at a strictly fixed rate, smoothing out bursts entirely. Fixed window counter: count requests in discrete time windows (e.g., per minute); simple, but allows a burst right at a window boundary. Sliding window: a more precise (and more expensive) version that avoids the boundary-burst problem by considering a continuously moving time window rather than fixed buckets.

Token bucket in code

class TokenBucket:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity
        self.tokens = capacity
        self.refill_rate = refill_rate  # tokens per second
        self.last_refill = time.now()

    def allow_request(self):
        now = time.now()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
        self.last_refill = now

        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False  # rate limited

Why token bucket is the common default, and when the alternatives win

Token bucket's ability to absorb a reasonable burst (a user rapid-clicking a few times) while still enforcing a steady average rate makes it a good general-purpose default. Leaky bucket is preferred when strict, perfectly smooth output is genuinely required — protecting a fragile downstream system that can't handle any burst at all, even a small one. Fixed window is the simplest to implement and reason about, appropriate when perfect precision at window boundaries doesn't matter much. Sliding window log or counter is chosen when boundary bursts are a real, unacceptable risk and the extra implementation cost is worth it.

The fixed-window boundary problem, made concrete

A fixed window allowing 100 requests/minute could theoretically allow 100 requests at 11:59:59 and another 100 at 12:00:00 — 200 requests in two seconds, technically compliant with "100 per minute" in each window, but clearly not the actual intent. This specific weakness is exactly what sliding window algorithms exist to close.
