11.17 Event sourcing & CQRS

Every database in Chirp's story stored current state — the latest value, overwriting the last. There's a genuinely different philosophy: store every change that ever happened, and never overwrite anything.

TL;DR
Event sourcing stores the full sequence of things that happened ("post created," "post edited," "post liked") rather than just the current state — current state becomes something you compute by replaying the events, not something you directly store and overwrite. CQRS (Command Query Responsibility Segregation) is the natural pairing: separate the model used for writes (append an event) from the model used for reads (a precomputed, query-optimized view built from those events) — genuinely the same shape as Chapter 5's read replicas, but generalized far beyond just database replication.

Try it: watch current state get derived by replaying events

Why this would have genuinely helped Chirp's edit-history problem

Recall Chapter 4.4: Chirp's cache showed a stale version of an edited post. With event sourcing, "what did this post look like five minutes ago" isn't a hard question at all — it's just replaying events up to that point in time. Chirp's actual database, storing only current state, has no memory of what a post looked like before its most recent edit. This is a real, concrete capability event sourcing provides that Chirp's actual architecture never had.

Why Chirp didn't actually need this, and that's a legitimate reason to skip it

Event sourcing adds real complexity: every piece of code that reads data now needs a materialized view built from events, rather than a simple table lookup, and replaying a long event history to rebuild a view has a real computational cost. Chirp's actual requirements — show the current feed, current profile, current follower count — never needed full history or audit trails badly enough to justify that complexity. This is the same judgment call from Chapter 1.1, reapplied: the right architecture matches the actual requirement, and "we might want history someday" isn't the same as "we need it now."

Where it genuinely earns its place: audit-critical systems

13.4's payment system is exactly the kind of place event sourcing shines — "show me every state this transaction has ever been in" is often a real, non-negotiable requirement (for disputes, compliance, debugging), not a nice-to-have. A system whose core value is an accurate historical record, rather than just current state, is where event sourcing's added complexity is worth paying for.
