11.1 API design principles

Chirp's services (Chapter 8) talk to each other constantly. What they say to each other, and how they say it, is its own design discipline.

TL;DR
REST models everything as resources (/posts/123) manipulated via HTTP verbs (GET, POST, PUT, DELETE) — simple, cacheable, and the default choice for most public APIs. GraphQL lets a client specify exactly which fields it needs across multiple resources in one request — powerful for complex, varied client needs, at the cost of losing simple HTTP caching. gRPC uses a strict binary protocol and generated code for fast, efficient service-to-service calls — the common choice for internal communication between services like Chirp's, where both ends are code you control. None is universally "best" — each fits a different communication shape.

Resource naming and status codes: the REST conventions worth internalizing

Resources are nouns, not verbs: /posts and /posts/123, never /getPost?id=123. HTTP status codes carry real meaning a client can act on programmatically: 200 success, 201 created, 400 bad request (client's fault), 404 not found, 429 rate limited (directly relevant to 11.2), 500 server error. Getting these right means a client can handle errors correctly without parsing response bodies just to figure out what went wrong.

Idempotent API design: extending 7.3's lesson to the API layer directly

Recall Chapter 7.3: at-least-once delivery means a request might arrive more than once — a client's network call times out, they retry, but the first request actually succeeded. A well-designed API supports an idempotency key: the client generates a unique ID for a logical operation (like "create this post") and sends it with every retry attempt; the server recognizes a repeated key and returns the original result instead of creating a duplicate. This is the exact same principle from 7.3, applied at the API contract level rather than inside a queue consumer. 

POST /posts
Idempotency-Key: a1b2c3d4-...

def create_post(request):
    key = request.headers["Idempotency-Key"]
    if redis.exists(f"idem:{key}"):
        return redis.get(f"idem:{key}")  # return original result, don't recreate

    result = database.create_post(request.body)
    redis.set(f"idem:{key}", result, expire_seconds=86400)
    return result

Versioning: designing for the API to change without breaking clients

An API used by external developers (or even other internal teams) can't change its contract freely without warning — a common approach is embedding a version in the URL (/v1/posts, /v2/posts) or a header, allowing old and new versions to run simultaneously while clients migrate. Skipping this and changing behavior silently is a frequent, avoidable source of production incidents.

Check your understanding

1. Why is gRPC typically the preferred choice for service-to-service communication within a system like Chirp's, rather than REST or GraphQL?
This is about matching the tool to the communication shape — internal, code-controlled communication has different priorities (speed, efficiency) than a public-facing API (broad compatibility, human readability).
2. How does an idempotency key solve the same underlying problem as Chapter 7.3's message deduplication, at a different layer?
This is the same pattern-recognition skill emphasized throughout this track — recognizing that "handle duplicate delivery safely" recurs in different disguises across different layers of a system.
3. Why does API versioning matter for an API with external or cross-team consumers?
This is a practical, common real-world discipline — unversioned APIs that change silently are a frequent, avoidable cause of production incidents for anyone depending on that contract.
