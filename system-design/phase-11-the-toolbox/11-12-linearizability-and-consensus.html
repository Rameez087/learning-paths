11.12 Linearizability & consensus

11.3's "C" in CAP has a precise name. 11.6's leader election is a specific instance of a much bigger idea. Here's both, named properly.

TL;DR
Linearizability is the strongest consistency guarantee: once any client's write completes, every subsequent read by any client sees that write (or a later one) — the system behaves as if there's only ever one copy of the data, updated instantaneously. Consensus is the general problem of getting multiple nodes to agree on a single value despite failures — and it's the actual mechanism that makes linearizable systems possible. 11.6's leader election was a specific instance of consensus (agreeing on "who's the leader"); named algorithms like Raft and Paxos solve the general version of this problem.

Why 11.3's CAP theorem "Consistency" specifically means this

When CAP theorem says a system chooses "Consistency" during a partition, it specifically means linearizability — every client sees the same, most up-to-date view, as if there were only one copy of the data. This is why Chapter 5's asynchronous replicas are explicitly not linearizable (5.3's whole bug was a read not seeing a very recent write) — Chirp deliberately chose availability and performance over this specific guarantee, precisely the trade-off named in 11.3.

Raft's core idea, at the level worth actually knowing

Raft (and Paxos, which solves the same problem differently) works by having nodes elect a leader — exactly 11.6's leader election, now recognized as literally running a consensus algorithm — and having that leader sequence all writes into a numbered log, which it replicates to followers. A write is only considered committed once a majority of nodes have it in their log — 11.6 and 11.10's quorum idea again, this time guaranteeing that even if the leader crashes immediately after, the committed write survives on whichever node becomes the new leader.

Where consensus shows up as a concrete building block: coordination services

Tools like ZooKeeper and etcd exist specifically to run consensus (via Raft or a similar protocol) as a reusable service, so individual applications don't need to implement it themselves. A system needing to reliably elect a leader, store configuration that must be linearizable, or coordinate distributed locks typically reaches for one of these rather than building consensus from scratch — the practical, real-world answer to "how do I actually get 11.6's leader election correctly implemented."
