7.3 Orchestration frameworks: graphs vs. chains

Why an entire framework category exists just to add loops and memory back into LLM pipelines.

TL;DR
A linear chain (3.5) can't express "retry this step," "loop until a condition is met," or "pause and wait for human approval before continuing." LangGraph, the most widely adopted framework for this as of 2026, models a workflow as a stateful, cyclic graph instead: nodes are functions that do work (an LLM call, a tool execution), edges (including conditional edges) decide what runs next, and a shared state object persists and updates across every step, checkpointed so execution can resume after a failure. According to one 2026 industry survey, over 60% of production agent incidents trace back to state-management failures — agents losing context mid-workflow, repeating steps, or crashing without recovery — which is precisely the failure class this graph model is built to prevent.

The three primitives

  • State — a shared, typed object every node can read and update. This is the workflow's persistent memory for a given run, not something re-derived from scratch at each step.
  • Nodes — Python functions that receive the current state, do something (an LLM call, a tool execution, a validation check), and return a partial state update.
  • Edges — transitions between nodes. A conditional edge routes to a different next node depending on the current state, which is exactly what implements branching and looping — a linear chain has no equivalent structure for this at all.

Why this matters more than it might seem

A linear chain fundamentally cannot express: "call a model, check the result, decide whether to retry or escalate, invoke two tools in parallel, then wait for human approval." Any of these control-flow patterns — retries, conditional branching, pausing for human input, looping until a condition is satisfied — require something with the structure of a graph, not a straight line of steps. This is the direct reason agent frameworks moved from simple chains toward explicit graph structures as agentic workflows (Phase 8) became genuinely non-linear.

Explicit graphs also change how failures are debugged

Because the graph structure is defined before execution and traversed deterministically, a node failure is localized: the graph identifies exactly which step produced the error, what its inputs were, and which downstream nodes never ran as a result. This is a qualitatively different debugging experience than an opaque single long-running process where a failure partway through leaves you guessing what state the system was actually in.

When you don't need this

If a workflow is genuinely linear — step A always leads to step B always leads to step C, no loops, no conditional branching, no need to persist state across a pause — a simple chain (3.5) is the right tool. Reaching for graph-based orchestration on a workflow that's actually linear adds complexity (state schema design, checkpointing) that isn't earning its keep.

Check your understanding

1. What can a graph-based workflow express that a linear chain cannot?
A linear chain only moves forward through a fixed sequence — it has no structural way to loop back, branch conditionally, or pause and resume, all of which a graph's conditional edges and cyclic structure support directly.
2. What was cited as the majority cause of production agent incidents in the 2026 survey referenced above?
Over 60% of incidents traced back to state issues in that survey — this is specifically what a persistent, checkpointed state object (as opposed to state that's implicitly discarded between steps) is designed to prevent.
3. When is a simple linear chain still the right choice over a graph-based framework?
Graph-based orchestration adds real complexity (state schema, checkpointing) that isn't worth it for a workflow that's actually linear — matching the tool to the actual shape of the task still applies here.
