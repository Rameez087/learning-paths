7.2 Fallback chains

If your app depends on a single LLM provider, you already have a fallback strategy: sit there and wait.

TL;DR
Every LLM provider has outages — reported figures for early 2026 include over a hundred incidents in a 90-day window for one major provider, and even a provider advertising 99.76% uptime still works out to roughly 16 hours of downtime a year. A fallback chain automatically switches to a backup model when the primary fails, times out, or hits a rate limit. The subtle but important detail: chain order should usually be set by cost, not just availability — if your fallback jumps straight to a 3x-more-expensive model, an outage silently triples your costs on top of already being disruptive.

Try it: simulate an outage and watch the fallback chain react

The three components of a resilient setup

  • The router — decides which model handles a request under normal conditions (7.1).
  • The gateway — a single entry point that handles authentication for every provider behind it, so your application code doesn't need separate integration logic per provider.
  • The fallback logic — automatically tries the next provider in the chain when the current one fails, ideally transparent to the end user.

Order by cost, not just by availability

A concrete illustrative case: if a cheap model costs roughly a tenth of your mid-tier model, and your fallback chain jumps straight from mid-tier to a model costing 3x the mid-tier price, then every minute of the primary provider's outage costs meaningfully more than normal operation — on top of the outage itself already being disruptive. The fix is explicit: structure the fallback chain so cost increases gradually as you move down it, rather than jumping straight to whatever "the best other option" happens to be.

Silent degradation is worse than an explicit failure

A specific production caution: when the preferred model for a task class is unavailable, the fallback needs to be an explicit, logged decision — not a silent substitution that quietly routes a task-specialized request to a mismatched model with different behavior. An explicit failure that surfaces in monitoring is easier to catch and fix than a silent quality regression nobody notices until users start complaining.

What to actually build

async def call_with_fallback(prompt, chain=["claude-sonnet", "gpt-4o", "claude-haiku"]):
    for model in chain:
        try:
            return await call_model(model, prompt, timeout=10)
        except (RateLimitError, TimeoutError, ServiceUnavailableError) as e:
            log_fallback_event(model, error=e)  # explicit, not silent
            continue
    raise AllProvidersFailedError()

Note the explicit exception types caught and the explicit logging call — this is the difference between a fallback system you can debug at 2am and one that silently degrades without anyone noticing until a customer complains.

Check your understanding

1. Why should a fallback chain be ordered by cost rather than purely by preference or availability?
An outage is already disruptive — a poorly-ordered fallback chain compounds that by also spiking costs, which is avoidable by structuring the chain so cost increases gradually rather than jumping to the priciest available option.
2. Why is silent degradation to a mismatched model considered worse than an explicit failure?
Visibility matters — an explicit, logged fallback event gives engineers a chance to notice and respond, while a silent substitution can persist undetected until it shows up as a user complaint.
3. What role does "the gateway" play in a multi-provider setup?
The gateway is an infrastructure layer distinct from the router — it's about unified access and credential management across providers, not about the model-selection logic itself.
