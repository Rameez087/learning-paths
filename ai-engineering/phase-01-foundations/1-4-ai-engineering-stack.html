1.4 The AI engineering stack

Where APIs, retrieval, agents, and evaluation each sit — and why this order matters.

TL;DR
The AI engineering stack has four layers, bottom to top: the foundation model (you don't build this), the prompt/API layer (how you talk to it), the retrieval & agent layer (how you give it knowledge and let it act), and the evaluation & ops layer (how you know it's actually working). Nearly every phase after this one in this track is a deep dive into one of the middle two layers.

Layer 1: the foundation model

This is GPT, Claude, Gemini, Llama, or similar — trained by a small number of labs at enormous cost. As an AI engineer, this layer is a dependency you consume via API, not something you build. It's worth remembering because it reframes what "AI engineering" even means: you're not competing on who has the smartest model, you're competing on how well you wire an already-smart model into a system that's reliable, fast, and cheap enough to ship.

Layer 2: prompt & API

This is the interface layer — system prompts, few-shot examples, structured output schemas, prompt versioning (covered in 1.3), plus the mechanics of actually calling a model: SDKs, streaming responses token-by-token instead of waiting for the full answer, function calling / tool use (letting the model request that your code run something), and async patterns for handling many concurrent requests without blocking. We'll build this layer hands-on in Phase 4.

Layer 3: retrieval & agents

A foundation model only knows what was in its training data, frozen at some cutoff date, plus whatever you put directly in the prompt. This layer is how you get around that:

  • Retrieval-Augmented Generation (RAG) — chunking your own documents, converting them to embeddings, storing them in a vector database, and retrieving the most relevant pieces to insert into the prompt at query time. This is reportedly the single most common pattern in real enterprise AI deployments — most production AI systems are RAG systems, not agents doing open-ended reasoning. Full treatment in Phase 6.
  • Agents — giving the model tools (functions, APIs, database queries) it can choose to call, and looping: reason about what to do, call a tool, observe the result, decide the next step. This is the ReAct (Reason + Act) pattern. Full treatment in Phase 8.
  • Multi-LLM orchestration — routing different requests to different models based on task type, cost, or latency needs, rather than sending everything to one model. Full treatment in Phase 7.

Layer 4: evaluation & operations

This is the layer most learning resources skip, and multiple 2026 industry sources single it out as the most underrated skill in the field: nearly every senior AI engineering role now expects experience designing evaluation pipelines, building golden datasets, and setting up LLM-as-a-judge workflows — before any fine-tuning work even starts. The reasoning is blunt: teams that can't measure whether their model's output is actually good cannot ship it safely, no matter how clever the prompt or how sophisticated the agent.

This layer also covers what happens after you ship: monitoring for model drift, cost tracking per request, latency budgets, and caching. Full treatment in Phases 9 and 11.

Why this order

It's tempting to jump straight to agents because they're the most exciting layer — but an agent built on unreliable prompts, with no retrieval grounding, and no way to evaluate whether it's working, tends to demo well and fail in production. This track follows the stack bottom-up on purpose: solid prompting and API mechanics first, then retrieval, then orchestration and agents, with evaluation threaded through from Phase 9 onward rather than bolted on at the end.
