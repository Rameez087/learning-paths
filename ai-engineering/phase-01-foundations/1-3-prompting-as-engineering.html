1.3 Prompting as an engineering skill

Prompts aren't magic words — they're the interface between your logic and the model. Treat them like code.

TL;DR
Four techniques cover most production prompting: role/context/task/format structure for basic clarity, few-shot examples to teach a pattern words can't fully describe, chain-of-thought to improve multi-step reasoning, and structured output to make responses machine-parseable. Beyond that, prompts need the same discipline as code: version control, test sets, and caching awareness.

The four-element structure

Most prompts that underperform are missing one of four things: role (who should the model act as), context (what background does it need), task (what exactly do you want done), and format (what shape should the output take). Stating the role explicitly — "You are a senior backend engineer reviewing this PR" versus no role at all — alone tends to lift output quality noticeably, most reliably on open-ended or creative tasks; on strict classification or factual lookups the effect is much smaller.

Few-shot: show, don't just tell

Few-shot prompting means giving the model 2–5 examples of the input/output pattern you want before handing it the real task. It's the most reliable way to enforce a specific format or handle a narrow domain task where the model's default instinct diverges from what you actually need — describing the difference in words is usually harder than just showing it.

A counterintuitive research finding worth internalizing: what matters most isn't that every example's label is perfectly correct — it's that the examples cover the diversity of your actual input space and demonstrate the label format. Even prompts with some deliberately mislabeled few-shot examples still outperformed giving the model no examples at all, because the examples were still teaching the model the shape of the task.

Chain-of-thought: only where it earns its cost

Asking a model to "think step by step" before answering measurably improves accuracy on problems with real reasoning depth — multi-step logic, trade-off analysis, anything with more than one valid path. But it isn't free: more reasoning means more tokens, more latency, and more chances for the model to drift off-task before it reaches an answer.

Two things worth knowing before you reach for it by default:

  • Skip it for dedicated reasoning models. Models with built-in extended thinking (Claude's Extended Thinking, OpenAI's o-series, Gemini's Thinking Mode) already reason internally before responding — explicitly telling them to "think step by step" on top of that is redundant.
  • Separate the reasoning from the final answer. The production pattern that works well: let the model reason at length internally, then require a short, fixed-format final answer — "return only the recommendation, top risks, and next action as bullet points." This keeps the output reviewable without losing the accuracy benefit of the reasoning.

Structured output: making responses parseable

If a prompt's output feeds into other code, plain prose is the wrong format — you want JSON, XML, or another schema you can parse reliably. The catch: asking for "valid JSON" without specifying exact keys, types, and edge cases still produces inconsistent results. Structure only helps when the contract is fully explicit.

  "confidence": number,      // 0.0 to 1.0
  "reasoning": string        // one sentence, max 20 words
}

Treating prompts like production code

Once a prompt runs more than once in a real system, three engineering habits stop being optional:

  • Version control your prompts. Prompt drift is real: you adjust wording on a Thursday, forget exactly what changed, and spend Monday debugging output that used to be reliable.
  • Build a golden test set. A small set of representative inputs with expected outputs, run against every prompt change — this is regression testing, except the "code" under test is the instructions themselves.
  • Order content for caching. Put static content — system instructions, few-shot examples, tool definitions — first, and variable content — the actual user message — last. Many providers cache the static prefix, which cuts cost and latency on repeated calls.

Caching works on a static prefix — if the same system instructions and examples appear at the start of every call, the provider can cache and reuse that portion, cutting cost and latency.
