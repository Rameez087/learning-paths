1.5 Your first LLM call

Everything from 1.1–1.4, made real in eight lines of code.

TL;DR
A working LLM integration is: install the SDK, set an API key as an environment variable (never hardcode it), call client.messages.create() with a model, a token limit, and a message list, then read the text back out of the response. Everything more advanced in this track — RAG, agents, orchestration — is this same call, wrapped in more machinery.

Setup

python -m venv venv
source venv/bin/activate      # on Windows: venv\Scripts\activate
pip install anthropic

export ANTHROPIC_API_KEY="sk-ant-your-key-here"

Get an API key from the Anthropic Console. Setting it as an environment variable rather than pasting it into your code isn't a nitpick — a hardcoded key is exactly the kind of thing that ends up committed to a public GitHub repo by accident, and API keys are billable secrets. The SDK reads ANTHROPIC_API_KEY automatically, so your code never touches the raw key at all.

The call

import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

message = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[
        {"role": "user", "content": "Explain what a race condition is, in two sentences."}
    ]
)

print(message.content[0].text)

Trace this back to 1.2 and 1.3: messages is the token sequence the model attends over. max_tokens caps how many times the predict→sample→append loop is allowed to run. The absence of a system parameter here means there's no role definition — the model is answering with its default behavior, not as any particular persona.

Adding a system prompt

This is 1.3's role/context/task/format structure, expressed as code. The system parameter sets standing instructions that apply to the whole conversation, separate from the user's actual message: 

message = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system="You are a senior backend engineer. Answer concisely, in plain English, with no code unless explicitly asked for it.",
    messages=[
        {"role": "user", "content": "Explain what a race condition is, in two sentences."}
    ]
)

Reading the response object

message.content is a list of content blocks — usually one text block, but a response can contain multiple blocks (for example, a thinking block followed by a text block, if extended thinking is enabled). Production code should check block types rather than always assuming content[0] is the text you want: 

for block in message.content:
    if block.type == "text":
        print(block.text)

Tracking cost as you go

Every response includes token usage — this is the "tok / tok/s / cost" readout from the live orchestration visual back in Phase 1's overview. Reading this from day one builds the habit that becomes essential once you're running many calls in Phase 7's orchestration work: 

print(message.usage.input_tokens, message.usage.output_tokens)

Check your understanding

1. Why should an API key be set as an environment variable instead of hardcoded in a script?
This is a security practice, not a technical requirement of the SDK — a leaked key in a public repo can be used by anyone to run billable requests on your account.
2. What does the system parameter do that a user message doesn't?
The system prompt is where role/context instructions live, separate from the specific user turn — it's the code-level expression of the four-element prompt structure from 1.3.
3. Why check block.type == "text" instead of always reading message.content[0]?
Content blocks can include types beyond plain text, such as thinking blocks when extended thinking is enabled — checking the type is more robust than assuming a fixed position.
