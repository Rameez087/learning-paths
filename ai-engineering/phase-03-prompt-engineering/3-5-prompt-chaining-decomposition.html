3.5 Prompt chaining & task decomposition

Divide and conquer, applied to LLM calls instead of algorithms.

TL;DR
Instead of asking one LLM call to solve a complex, multi-part task in a single monolithic prompt, prompt chaining breaks it into a sequence of smaller calls — each with a narrow, well-defined job, each passing its output forward as the next step's input. Research comparing this to single-prompt approaches has found accuracy improvements as large as 15.6% on multi-step tasks. The trade-off is latency and cost — more calls means more round trips — so chaining earns its complexity on tasks that are genuinely sequential, not on tasks a single well-structured prompt already handles fine.

Why decomposition beats one giant prompt

  • Each step is simpler. A prompt with one narrow job is easier to get right, easier to debug, and less likely to silently drop part of a compound instruction the way an overloaded single prompt can.
  • Intermediate results are inspectable. When something goes wrong, you can see exactly which stage produced the bad output, instead of debugging one long, opaque final response.
  • Different steps can use different models or settings. A cheap, fast model can handle an easy extraction step; a stronger model can be reserved for the step that actually needs deep reasoning — this is the seed of the multi-LLM orchestration in Phase 7.
  • Structured output between steps acts like an API contract. If step 1 emits a defined JSON shape rather than loose prose, step 2 can consume it reliably — unstructured text passed between steps is fragile and prone to silent misinterpretation.

Validation gates between steps

A chain without checks between steps just moves the "hope it worked" problem further down the pipeline. The stronger pattern adds a gate after each step — either a programmatic check (does the output match the expected schema? is a required field non-empty?) or an LLM-based check (does this summary actually reflect the source content?) — that catches a bad intermediate result before it propagates into every downstream step and quietly corrupts the final output.

When chaining is the wrong tool

Chaining assumes the steps are genuinely sequential — each one depends on the previous step's output before it can meaningfully begin. Two adjacent mistakes worth naming:

  • Don't chain independent subtasks that could run in parallel. If step 2 and step 3 don't actually need each other's output, forcing them into a sequence just adds latency for no benefit — that's a parallelization problem, not a chaining one.
  • Don't chain what a single well-structured prompt already handles. If a task genuinely fits in one prompt with clear role/context/task/format (1.3) and doesn't require intermediate decisions, added chain steps are pure overhead — more latency, more cost, more places to fail, no accuracy benefit.

Check your understanding

1. What is the core mechanism of prompt chaining?
Chaining is explicitly sequential and modular — a series of narrow, purpose-built prompts, not repeated sampling of one prompt (that's self-consistency, 3.1) and not a single monolithic instruction.
2. What does a validation gate between chain steps protect against?
Without a check between steps, an error in step 1 flows unnoticed into steps 2, 3, and 4 — a gate catches it early, before it corrupts the whole pipeline's output.
3. When is prompt chaining the wrong choice?
Chaining specifically fits genuinely sequential dependencies. Forcing independent subtasks into a sequence adds latency for no benefit, and adding chain steps to a task a single prompt already solves just adds cost and failure points.
