8.3 Multi-agent patterns

Reported industry data: roughly 40% of multi-agent pilots fail — usually from picking the wrong coordination pattern, not the wrong model.

TL;DR
Multi-agent systems divide a complex task among several specialized agents that coordinate through a defined structure, rather than one agent handling everything with many tools. Industry guidance is blunt about when to actually reach for this: use the lowest level of complexity that reliably meets your requirements — most tasks don't need multiple agents at all, and starting there anyway is reported as the single most common architecture mistake teams make. When you do need it, the coordination pattern you pick matters more than which model powers each agent.

Try it: explore the patterns and their real failure modes

The decision framework practitioners actually use

  • Known task decomposition, fixed subtasks → orchestrator-worker (a single point of accountability delegates known subtasks to specialists).
  • Fixed linear steps that never change order → sequential pipeline (this is 3.5's chaining, applied across separate agents instead of separate prompts).
  • Four or more genuinely independent tasks → fan-out/fan-in (parallel, no dependencies between branches).
  • Open-ended problems with no predetermined solution path → manager/supervisor pattern, where the plan itself is discovered through iteration rather than fixed upfront.

Why "start simple" isn't just caution — it's backed by real failure data

Reported figures describe a roughly 1,445% increase in enterprise interest in multi-agent systems within about a year, alongside organizations now running a double-digit average number of agents in production. But interest and adoption running ahead of reliability shows up directly in the pilot failure rate — the recommendation from teams who've actually shipped these systems is consistently to under-build rather than over-build: pick the simplest pattern that structurally fits the problem, and only add coordination complexity when a single agent demonstrably fails on tool selection, context capacity, or multi-step reasoning.

Check your understanding

1. What is the most commonly cited architecture mistake teams make with multi-agent systems in 2026?
Industry guidance is explicit: use the lowest level of complexity that reliably meets requirements — most tasks don't need coordination overhead at all, and adding it unnecessarily is the more common failure than under-architecting.
2. When does the manager/supervisor pattern (plan discovered through iteration) fit best?
Unlike orchestrator-worker (known subtasks upfront), the manager pattern is specifically for cases where the plan itself has to be discovered and can pivot mid-execution based on what's found.

This is a specific, named trade-off of the pattern's flexibility — the same iterative discovery that lets it handle open-ended problems also means wasted branches are a real, hard-to-budget cost.
