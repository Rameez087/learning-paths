8.2 Tool design for agents

In a single tool call (4.2), a bad description costs you one wrong answer. In an agent loop, it costs you a runaway chain of them.

TL;DR
Everything from 4.2 about tool schemas applies here, at higher stakes: an agent selects tools repeatedly, autonomously, across many steps with no human reviewing each individual choice. A vague tool description that occasionally misfires in a single-call context can compound into genuine goal drift or wasted work across a long agent loop. Good agent tool design means narrow, single-purpose tools with unambiguous names and descriptions, explicit boundaries on what the tool does and doesn't do, and — critically — giving the agent only the tools it actually needs for its task, not everything available.

The principle of least privilege, applied to agent tools

  

    This connects directly back to 3.4's defense-in-depth guidance: give an agent only the tools
    and data access it strictly needs for its specific task, nothing more. An agent that can't send
    email cannot be tricked into exfiltrating data via email, regardless of what a prompt injection
    or a reasoning error tells it to do. This isn't a security afterthought bolted on — it's a
    design decision made when the tool list is first assembled.
  


  
Narrow tools beat swiss-army-knife tools

  

    A single tool that does five different things based on a "mode" parameter is harder for a model
    to select correctly than five separate, narrowly-scoped tools each with an unambiguous purpose.
    This mirrors good API design generally, but the stakes are higher here: a human developer
    reading confusing documentation can still figure out the right call by trial and error; an
    agent making the wrong tool selection autonomously, mid-loop, often just proceeds confidently
    with the wrong result unless something explicitly catches it.
  


  
Explicit failure handling in the tool contract

  

    A tool's schema should make clear what happens when it fails — a malformed input, a timeout, a
    permission error — rather than leaving the agent to guess. Production agent frameworks
    typically require this explicitly: what error shape gets returned, and what the agent should do
    with it (retry, escalate, report back to the user), rather than assuming the agent will figure
    out sensible fallback behavior from an empty or ambiguous error response.
  


  

    
Check your understanding

    

      
1. Why does tool description quality matter more in an agent loop than in a single tool call?

      

        
        
        
      

      
Every tool selection in an agent loop compounds — a subtly wrong choice early on can cascade through subsequent reasoning and actions, unlike a single tool call where the "blast radius" of a bad selection is contained to that one exchange.

    

    

      
2. Why is giving an agent only the minimum tools it needs a security practice, not just tidiness?

      

        
        
        
      

      
This is the same principle from 3.4's defense-in-depth guidance, applied to tool design directly — restricting capability is a real mitigation against both prompt injection and simple agent reasoning errors.

    

    

      
3. Why do narrow, single-purpose tools tend to work better than one multi-mode tool?

      

        
        
        
      

      
This mirrors general API design wisdom, but the stakes for an autonomous agent are higher — a wrong "mode" selection often proceeds silently rather than being caught the way a confused human developer might catch their own mistake.
