9.3 Offline vs. online evals

A pre-release gate and a production dashboard are two different tools with two different jobs.

TL;DR
Offline evaluation runs before a change ships — against the golden dataset (9.1), gating a deployment based on whether metrics hold or regress. Online evaluation runs continuously against real production traffic after a change has shipped, watching for drift, sampling low-confidence cases into human review, and feeding genuinely new failures back into the golden dataset. Neither replaces the other: offline evals catch regressions before users see them; online evals catch the failure modes that only show up once real, unpredictable users start using the system.

Where each fits in the development lifecycle

  • Pre-release / CI gate — before any new model version or major prompt change ships, run offline evals against both the golden dataset (catching known failure patterns) and a red-team dataset covering adversarial inputs and known attack patterns from 3.4. The golden dataset covers failures already seen; adversarial pre-release testing is specifically for finding the ones that haven't been seen yet.
  • Continuous production monitoring — once shipped, online evals (often using the same reference-free LLM-judge metrics from 9.2) sample real traffic, track quality metrics over time, and specifically watch for drift: quality degrading gradually in a way a single offline snapshot would never catch.

The closed loop that makes both stronger over time

The two aren't independent — production monitoring is what feeds the next golden dataset. Low-confidence or low-scoring cases sampled from real traffic get routed to human review, and every meaningful production failure identified this way becomes a future regression test case added to the golden set. This closes the loop: offline evals get better specifically because online monitoring keeps surfacing gaps the current golden dataset doesn't cover.

What a CI gate actually checks

A deployment gate compares the candidate version's metrics against the current production version's baseline on the same golden dataset — not against an absolute pass/fail threshold in isolation, but as a regression check. A metric holding steady or improving passes; a metric regressing beyond an agreed tolerance blocks the deployment until investigated. This is exactly analogous to a software test suite blocking a merge, except the "tests" here are quality metrics computed by deterministic checks and calibrated LLM judges rather than assertions on exact output.

Check your understanding

1. What is the primary purpose of an offline eval in the deployment lifecycle?
Offline evaluation is specifically a pre-release check against a known, curated dataset — its job is to catch a regression before real users ever see it.
2. What kind of failure can online evaluation catch that offline evaluation typically cannot?
A golden dataset is fixed and known in advance — it can't capture novel failure patterns real users produce, or a slow quality decline that only shows up when watched continuously over time.
3. How does online evaluation make offline evaluation better over time?
This closed loop is central to why evaluation programs improve — real failures surfaced in production become the next generation of regression tests, keeping the golden dataset representative of what actually goes wrong.
