6.5 Knowledge graphs for RAG

Vector search tells you which chunks are similar. A knowledge graph tells you how the things in those chunks actually relate to each other.

TL;DR
Vector RAG (Phases 5-6 so far) represents everything as geometry — meaning as position in vector space. It's fast, cheap, and good at "find me the passage about X." It has no native concept of how X relates to Y unless that relationship happens to be spelled out in the same chunk. A knowledge graph stores entities as nodes and explicit relationships as edges, making multi-hop reasoning ("how did A affect B, which affected C?") a graph traversal instead of a hopeful similarity search. GraphRAG combines both: vector search for broad recall, graph traversal for connected, relational context. One AWS-published benchmark found adding graph structure lifted answer precision by up to 35% on exactly the query types vector search struggles with.

The ambiguity problem, concretely

Consider the word "Java." Depending on context, it's an island, a programming language, or a coffee brand — and in raw vector space, without enough surrounding text, these can cluster ambiguously. A knowledge graph resolves this structurally: a node for "Java" connected by edges to "runtime environments" and "Oracle" is unambiguous by construction, because the relationship itself is stored explicitly rather than inferred from proximity in embedding space.

Where the benchmark gap is largest

Reported results on enterprise analytics queries found vector RAG achieving roughly 16.7% accuracy overall, dropping to 0% specifically on questions requiring aggregation across metrics, KPIs, or strategic entities — while GraphRAG held between 56-80% across those same categories. On multi-hop reasoning tasks more broadly, GraphRAG has been reported reaching 80-85% accuracy where vector RAG stalls around 45-50%. The pattern is consistent: the gap widens specifically as query complexity increases — more entities, more logical hops — which is exactly where pure similarity search degrades.

The real cost: this isn't a free upgrade

Building a knowledge graph requires entity extraction and entity resolution (merging different mentions of the same real-world entity — "Bob Smith," "R. Smith," and "the CEO" might all need to resolve to one node), and this is an ongoing process as the corpus grows, not a one-time construction pass. Getting an extraction wrong has a "correction cascade" cost — fixing one bad extraction can require re-checking every downstream summary or aggregation that depended on it. This upfront and ongoing maintenance cost is exactly why GraphRAG is a deliberate, evaluated decision, not a default upgrade over vector RAG.

The honest 2026 framing: route, don't replace

Current guidance is specific: don't frame this as "GraphRAG vs. RAG" as a single up-front architectural choice made once. Most real production queries have a content dimension, a relational dimension, or both — the practical pattern is a hybrid router (echoing 5.4's hybrid search) that selects a graph path, a vector path, or both per query, rather than committing to graph-only or vector-only as a blanket policy across every request type.

Check your understanding

1. Why does vector RAG struggle with a query like "how did the delay in Project Apollo affect Q3 APAC margins?"
Vector similarity retrieves relevant chunks about each entity independently — it has no built-in mechanism for representing or traversing the specific causal link between them, which is exactly what a graph edge would capture explicitly.
2. Why is entity resolution described as an ongoing process rather than a one-time setup step?
As new documents are added, new mentions and name variants of existing entities appear, and these need continuous resolution to the correct canonical node — this ongoing cost is part of what makes GraphRAG a deliberate investment.
3. What's the recommended 2026 framing for choosing between vector RAG and GraphRAG?
Current guidance specifically warns against treating this as a single once-made architectural choice — most real query traffic has a mix of content-similarity needs and relational needs, best served by routing per query rather than committing entirely to one approach.
