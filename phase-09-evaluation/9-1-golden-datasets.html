Phase 9 · Evaluation

9.1 Golden datasets

The foundation everything else in this phase is built on — and the one thing you cannot skip.

TL;DR
A golden dataset is a curated set of representative inputs with known-good expected outputs (or expert-graded verdicts), used to measure whether your system actually works — as opposed to public leaderboards (MMLU, HumanEval, GSM8K), which measure base model capability in isolation and say very little once you add retrieval, tools, a system prompt, and your actual workflow on top. Practical 2026 guidance is specific: start with roughly 50 real failure cases, have a domain expert grade them pass/fail with written critiques, and build outward from there — not a sprawling 500-example dataset assembled before you've shipped anything to evaluate.

Why leaderboard benchmarks aren't your evaluation

Public benchmarks were designed to compare base models against each other under controlled conditions — they help narrow a model shortlist. But the same model can score differently on the identical benchmark depending on evaluation protocol details like zero-shot versus few-shot testing, and none of these benchmarks account for what actually determines your system's real behavior: your retrieval layer, your tool definitions, your system prompt, and the specific workflow your users actually run. A model topping a leaderboard is not the same claim as "this system works for my use case."

Where real examples should come from

  • Production logs — representative sessions pulled across user segments and difficulty levels, with privacy filters applied before anything is stored (this connects to the sensitive-data handling covered throughout Phase 3.4's security material).
  • Real failures, prioritized first — every meaningful production failure should become a future regression test case. This is more valuable early on than a large volume of examples the system already handles correctly.
  • Adversarial / red-team cases — deliberately constructed edge cases and known attack patterns (prompt injection variants from 3.4, malformed inputs), specifically for pre-release testing before a new model version or major prompt change ships.

Three types of checks belong in the dataset, at different costs

  • Deterministic / sanity checks — does the JSON parse? Does the classifier return one of the four expected labels? These run in milliseconds and catch obvious breakage before anything reaches a slower, more expensive judge.
  • Statistical checks — regex matching, keyword presence, simple heuristics.
  • LLM-as-a-judge — for genuinely open-ended quality questions a deterministic check can't capture (covered fully in 9.2), and the most expensive of the three per example.

A specifically flagged mistake: teams that skip the cheap deterministic layer and route everything straight to an LLM judge end up with slow, expensive pipelines doing work a 5ms check could have filtered out first.

Check your understanding

1. Why doesn't a strong score on a public benchmark like MMLU guarantee your specific application works well?
Everything your production system adds on top of the base model — RAG, tools, prompts, user-specific context — is exactly what a general leaderboard score doesn't account for.
2. What's the practical recommendation for starting a golden dataset from scratch?
2026 practitioner guidance specifically warns against sprawling upfront dataset construction — starting small with real, graded failures and expanding based on what you actually learn ships faster and stays more relevant.
3. Why check deterministic/sanity conditions before routing an output to an LLM judge?
This is a cost and speed optimization, not an accuracy claim — obvious failures (malformed JSON, wrong label set) don't need an expensive judge call to catch, so filtering them out first keeps the pipeline fast and cheap.
