4.1 Streaming responses

Same total wait time, radically different feel — and when it's not worth the complexity.

TL;DR
Without streaming, the server builds the entire response before sending a single byte — the user stares at a blank screen for the full generation time. Streaming ships each token over Server-Sent Events (SSE) the moment it's produced, so perceived latency drops from seconds to milliseconds even though total generation time is identical. Roughly 80% of user-facing calls benefit from streaming; roughly 80% of backend, non-interactive calls don't — matching the tool to the task matters more than defaulting to either.

The mechanism: Server-Sent Events

Streaming works over an HTTP connection kept open, with the server pushing small chunks as they're ready rather than closing the connection after one full response. Client code sets stream=True on the request, then reads incrementally: parse each incoming chunk as it arrives, extract the token, append it to the display, repeat. 

with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Explain quicksort."}]
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)

When streaming is overhead, not benefit

  • Short responses under ~50 tokens. If the full response completes in under half a second anyway, the connection management and chunk-parsing overhead of streaming adds complexity without a visible UX improvement.
  • Backend, non-interactive calls. A batch job classifying 10,000 support tickets overnight has no user watching a screen — there's nothing to make feel faster, so plain request/response is simpler and easier to reason about.
  • Anywhere you need the complete response before proceeding. If your code parses the full output as structured JSON (3.2) before doing anything with it, streaming individual tokens doesn't help — you're waiting for the closing brace regardless.

Streaming and tool calls interact carefully

When a model can call tools (4.2), the stream needs to distinguish plain text chunks from tool-call chunks as they arrive — production streaming code checks the event type on each chunk rather than assuming everything is displayable text. Getting this wrong is a real failure mode: partially-streamed tool call arguments displayed as if they were prose confuses users and can even leak internal call structure into a chat UI.

Check your understanding

1. Does streaming reduce the total time an LLM takes to generate a full response?
Streaming is purely a delivery mechanism — it changes perceived latency, not the underlying compute time the model needs to produce every token.
2. Why might a backend batch job NOT benefit from streaming?
Streaming's entire value proposition is about the user's experience of waiting — a job with no human watching in real time gains nothing from token-by-token delivery.
3. Why does mixing streaming with tool calls require extra care?
A streamed response can interleave text and tool-call chunks — treating a tool-call chunk as displayable text is a real production bug that can leak internal structure into a user-facing UI.
