4.3 Async & concurrent requests

30 sequential API calls take a minute. The same 30 calls, concurrent, take a few seconds.

TL;DR
An LLM API call spends almost all its time waiting on the network, not using your CPU — which makes it a textbook case for async/await concurrency. Firing 30 independent calls one at a time (sequentially) versus concurrently via asyncio.gather() is the difference between roughly 40–65 seconds and roughly 2–4 seconds in real published benchmarks, for identical work. The catch: unbounded concurrency slams into provider rate limits, so production code caps concurrency with a semaphore and layers in retry-with-backoff for when limits are hit anyway.

The core pattern: gather + semaphore

import asyncio
from openai import AsyncOpenAI

client = AsyncOpenAI()
SEMAPHORE = asyncio.Semaphore(5)  # never more than 5 requests in flight

async def call_one(prompt: str) -> str:
    async with SEMAPHORE:
        resp = await client.chat.completions.create(
            model="gpt-5-nano",
            messages=[{"role": "user", "content": prompt}]
        )
        return resp.choices[0].message.content

results = await asyncio.gather(
    *(call_one(p) for p in prompts),
    return_exceptions=True   # one failed call shouldn't crash the whole batch
)

The semaphore is doing real work here: without it, asyncio.gather() would fire every request at once, and a batch of a few hundred prompts would immediately trip the provider's rate limits. The semaphore caps how many requests are ever "in flight" simultaneously, regardless of how many total tasks are queued up.

What gather() alone doesn't give you

A semaphore plus gather() is genuinely enough for a small script. It is not enough for a production batch pipeline, which typically also needs:

  • Coordinated rate-limit cooldowns — when a 429 (rate limited) error comes back, backing off just that request isn't enough if every other concurrent task keeps hammering the same throttled endpoint.
  • Retry with exponential backoff — on a rate-limit or transient error, wait progressively longer between retries rather than immediately re-firing.
  • Token and cost accounting for failed attempts — a naive setup only tracks tokens for successful calls, silently under-counting real spend.
  • Bounded memory for very large batches — gather() builds every coroutine up front; streaming a million prompts through constant memory needs a different structure (a bounded queue of workers, not one giant gather call).

Check your understanding

1. Why are LLM API calls a good fit for async concurrency specifically?
Async concurrency shines specifically for I/O-bound work — while one request is waiting on the network, the event loop can be making progress on other requests instead of sitting idle.
2. What problem does a semaphore solve in concurrent LLM calls?
Without a concurrency cap, gather() would fire every task's request at once — a semaphore limits how many can be actively running, regardless of the total number queued.
3. What's a real limitation of plain asyncio.gather() for a large production batch?
gather() builds the full list of coroutines before running them — for a genuinely huge batch (hundreds of thousands of prompts), that doesn't fit in bounded memory, which is why production tools use a bounded worker-queue pattern instead.
