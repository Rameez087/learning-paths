4.4 Cost & token accounting

A $10,000/month bill dropping to $2,000 usually comes from three specific changes, not general belt-tightening.

TL;DR
Three techniques account for most of the achievable savings in production LLM costs: prompt caching (up to 90% off repeated input tokens), model routing (sending easy tasks to a cheaper model instead of your best one), and batch processing (roughly 50% off when results don't need to come back immediately). Combined, these three commonly cut total spend by 70%+ without a quality trade-off — because none of them change what the model produces, only how efficiently you're paying for it.

Prompt caching: the highest-leverage lever

Every LLM call recomputes attention key-value tensors for every input token. Prompt caching stores those computed tensors server-side, so if your next request starts with the same prefix, the model skips recomputation entirely and loads the cached result instead. On Anthropic's API, a cache read costs roughly 10% of the standard input rate — a 90% discount on any repeated prefix. This is why 3.1's "static content first, variable content last" ordering advice isn't just tidy structure — it's the difference between a cache hit and a cache miss on every single call.

A concrete illustrative case from real reported usage: a pipeline resending a 3,500-token system prompt roughly 12,000 times a month was paying about $180/month just on that redundant input. Turning on caching and moving latency-tolerant work to the batch API cut that same pipeline's bill by 61% — with byte-identical output quality.

Model routing: not every task needs your best model

Reported industry estimates put roughly 80% of routine production tasks as handleable by a cheap, fast model without measurably hurting output quality — classification, simple extraction, short summarization. Reserving an expensive premium model for the genuinely hard 20% (deep reasoning, nuanced writing, high-stakes decisions) is the single highest-ROI change most teams can make, often described as a few lines of routing logic. This is the practical, cost-driven version of the multi-LLM orchestration we'll build out fully in Phase 7.

What to actually monitor

  • Input vs. output token ratio. Output tokens commonly cost 2–5x more than input tokens per token — capping max_tokens aggressively on tasks that don't need long responses is free money.
  • Cache hit rate. Most providers surface this directly in the response (e.g. a cached_tokens field) — wire it into monitoring so a silent regression (a prompt structure change that breaks caching) triggers an alert instead of a surprise invoice.
  • Cost on failed attempts. A naive tracking setup only counts tokens spent on successful calls, quietly under-reporting real spend from retries and validation failures.
  • Token counts across model generations aren't directly comparable. A newer tokenizer can produce meaningfully more tokens for identical text than an older one from the same vendor — always re-measure with the actual model in use rather than assuming last quarter's per-token estimate still holds.

Check your understanding

1. Why does prompt caching require static content first, variable content last (from 3.1)?
Prompt caching stores computed tensors for a prefix — if the user's variable query sits at the start, no two calls share an identical prefix, and the cache never gets a chance to hit.
2. What does model routing save money by doing?
Routing is selective, not uniform — the savings come from matching task difficulty to model cost, not from downgrading everything to the cheapest tier regardless of what the task needs.
3. Why is it risky to compare token-based cost estimates across different model generations from the same vendor?
Applying a price-per-token from one model generation to a token count measured on a different generation's tokenizer can leave a budget estimate off by a meaningful margin — always re-measure with the actual model in use.
