4.2 Function calling & tool use

How a model that can only generate text ends up looking up your database.

TL;DR
An LLM can't actually run code or query a database — it can only generate text. Tool use closes that gap: you describe available functions in a schema, the model decides when a function call would help, and it outputs a structured request to call one (arguments included) instead of a normal answer. Your code executes the actual function, then feeds the result back to the model as a new message, and the model continues from there — often producing a final natural-language answer that incorporates the tool's result. This request→execute→feed-back loop is the seed of everything in Phase 8's agents.

Try it: step through a real tool-use loop

A user asks about the weather. The model doesn't know current weather — it has no way to. Watch it call a tool instead of guessing.

The three-part schema

Every tool definition your code hands the model needs three things:

{
  "name": "get_weather",
  "description": "Get current weather for a city. Use this whenever the user asks about current conditions.",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "City name, e.g. 'Boston'"}
    },
    "required": ["city"]
  }
}

The description field matters more than it looks — it's the only signal the model has for when to reach for this tool versus answering directly or picking a different tool. A vague description ("weather stuff") produces unreliable tool selection; a specific one tied to concrete trigger conditions produces reliable selection.

The recommended execution pattern

Production tool-calling code generally follows: model suggests tool → your code executes it → model summarizes the result — explicitly not letting the model's suggested call run unchecked. Your code is the trust boundary: it decides whether the requested call is safe to actually execute, with what permissions, and what happens if it fails. 

messages = [{"role": "user", "content": "What's the weather in Boston?"}]

response = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=1024,
    tools=[weather_tool], messages=messages
)

if response.stop_reason == "tool_use":
    tool_call = next(b for b in response.content if b.type == "tool_use")
    result = get_weather(**tool_call.input)   # your actual function runs here

    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": tool_call.id, "content": str(result)}
    ]})
    final = client.messages.create(model="claude-sonnet-4-6", max_tokens=1024,
                                    tools=[weather_tool], messages=messages)

Why "the schema is a hint, not a hard constraint" (from 3.2) matters here

Even with a well-written schema, the model can occasionally suggest a call with a slightly wrong argument type or an oddly-shaped value. This is exactly why 3.2's Tier 3 (native structured output / constrained decoding) matters for tool arguments specifically — it's the difference between "the model usually gets the arguments right" and "the arguments are guaranteed to match the schema before your function ever runs."

Check your understanding

1. What does the model actually do when it "calls" a tool?
The model has no execution ability of its own — it produces text describing which tool it wants called and with what arguments; your application code is what actually runs anything.
2. Why does a tool's "description" field matter so much for reliability?
Tool selection is driven by the model reading the description and matching it against the user's request — vague descriptions produce unreliable selection regardless of how well-formed the input schema is.
3. Why shouldn't a model's suggested tool call be executed unchecked?
The recommended pattern explicitly separates "model suggests" from "code executes" — this is where permission checks, argument validation, and error handling belong, a theme that becomes central in Phase 8's agent design.
